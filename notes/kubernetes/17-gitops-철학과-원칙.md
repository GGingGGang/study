# GitOps 철학과 원칙 (GitOps Philosophy & Principles)

> 쿠버네티스 · GitOps · 학습내용: GitOps가 등장한 배경(push형 CD·수동 kubectl의 문제 — 드리프트·감사 난해·롤백 난해), 핵심 철학(선언형·Git 단일 진실 소스·지속적 조정·드리프트 탐지/교정), OpenGitOps 4원칙 상세, Pull vs Push CD 비교와 보안 경계, CI/CD 책임 분리, 장점과 한계(시크릿·비선언 작업)

---

## 1. GitOps가 뭐고 왜 등장했나

**GitOps**는 시스템의 **원하는 상태(desired state)** 를 전부 **Git 저장소에 선언형으로 기록**하고, 자동화된 **에이전트(컨트롤러)** 가 그 Git 상태와 클러스터의 **실제 상태(actual state)** 를 **계속 비교·일치시키는** 운영 방식이다. 한마디로 **"Git에 적힌 것이 곧 운영 환경"** 이 되도록 만드는 패러다임이다.

GitOps라는 용어는 2017년 Weaveworks가 정립했고, 이후 **OpenGitOps**(CNCF 산하 working group)가 벤더 중립적인 **4가지 원칙**으로 표준화했다. 즉 GitOps는 특정 제품 이름이 아니라 **운영 모델/원칙의 집합**이며, 그것을 구현하는 도구가 여러 개 존재하는 것이다.

### 1.1 GitOps 이전 — 무엇이 문제였나

GitOps가 풀려는 문제는 기존 배포 방식의 고통에서 나온다.

- **수동 `kubectl apply`**: 사람이 로컬에서 매니페스트를 직접 적용. 누가·언제·무엇을 바꿨는지 기록이 안 남고, 사람마다 손에 든 매니페스트 버전이 달라진다.
- **명령형(imperative) 운영**: `kubectl scale`, `kubectl edit`, `kubectl set image` 같은 **즉석 명령**으로 클러스터를 직접 주무른다. 이 변경은 **어떤 파일에도 기록되지 않으므로** 재현·추적이 불가능하다.
- **push형 CI/CD 파이프라인**: CI 서버(예: 빌드 도구)가 클러스터에 **직접 접속해 배포를 밀어넣는다(push)**. 이 경우 외부 CI 시스템이 클러스터의 **관리자 자격증명(kubeconfig)** 을 들고 있어야 한다.

이런 방식에서 **세 가지 핵심 고통**이 발생한다.

| 고통 | 내용 | GitOps의 해결 |
|------|------|---------------|
| **드리프트(drift)** | 실제 클러스터가 의도와 어긋남(누군가 손으로 replica를 늘림, 핫픽스를 직접 적용 등). 의도를 적은 곳이 없으니 "정상 상태"가 뭔지 아무도 모름 | Git이 유일한 기준 → 어긋나면 **자동 탐지·교정** |
| **감사(audit) 난해** | "이 변경 누가 했지?"에 답할 수 없음. 변경 이력이 사람의 셸 히스토리에 흩어짐 | 모든 변경 = **Git 커밋**(작성자·시각·리뷰·PR 승인 기록) |
| **롤백(rollback) 난해** | 이전 상태로 되돌리려면 "직전에 뭐였는지"를 알아야 하는데 기록이 없음 | 이전 커밋으로 **`git revert`** 하면 끝 |

★ 면접 포인트: "GitOps가 왜 필요하냐"는 질문에는 **드리프트·감사·롤백** 세 키워드로 답하면 깔끔하다. "수동 kubectl/push 파이프라인은 변경의 단일 기준점이 없어 추적·재현·복구가 어렵다 → GitOps는 Git을 단일 기준점으로 삼아 이를 해결한다."

## 2. GitOps의 핵심 철학 4가지

OpenGitOps 4원칙(3절)을 떠받치는 **사고방식**을 먼저 잡아두면 원칙이 자연스럽게 이해된다.

### 2.1 선언형(Declarative)

**"어떻게(how) 하라"가 아니라 "무엇(what)이 되어 있어야 한다"** 를 기술한다.

- 명령형: `kubectl scale deploy web --replicas=3` (지금 한 번 실행하는 동작)
- 선언형: 매니페스트에 `replicas: 3`이라고 **상태로 박아둔다**. 시스템이 알아서 그 상태를 **유지**한다.

쿠버네티스 자체가 선언형이라 GitOps와 궁합이 완벽하다. 매니페스트는 곧 "원하는 상태의 명세"이고, GitOps는 그 명세를 Git에 두는 것뿐이다.

### 2.2 Git = 단일 진실 소스(Single Source of Truth)

운영 환경의 "정답"은 클러스터 안이 아니라 **Git 저장소에 있다.** 클러스터는 Git을 비추는 거울일 뿐이다.

- 클러스터 상태가 궁금하면 클러스터가 아니라 **Git을 본다.**
- 환경을 통째로 날려도 **Git에서 다시 세울 수 있다**(재현성, 재해 복구).
- Git의 **버전 관리·브랜치·PR·코드 리뷰·접근 제어**를 그대로 운영에 끌어쓴다.

### 2.3 지속적 조정(Continuous Reconciliation)

에이전트가 주기적으로(또는 이벤트마다) **"원하는 상태(Git) vs 실제 상태(클러스터)"** 를 비교하는 **조정 루프(reconciliation loop)** 를 돈다. 이는 쿠버네티스 컨트롤러의 **reconcile 루프**와 같은 사상이다.

```
loop forever:
    desired = read(Git)          # 원하는 상태
    actual  = read(Cluster)      # 실제 상태
    if desired != actual:
        apply(desired)           # 차이를 메워 actual을 desired로 수렴
```

배포는 "한 번 밀어넣고 끝"이 아니라 **항상 수렴하도록 유지되는 상태**다.

### 2.4 드리프트 탐지·자동 교정(Drift Detection & Self-Healing)

조정 루프가 차이를 발견하면 그것이 곧 **드리프트**다. GitOps 도구는 이를 **탐지해 알리고**, 설정에 따라 **자동으로 Git 상태로 되돌린다(self-heal)**.

- 누군가 `kubectl edit`로 replica를 5로 바꿔도 → Git이 3이면 → **다시 3으로 교정.**
- 즉 **손으로 한 임시 변경은 살아남지 못한다.** 변경하려면 반드시 Git을 고쳐야 한다 → 모든 변경이 자연히 기록된다.

★★★ 면접 포인트: GitOps의 본질을 한 문장으로 — **"Git에 선언된 상태를, 컨트롤러가 지속적으로 클러스터에 조정(reconcile)해 드리프트를 자동 교정하는 운영 모델."** 이 한 문장에 4가지 철학이 다 들어있다.

## 3. OpenGitOps 4원칙 (표준 정의)

OpenGitOps(CNCF)는 GitOps를 다음 **4가지 원칙**으로 정의한다. 면접에서 "GitOps 원칙을 아느냐"고 물으면 이 4개를 정확히 대는 것이 좋다.

| # | 원칙 | 핵심 |
|---|------|------|
| 1 | **Declarative (선언형)** | 시스템이 관리하는 전체 상태를 **선언적으로 표현** |
| 2 | **Versioned and Immutable (버전 관리·불변)** | 원하는 상태를 **불변·버전 관리되는 저장소**에 저장 |
| 3 | **Pulled Automatically (자동으로 가져옴)** | 소프트웨어 에이전트가 원하는 상태를 **자동으로 가져옴** |
| 4 | **Continuously Reconciled (지속적 조정)** | 에이전트가 실제 상태를 **지속적으로 관찰하고 원하는 상태에 맞게 조정** |

### 3.1 ① Declarative — 선언형

GitOps로 관리되는 시스템의 **원하는 상태 전체가 선언적으로 표현**되어야 한다. "이렇게 만들어라" 절차가 아니라 **"이런 상태여야 한다"** 는 사실의 집합이다. 쿠버네티스 매니페스트(YAML)가 대표 예다.

### 3.2 ② Versioned and Immutable — 버전 관리·불변

원하는 상태가 **버전이 매겨지고 불변하며 완전한 이력이 보존되는** 저장소에 저장된다. 일반적으로 **Git**이 쓰여 GitOps라 불리지만, 원칙 자체는 "버전·불변·이력"이 핵심이지 반드시 Git이어야 하는 건 아니다(다만 사실상 표준은 Git).

- **불변(immutable)**: 과거 커밋은 바뀌지 않는다 → 특정 시점 상태를 **언제든 정확히 재현**.
- **완전한 버전 이력** → 감사·롤백의 기반.

### 3.3 ③ Pulled Automatically — 자동으로 가져옴

소프트웨어 에이전트가 저장소에서 원하는 상태를 **스스로 끌어온다(pull).** 외부에서 클러스터로 **밀어넣는(push) 것이 아니다.** 이 "pull" 성질이 보안 경계(4절)의 핵심이다.

### 3.4 ④ Continuously Reconciled — 지속적 조정

에이전트가 실제 시스템 상태를 **계속 관찰**하고, 원하는 상태와 다르면 **자동으로 조정**한다. 일회성 배포가 아니라 **상시 수렴**이다(드리프트 교정 포함).

★ 면접 포인트: 4원칙을 "선언형 / 버전·불변 / 자동 pull / 지속 조정"으로 외워두자. 특히 **③ Pulled Automatically** 가 push형 CD와 GitOps를 가르는 결정적 차이다.

## 4. Pull vs Push CD — 왜 GitOps는 Pull인가

이 비교는 GitOps 면접의 **단골 핵심**이다.

### 4.1 Push형 CD

CI/CD 파이프라인(외부 서버)이 빌드 후 **클러스터에 직접 접속해 배포를 밀어넣는다.**

```
[CI 서버] --(kubeconfig로 직접 접속)--> [클러스터에 kubectl apply / helm upgrade]
```

- 배포 주체가 **클러스터 바깥**에 있다.
- 따라서 외부 CI 서버가 **클러스터 자격증명(관리자 kubeconfig)** 을 보관해야 한다.

### 4.2 Pull형 CD (GitOps)

**클러스터 안에 사는 에이전트**가 Git을 감시하다가 변경을 **스스로 끌어와(pull)** 적용한다.

```
[개발자] --push--> [Git config repo] <--watch/pull-- [클러스터 내부 에이전트] --apply--> [클러스터]
```

- 배포 주체가 **클러스터 안**에 있다.
- 외부에 클러스터 자격증명을 줄 필요가 없다. 에이전트는 **클러스터 내부 권한**으로 동작한다.

### 4.3 비교 표

| 항목 | Push형 CD | Pull형 CD (GitOps) |
|------|-----------|---------------------|
| 배포를 실행하는 주체 | 외부 CI/CD 서버 | **클러스터 내부 에이전트** |
| 클러스터 자격증명 위치 | **외부 CI에 보관**(유출 시 클러스터 장악) | 클러스터 내부에만 존재(외부 노출 X) |
| 보안 경계 방향 | 외부→내부로 **들어옴**(인바운드 연결 필요) | 내부→외부로 **나감만**(아웃바운드 pull) |
| 드리프트 교정 | 보통 안 함(밀어넣고 끝) | **지속 조정으로 자동 교정** |
| 단일 진실 소스 | 파이프라인 실행 결과(휘발적) | **Git** |
| 클러스터 추가 시 | 외부에 자격증명 N개 분배·관리 | 각 클러스터가 알아서 pull(확장 용이) |

### 4.4 왜 Pull이 우세한가 (보안 관점)

- **자격증명이 클러스터를 떠나지 않는다**: push형은 CI 서버가 뚫리면 클러스터 관리자 권한이 통째로 샌다. pull형은 자격증명이 클러스터 내부에만 있어 **공격 표면이 작다.**
- **방화벽 친화적**: 클러스터가 **외부로 나가는(egress) 연결만** 열면 된다. 외부에서 클러스터로 들어오는 인바운드 포트를 열 필요가 없다 → 비공개(private) 클러스터에 유리.
- **최소 권한**: 에이전트는 자기 클러스터 안에서 필요한 만큼의 권한만 가지면 된다.

★★★ 면접 포인트: "GitOps가 왜 보안상 유리한가?" → **"pull 모델이라 클러스터 자격증명을 외부 CI에 노출하지 않고, 인바운드 연결 없이 아웃바운드 pull만으로 동작하기 때문"** 이라고 답하면 핵심을 짚은 것이다.

## 5. CI와 CD의 책임 분리

GitOps의 또 다른 핵심은 **CI(지속적 통합)와 CD(지속적 배포)를 깨끗이 분리**한다는 점이다.

| 단계 | 책임 | 일반적 위치 |
|------|------|-------------|
| **CI** | 소스 빌드, 테스트, **컨테이너 이미지 생성·레지스트리 push** | CI 서버(예: 빌드 자동화 도구) |
| **CD** | **Git의 배포 매니페스트 변경을 감지해 클러스터에 조정** | 클러스터 내부 GitOps 에이전트 |

흐름:

```
1. 개발자가 앱 코드 push
2. CI가 빌드·테스트 → 컨테이너 이미지 만들어 레지스트리에 push (예: GHCR)
3. CI(또는 자동화)가 "배포 설정 저장소(config repo)"의 이미지 태그를 새 버전으로 커밋
4. CD 에이전트가 config repo 변경을 pull 감지 → 클러스터에 조정(reconcile)
```

이렇게 나누면:

- **CI는 "이미지를 만드는 것"까지만** 책임진다. 클러스터에 손대지 않으므로 클러스터 자격증명이 필요 없다.
- **CD는 "Git에 적힌 상태로 클러스터를 맞추는 것"만** 책임진다.
- 둘의 접점은 **Git(config repo) 하나**다. CI는 Git에 "원하는 상태"를 쓰고, CD는 그걸 읽어 적용한다.

★ 면접 포인트: "CI/CD를 GitOps에서 어떻게 나누나?" → **"CI는 이미지 빌드·push까지, CD는 Git 매니페스트를 클러스터에 조정까지. 둘의 유일한 인터페이스는 Git 저장소다."**

## 6. GitOps의 장점

- **재현성·재해 복구**: 클러스터가 통째로 날아가도 Git에서 복원. 환경을 코드로 다시 세운다.
- **감사·규정 준수**: 모든 변경이 커밋·PR로 남아 **누가·언제·왜** 가 추적된다. 승인 워크플로(PR 리뷰)를 운영에 강제.
- **쉬운 롤백**: 문제가 생기면 `git revert`로 직전 커밋으로 되돌리면 에이전트가 알아서 조정.
- **드리프트 방지**: 손으로 한 변경이 자동 교정되어 환경이 의도에서 벗어나지 않는다.
- **개발자 경험**: 개발자는 익숙한 **Git 워크플로(PR/머지)** 로 배포한다. 클러스터 접근 권한을 일일이 줄 필요가 없다.
- **다중 클러스터 확장**: 클러스터마다 에이전트가 알아서 pull → 수십 개 클러스터로도 확장 쉬움.

## 7. GitOps의 한계·주의점

GitOps가 만능은 아니다. 면접에서 한계를 물으면 다음을 짚으면 좋다.

### 7.1 시크릿(secret) 관리

**평문 시크릿을 Git에 그대로 두면 절대 안 된다.** Git은 이력이 영구 보존되므로, 한 번 커밋된 비밀번호는 사실상 영원히 남는다. GitOps에서 시크릿은 별도 기법이 필요하다(개념만):

- **암호화 후 커밋**: 시크릿을 **암호화한 형태**로 Git에 넣고, 클러스터 안에서만 복호화하는 방식(예: 봉인된 시크릿 형태, 파일 암호화 도구).
- **외부 시크릿 저장소 참조**: 실제 값은 외부 비밀 저장소(예: Vault 류)에 두고, Git에는 **"어디서 가져오라"는 참조만** 선언. 오퍼레이터가 런타임에 동기화.

핵심 원칙: **민감 정보의 평문은 Git에 들어가지 않는다.**

### 7.2 선언형으로 표현하기 어려운 작업

GitOps는 "상태를 선언"하는 모델이라, **절차적·일회성·순서 의존 작업**에는 잘 안 맞는다.

- 일회성 데이터 마이그레이션, 복잡한 배포 오케스트레이션, 외부 시스템 호출 등은 순수 선언형으로 표현이 어렵다.
- 이런 부분은 별도 훅(hook)·잡(Job)·외부 도구로 보완해야 한다.

### 7.3 그 외 운영 부담

- **저장소 구조 설계**가 필요하다(앱/설정 분리, 환경 분리 등). 설계가 나쁘면 오히려 복잡해진다.
- **이미지 태그 자동 갱신** 같은 "코드→Git 반영" 자동화를 별도로 구축해야 한다.
- 에이전트 자체의 운영(가용성·접근 제어)도 관리 대상이 된다.

★ 면접 포인트: GitOps의 한계로는 **① 시크릿(평문 금지·별도 도구 필요), ② 비선언적/일회성 작업의 어려움** 두 가지를 꼭 언급할 수 있어야 한다.

---

### 한 줄 요약

GitOps는 **원하는 상태를 Git에 선언형으로 두고(단일 진실 소스), 클러스터 내부 에이전트가 그것을 자동으로 pull해 지속적으로 조정·드리프트 교정**하는 운영 모델이다. OpenGitOps 4원칙(**선언형 / 버전·불변 / 자동 pull / 지속 조정**)이 표준이며, **pull 모델**이라 클러스터 자격증명을 외부에 노출하지 않아 push형 CD보다 보안·감사·롤백에서 우위에 있다. 단, **시크릿(평문 금지)** 과 **비선언적 작업** 은 한계로 남는다.
