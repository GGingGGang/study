# 실전 면접 예상질문 (Kubernetes Interview Q&A)

> 쿠버네티스 · 실전·취준 · 학습내용: 주니어(3년차) 백엔드/DevOps 면접에서 자주 나오는 쿠버네티스 질문을 카테고리별로 모아 핵심 키워드 중심의 모범답안으로 정리 — ① 아키텍처/컨트롤플레인 ② 워크로드 ③ 네트워킹·Service ④ 스토리지 ⑤ 스케줄링 ⑥ 보안 ⑦ 오토스케일 ⑧ 서비스 메시 ⑨ GitOps/CI·CD. 각 질문에 ★ 핵심답을 먼저 제시

---

## 1. 아키텍처 / 컨트롤 플레인

### Q1. 쿠버네티스 구조를 컨트롤 플레인과 워커 노드로 나눠 설명하라 ★★★
**★ 핵심답:** 컨트롤 플레인이 "원하는 상태"를 저장·결정하고, 워커 노드가 그걸 실제로 실행한다. 핵심은 **선언형 + 조정 루프(reconciliation loop)** 다.

- **컨트롤 플레인**
  - **kube-apiserver**: 모든 요청의 단일 진입점(REST). 인증·인가·어드미션을 거쳐 etcd에 저장. 컴포넌트끼리도 apiserver를 통해서만 소통.
  - **etcd**: 클러스터의 모든 상태를 담는 **분산 KV 저장소(단일 진실 소스)**.
  - **kube-scheduler**: 갈 곳이 정해지지 않은 파드를 보고 **어느 노드에 둘지** 결정(필터링→스코어링).
  - **kube-controller-manager**: Deployment·ReplicaSet·Node 등 각종 컨트롤러가 **현재 상태를 원하는 상태로 끌고 가는** 루프를 돌림.
  - **cloud-controller-manager**: 클라우드(OKE 등)의 LB·노드·라우트 연동.
- **워커 노드**
  - **kubelet**: 노드 에이전트. apiserver가 준 파드 스펙대로 컨테이너를 띄우고 상태를 보고.
  - **컨테이너 런타임(containerd)**: CRI로 kubelet과 통신해 실제 컨테이너 실행.
  - **kube-proxy**: Service의 가상 IP를 실제 파드로 라우팅(iptables/IPVS 규칙).

### Q2. "선언형(declarative)"이 무슨 뜻인가 ★★★
**★ 핵심답:** "어떻게(how)"가 아니라 **"원하는 최종 상태(what)"** 를 YAML로 선언하면, 컨트롤러가 현재 상태와 비교해 차이를 메운다. `apply`가 멱등한 이유.

명령형(`kubectl run`/`create`)은 "이 동작을 하라"고 지시하고, 선언형(`apply -f`)은 "이 상태가 되게 하라"고 선언한다. 자가 치유·드리프트 교정·GitOps가 모두 이 위에서 동작한다.

### Q3. etcd가 죽으면 어떻게 되나 ★★
**★ 핵심답:** **새 변경(쓰기)이 불가**해지고 컨트롤 플레인이 마비된다. 단, 이미 떠 있는 파드는 kubelet이 계속 돌려서 당장 워크로드가 다 죽지는 않는다. 그래서 etcd는 **홀수 노드로 쿼럼을 갖춰 HA 구성하고 정기 백업**한다.

### Q4. 파드(Pod)란 무엇이며 왜 컨테이너가 아니라 파드 단위인가 ★★
**★ 핵심답:** 파드는 **배포·스케줄의 최소 단위**로, 같은 네트워크 네임스페이스(IP)와 볼륨을 공유하는 1개 이상 컨테이너의 묶음이다. 메인 컨테이너 + 보조(사이드카·init) 컨테이너를 한 생명주기로 묶기 위함이다.

## 2. 워크로드 (Deployment / StatefulSet / 롤링)

### Q5. Deployment, ReplicaSet, Pod의 관계 ★★★
**★ 핵심답:** **Deployment → ReplicaSet → Pod** 계층. Deployment가 버전·롤아웃 전략을 관리하고, 각 버전마다 ReplicaSet을 만들며, ReplicaSet이 정해진 수의 Pod를 유지한다. 롤백은 **이전 ReplicaSet으로 되돌리는 것**.

### Q6. 롤링 업데이트는 어떻게 동작하나. maxSurge / maxUnavailable은? ★★★
**★ 핵심답:** 새 ReplicaSet의 파드를 조금씩 늘리고 옛 파드를 조금씩 줄이며 **무중단 교체**한다.
- **maxSurge**: 원하는 수보다 **추가로 더 띄울 수 있는** 파드 수(여유분).
- **maxUnavailable**: 업데이트 중 **동시에 내려가도 되는** 파드 수.
- 둘로 교체 속도와 가용성의 균형을 맞춘다. 문제 생기면 `kubectl rollout undo`로 직전 리비전 복귀.

### Q7. Deployment와 StatefulSet의 차이 ★★★
**★ 핵심답:** 상태가 없는 워크로드는 Deployment, **안정적 식별자·순서·전용 스토리지가 필요한 상태 저장(DB 등)** 은 StatefulSet.

| 구분 | Deployment | StatefulSet |
|------|------------|-------------|
| 파드 이름 | 랜덤 해시 | **순서 있는 고정 이름**(`-0`, `-1`...) |
| 기동/종료 순서 | 무순서 | **순차적(0→1→2)** |
| 스토리지 | 보통 공유/무상태 | **파드별 전용 PVC**(volumeClaimTemplates) |
| 네트워크 | Service ClusterIP | **헤드리스 Service로 안정적 DNS** |
| 용도 | 웹/API 등 무상태 | DB, Kafka, 분산 시스템 |

### Q8. DaemonSet / Job / CronJob은 언제 쓰나 ★★
**★ 핵심답:** **DaemonSet**=모든(또는 일부) 노드에 1개씩(로그 수집기·CNI·노드 익스포터). **Job**=완료가 목적인 일회성 작업(배치). **CronJob**=스케줄로 Job 실행(정기 작업).

### Q9. 컨테이너가 종료될 때 트래픽을 끊김 없이 빼려면? ★★
**★ 핵심답:** **preStop 훅 + terminationGracePeriod + readiness**. 종료 신호가 오면 readiness를 떨궈 엔드포인트에서 빠지게 하고, preStop으로 진행 중 요청을 마무리한 뒤 SIGTERM→유예시간→SIGKILL 순으로 정리한다.

## 3. 네트워킹 / Service (kube-proxy / Ingress vs Gateway)

### Q10. Service의 타입을 설명하라 ★★★
**★ 핵심답:** 파드는 죽고 살며 IP가 바뀌므로, **안정적 가상 IP/DNS로 파드 그룹을 묶는 추상화**가 Service다.

| 타입 | 설명 |
|------|------|
| **ClusterIP** | 클러스터 내부 전용 가상 IP(기본). 내부 통신 |
| **NodePort** | 각 노드의 포트로 외부 노출(30000~32767) |
| **LoadBalancer** | 클라우드 LB 프로비저닝(OKE면 OCI LB) |
| **ExternalName** | 외부 도메인으로 CNAME 매핑 |
| **Headless**(ClusterIP: None) | VIP 없이 파드 IP를 직접 DNS로 — StatefulSet용 |

### Q11. Service가 어떻게 파드를 찾고 부하를 분산하나 ★★★
**★ 핵심답:** Service의 **셀렉터**와 일치하는 **Ready 파드들의 IP가 EndpointSlice**에 등록되고, **kube-proxy가 노드에 iptables/IPVS 규칙**을 깔아 ClusterIP로 온 트래픽을 그 파드들로 분산한다. 연결이 안 되면 EndpointSlice가 비었는지부터 본다.

### Q12. kube-proxy의 역할과 모드 ★★
**★ 핵심답:** 각 노드에서 **Service VIP → 실제 파드 IP** 라우팅 규칙을 관리. **iptables 모드**(랜덤 분산)와 **IPVS 모드**(대규모에서 성능·알고리즘 우위)가 있다. 패킷을 직접 프록시하기보다 커널 규칙을 설치하는 방식.

### Q13. CNI가 뭐고 어떤 걸 쓰나 ★★
**★ 핵심답:** 파드 네트워킹(파드 IP 할당·노드 간 통신)을 담당하는 플러그인 규격. **Flannel**(단순한 오버레이, VXLAN), Calico(네트워크 폴리시·BGP) 등이 있다. "모든 파드는 NAT 없이 서로 통신 가능"이라는 쿠버네티스 네트워크 모델을 CNI가 구현한다.

### Q14. Ingress vs Gateway API ★★★
**★ 핵심답:** 둘 다 L7 외부 진입을 다루지만, **Gateway API가 Ingress의 한계(어노테이션 남발, 역할 분리 부재)를 개선한 차세대 표준**이다.

| 구분 | Ingress | Gateway API |
|------|---------|-------------|
| 표현력 | 제한적, 벤더별 **어노테이션 의존** | 풍부(헤더·트래픽 분할 등) **표준 필드** |
| 프로토콜 | 주로 HTTP/HTTPS | HTTP/TCP/TLS/gRPC 등 |
| 역할 분리 | 약함 | **GatewayClass(인프라)/Gateway(운영)/HTTPRoute(개발) 로 RBAC 분리** |
| 이식성 | 컨트롤러마다 다름 | 표준 CRD로 이식성↑ |

Gateway API는 **GatewayClass(누가 구현하나) → Gateway(리스너·포트·TLS) → HTTPRoute(라우팅 규칙)** 로 책임이 나뉜다. 플랫폼 팀은 Gateway를, 개발 팀은 자기 네임스페이스의 HTTPRoute만 관리하는 식.

### Q15. 클러스터 내부 DNS는 어떻게 되나 ★★
**★ 핵심답:** **CoreDNS**가 `<svc>.<ns>.svc.cluster.local` 형식으로 서비스 이름을 ClusterIP로 해석한다. 같은 네임스페이스면 짧은 이름, 다르면 `<svc>.<ns>`.

## 4. 스토리지 (PV / PVC / CSI)

### Q16. PV와 PVC의 관계 ★★★
**★ 핵심답:** **PV**(PersistentVolume)는 관리자/프로비저너가 제공하는 **실제 스토리지 자원**, **PVC**(PersistentVolumeClaim)는 사용자(파드)가 내는 **요청서**다. PVC가 조건(용량·접근모드)에 맞는 PV에 **바인딩**되고, 파드는 PVC만 참조한다 — 스토리지 구현을 몰라도 되게 분리한 것.

### Q17. StorageClass와 동적 프로비저닝 ★★★
**★ 핵심답:** 미리 PV를 안 만들어두고, PVC가 오면 **StorageClass에 지정된 프로비저너(CSI 드라이버)가 자동으로 PV를 생성**한다(동적 프로비저닝). OKE면 OCI Block Volume CSI(`oci-bv`) 등이 프로비저너 역할.

### Q18. accessMode와 reclaimPolicy ★★
**★ 핵심답:**
- **accessMode**: `ReadWriteOnce`(한 노드 RW, 블록스토리지 보통), `ReadOnlyMany`, `ReadWriteMany`(여러 노드 RW, 파일스토리지), `ReadWriteOncePod`(한 파드만).
- **reclaimPolicy**: PVC 삭제 시 PV 처리 — `Retain`(보존, 수동 정리), `Delete`(같이 삭제). **데이터 보호가 중요하면 Retain**.

### Q19. CSI가 뭔가 ★
**★ 핵심답:** Container Storage Interface — **스토리지 벤더가 쿠버네티스 코드 수정 없이 드라이버를 붙이는 표준 인터페이스**. 클라우드 블록/파일 스토리지가 이 표준으로 연동된다.

### Q20. WaitForFirstConsumer 바인딩 모드 ★
**★ 핵심답:** StorageClass의 `volumeBindingMode: WaitForFirstConsumer`는 **파드가 스케줄될 때까지 PV 생성·바인딩을 미룬다.** 파드가 갈 노드의 가용 영역에 맞춰 볼륨을 만들기 위함. 그래서 PVC가 한동안 Pending인 건 정상일 수 있다.

## 5. 스케줄링 (affinity / taint)

### Q21. 파드가 노드에 배치되는 과정 ★★
**★ 핵심답:** 스케줄러가 **필터링(Filtering: 자원·셀렉터·taint 등으로 후보 노드 추림) → 스코어링(Scoring: 남은 후보에 점수)** 두 단계로 최적 노드를 고른다. requests를 기준으로 자원 적합성을 본다(limits는 런타임 상한).

### Q22. nodeSelector / nodeAffinity / podAffinity 차이 ★★
**★ 핵심답:**
- **nodeSelector**: 가장 단순. 라벨 같으면 그 노드에.
- **nodeAffinity**: 더 표현력 있는 노드 선택(`required`=필수, `preferred`=선호).
- **podAffinity/antiAffinity**: 다른 **파드와 같이/떨어뜨려** 배치(예: 레플리카를 서로 다른 노드/존에 분산 → antiAffinity).

### Q23. taint와 toleration ★★★
**★ 핵심답:** **taint는 노드가 "나는 아무 파드나 안 받는다"고 거는 거부 표식**, **toleration은 파드가 "그 taint를 견딜 수 있다"는 허가증**이다. 둘이 맞아야 그 노드에 뜬다. GPU 노드·전용 노드풀 격리에 쓴다. (taint effect: `NoSchedule`, `PreferNoSchedule`, `NoExecute`.)

### Q24. requests와 limits ★★★
**★ 핵심답:** **requests=스케줄링 보장 최소치(노드 자원 예약 기준)**, **limits=런타임 상한(넘으면 CPU는 throttle, 메모리는 OOMKill)**. requests와 limits를 같게 두면 QoS가 **Guaranteed**가 되어 축출 우선순위에서 가장 안전하다.

## 6. 보안 (RBAC / PSA / 시크릿)

### Q25. RBAC을 구성요소로 설명하라 ★★★
**★ 핵심답:** **누가(Subject) — 무엇을(Role) — 연결(Binding)**.
- **Role/ClusterRole**: 권한 집합(verb+resource). Role은 네임스페이스 한정, ClusterRole은 클러스터 전역.
- **RoleBinding/ClusterRoleBinding**: 그 Role을 **사용자/그룹/ServiceAccount에 연결**.
- 디버깅은 `kubectl auth can-i <verb> <resource> --as=<subject>`. 원칙은 **최소 권한**.

### Q26. ServiceAccount란 ★★
**★ 핵심답:** **파드(워크로드)가 apiserver에 인증할 때 쓰는 신원**이다. 사람은 User, 워크로드는 ServiceAccount. 토큰이 파드에 마운트되어 클러스터 API 호출 권한을 RBAC로 제어한다.

### Q27. Secret은 정말 안전한가 ★★★
**★ 핵심답:** 기본 Secret은 **암호화가 아니라 base64 인코딩**일 뿐이라 etcd에 평문에 가깝게 저장된다. 그래서 **etcd 저장 암호화(encryption at rest)**, **RBAC로 접근 제한**, 그리고 외부 시크릿 매니저(예: OpenBao/Vault) + External Secrets로 끌어오는 패턴을 쓴다. Git에는 평문 시크릿을 절대 올리지 않는다(SealedSecrets/SOPS 등으로 암호화).

### Q28. Pod Security Admission(PSA)이 뭔가 ★★
**★ 핵심답:** PodSecurityPolicy(폐기됨)를 대체하는 내장 어드미션으로, **네임스페이스 단위로 Pod Security Standards(privileged / baseline / restricted)** 를 강제한다. 모드는 `enforce`(차단)/`audit`/`warn`. restricted는 루트 금지·권한 상승 금지 등.

### Q29. NetworkPolicy ★★
**★ 핵심답:** **파드 간 트래픽을 라벨 기반으로 허용/차단**하는 L3/L4 방화벽. 기본은 모두 허용이지만, 한 번 정책이 걸리면 명시된 것 외엔 차단(deny by default 효과). 단, **CNI가 지원해야** 동작한다(Flannel 단독은 미지원, Calico 등 필요).

## 7. 오토스케일 (HPA)

### Q30. HPA는 어떻게 동작하나 ★★★
**★ 핵심답:** **HorizontalPodAutoscaler**는 metrics-server가 주는 CPU/메모리(또는 커스텀 메트릭)를 보고 **레플리카 수를 자동 조절**한다. 공식: 원하는 레플리카 = 현재 레플리카 × (현재 메트릭 / 목표 메트릭). 목표 CPU 50%인데 현재 100%면 2배로 스케일아웃.

### Q31. HPA / VPA / Cluster Autoscaler 차이 ★★
**★ 핵심답:**
- **HPA**: 파드 **개수**를 늘리고 줄임(수평).
- **VPA**: 파드의 **requests/limits**를 조절(수직).
- **Cluster Autoscaler**: 파드를 둘 **노드가 부족하면 노드를 추가**(OKE 노드풀 확장). HPA가 파드를 늘렸는데 자리가 없으면 CA가 노드를 늘리는 식으로 함께 동작.

### Q32. HPA가 동작하려면 전제조건은? ★★
**★ 핵심답:** **파드에 resources.requests가 설정**돼 있어야 하고(퍼센트 계산 기준), **metrics-server**가 클러스터에 있어야 한다. requests가 없으면 CPU 기반 HPA가 동작하지 않는다.

## 8. 서비스 메시 (사이드카 vs ambient / mTLS)

### Q33. 서비스 메시가 뭐고 왜 쓰나 ★★★
**★ 핵심답:** 서비스 간 통신을 **애플리케이션 코드 변경 없이** 다루는 인프라 계층. **mTLS 암호화, 트래픽 관리(카나리·재시도·타임아웃), 관측성(메트릭·트레이스)** 을 코드 밖에서 일괄 제공한다. 대표 구현이 Istio.

### Q34. 사이드카 모드 vs Ambient 모드 ★★★
**★ 핵심답:** 기존 Istio는 **파드마다 Envoy 사이드카를 주입**했는데, Ambient는 그걸 없애 **노드 단위 ztunnel(L4) + 필요 시 waypoint(L7)** 로 분리한 새 데이터플레인이다.

| 구분 | 사이드카 | Ambient |
|------|----------|---------|
| 프록시 위치 | **파드마다 Envoy** | **노드의 ztunnel**(L4) + 선택적 waypoint(L7) |
| 자원 오버헤드 | 파드 수만큼 ↑ | 낮음(프록시 수 적음) |
| 주입·재시작 | 사이드카 주입 위해 파드 재시작 필요 | 앱 파드 손 안 댐 |
| L7 기능 | 항상 가능 | **waypoint 배치 시** 가능 |
| mTLS | 사이드카가 처리 | ztunnel이 L4 mTLS 처리 |

**핵심 트레이드오프:** Ambient는 오버헤드와 운영 부담(사이드카 주입·재시작)을 줄이는 대신, L7 기능은 waypoint를 둬야 한다. 무거운 사이드카가 부담이거나 점진 도입을 원하면 Ambient가 유리.

### Q35. mTLS를 메시가 어떻게 자동으로 거나 ★★
**★ 핵심답:** 컨트롤 플레인(istiod)이 각 워크로드에 **SPIFFE 신원 기반 인증서를 발급·교체**하고, 데이터플레인(사이드카 또는 ztunnel)이 그 인증서로 **서로 양방향 TLS**를 맺는다. 앱은 평문으로 통신하지만 메시가 구간을 암호화한다. `PeerAuthentication`으로 STRICT mTLS 강제 가능.

### Q36. 서비스 메시로 카나리 배포를 어떻게 하나 ★★
**★ 핵심답:** 라우팅 규칙(트래픽 가중치)로 **새 버전에 트래픽을 10% → 50% → 100% 점진 전환**한다. 코드/Service 변경 없이 비율만 조정해 안전하게 릴리스하고, 문제 시 가중치를 0으로 되돌린다.

## 9. GitOps / CI·CD

### Q37. GitOps가 뭔가. 핵심 원칙은? ★★★
**★ 핵심답:** **Git을 시스템 상태의 단일 진실 소스로 삼고, 선언형으로 기술된 원하는 상태를 에이전트가 클러스터에 지속적으로 동기화·교정**하는 운영 방식. 4원칙: ① **선언형** ② **버전관리·불변(Git)** ③ **자동 적용(pull)** ④ **지속 조정(드리프트 감지·교정)**.

### Q38. push 배포와 pull 배포(GitOps)의 차이 ★★★
**★ 핵심답:** 전통 CI는 외부에서 클러스터로 **밀어넣는다(push)** — CI가 클러스터 자격증명을 들고 있어야 한다. GitOps는 클러스터 안 에이전트(ArgoCD)가 Git을 **끌어와(pull)** 적용 — **클러스터 크리덴셜을 외부 CI에 노출하지 않아** 더 안전하고, Git 이력이 곧 배포 이력이라 롤백이 `git revert`다.

### Q39. ArgoCD의 핵심 개념 ★★★
**★ 핵심답:** **Application** 리소스가 "어느 Git 경로(원하는 상태) → 어느 클러스터/네임스페이스"를 정의하고, ArgoCD가 둘을 비교해 **Synced/OutOfSync**, **Healthy/Degraded** 상태를 보여준다. **auto-sync + self-heal + prune**을 켜면 드리프트를 자동 교정하고 Git에서 지운 리소스를 정리한다.

### Q40. 이미지 빌드부터 배포까지 파이프라인을 설명하라 ★★★
**★ 핵심답:** **CI는 빌드/테스트/이미지 푸시까지, CD(배포)는 GitOps가** 담당하도록 분리한다.
1. 코드 push → CI(예: GitHub Actions)가 빌드·테스트.
2. 컨테이너 이미지를 **GHCR**(ghcr.io)에 푸시(태그는 커밋 SHA 등 고정값).
3. CI가 **배포용 Git 매니페스트의 이미지 태그를 새 값으로 커밋**(또는 PR).
4. **ArgoCD가 그 변경을 감지해 클러스터에 동기화** → 롤링 업데이트.
5. 문제 시 Git revert로 즉시 롤백.

**`kubectl set image` 같은 수동 배포는 GitOps와 충돌**(OutOfSync로 되돌려짐)하므로, 운영 변경은 항상 Git을 거친다.

### Q41. CI에서 클러스터로 이미지를 어떻게 인증하나 (GHCR) ★★
**★ 핵심답:** 프라이빗 GHCR 이미지는 **`docker-registry` 타입 Secret(imagePullSecret)** 을 만들어 ServiceAccount나 파드 spec에 연결해야 kubelet이 풀할 수 있다. 자격은 `read:packages` 권한의 PAT 또는 GitHub Actions 토큰.

### 한 줄 요약
면접의 뼈대는 **선언형 + 조정 루프**라는 한 문장으로 수렴한다 — apiserver/etcd/scheduler/controller가 원하는 상태를 지키고(아키텍처), Deployment·StatefulSet으로 워크로드를 굴리며(워크로드), Service·EndpointSlice·Gateway로 트래픽을, PV/PVC/CSI로 스토리지를, affinity·taint로 배치를, RBAC·PSA·Secret으로 보안을, HPA로 탄력성을, 메시(사이드카/ambient·mTLS)로 통신을, 그리고 GitOps(ArgoCD·GHCR)로 그 모든 선언을 Git에서 클러스터로 동기화한다. **"왜 그렇게 하나"의 트레이드오프를 키워드와 함께 말하는 것**이 합격선이다.
