# 실전 트러블슈팅 플레이북 (Troubleshooting Playbook)

> 쿠버네티스 · 실전·취준 · 학습내용: 현업에서 마주치는 증상별로 [증상 → 진단 명령 → 흔한 원인 → 해결]을 표로 정리 — Pending, CrashLoopBackOff, ImagePullBackOff/ErrImagePull, OOMKilled, Service 연결 실패, DNS 실패(CoreDNS), 인증서/HTTPS 미동작(cert-manager·Gateway), RBAC Forbidden, 프로브 실패 재시작, 노드 NotReady. 면접에서 "장애 어떻게 잡냐"에 바로 답이 되는 진단 흐름

---

## 0. 모든 장애의 공통 시작점 ★★★

증상을 만나면 **늘 같은 순서로 좁혀 들어간다.** 면접에서 "어디부터 보냐"고 물을 때 그대로 답하면 되는 흐름이다.

```bash
k get pods -o wide                # 상태(STATUS)·재시작 횟수·노드 확인
k describe pod <pod>              # 맨 아래 Events: 가 1순위 단서
k logs <pod>                      # 앱이 떴다면 앱 로그
k logs --previous <pod>          # 죽었다 살아나는 중이면 직전 로그
k get events --sort-by=.lastTimestamp -A   # 시간순 전체 이벤트
```

원칙은 **STATUS 확인 → describe의 Events → logs** 순이다. STATUS만 봐도 어느 단계에서 막혔는지(스케줄 전인지, 이미지 단계인지, 실행 후인지) 드러난다.

## 1. Pending (스케줄이 안 됨) ★★★

스케줄러가 파드를 올릴 노드를 못 찾은 상태로, **컨테이너 시작 이전 단계**다.

진단:
```bash
k describe pod <pod>          # Events의 "FailedScheduling" 메시지가 핵심
k get nodes -o wide
k top nodes                   # 자원 여유 확인
k describe node <node> | grep -A8 Allocated
```

| 흔한 원인 | Events에 보이는 단서 | 해결 |
|-----------|----------------------|------|
| **자원 부족** (CPU/메모리) | `Insufficient cpu/memory` | requests 낮추거나 노드 추가/스케일아웃, HPA/노드풀 확장 |
| **nodeSelector/affinity 불일치** | `node(s) didn't match node selector/affinity` | 라벨 확인 `k get nodes --show-labels`, 셀렉터 수정 |
| **taint 때문에 거부** | `node(s) had untolerated taint` | 파드에 toleration 추가하거나 노드 taint 제거 |
| **PVC가 Pending** | 파드 Events에 volume 관련, `k get pvc` 가 Pending | StorageClass 존재·이름 확인, OKE는 oci-bv 등 CSI 프로비저너 확인 |
| **포트/호스트 제약** | `didn't have free ports` | hostPort 충돌 제거 |

**OKE 같은 매니지드에서 자원이 부족하면 노드풀을 스케일하거나** cluster-autoscaler가 켜져 있는지 확인한다. **PVC Pending은 StorageClass의 `volumeBindingMode: WaitForFirstConsumer`** 때문에 파드가 스케줄될 때까지 일부러 기다리는 정상 동작일 수도 있으니, 둘을 같이 봐야 한다.

## 2. CrashLoopBackOff (떴다가 계속 죽음) ★★★

컨테이너가 시작은 되는데 곧 **종료되고 재시작을 반복**하면서 backoff 간격이 점점 길어진다. 이미지나 스케줄 문제가 아니라 **앱 자체나 설정 문제**다.

진단:
```bash
k logs --previous <pod>            # ★ 직전에 죽은 컨테이너 로그 = 진짜 에러
k describe pod <pod>               # Last State: Terminated, Exit Code, Reason
k logs <pod> -c <container>        # 멀티 컨테이너면 컨테이너 지정
```

| 흔한 원인 | 단서 | 해결 |
|-----------|------|------|
| **앱이 즉시 에러로 종료** | logs에 스택트레이스, Exit Code 1 | 코드/설정 버그 수정 |
| **필수 환경변수·ConfigMap 누락** | 로그에 "missing env" / nil | env·ConfigMap·Secret 마운트 확인 |
| **DB·의존 서비스 연결 실패** | "connection refused/timeout" | 의존성 기동 순서, 네트워크/Service 확인 |
| **liveness probe가 너무 빡빡** | describe에 프로브 실패로 kill | initialDelaySeconds 늘리거나 startupProbe 추가 (→ 9번) |
| **OOM으로 죽음** | Reason: OOMKilled, Exit 137 | (→ 4번) |
| **잘못된 command/entrypoint** | "exec format error", "no such file" | command/args, 아키텍처(arm64/amd64) 확인 |

핵심은 역시 **`--previous`**다. 지금 로그는 비어 있고 원인은 죽은 인스턴스에 남아 있다. **Exit Code 0이면 할 일을 끝내고 정상 종료한 것** — 오래 돌아야 할 워크로드가 아니라 잡(Job)성 컨테이너를 Deployment로 잘못 띄운 경우다.

## 3. ImagePullBackOff / ErrImagePull (이미지를 못 받음) ★★★

이미지를 레지스트리에서 가져오지 못한 상태로, **컨테이너 시작 전**에 막힌다.

진단:
```bash
k describe pod <pod>     # Events: "Failed to pull image ... <원인>"
```

| 흔한 원인 | 단서 | 해결 |
|-----------|------|------|
| **태그 오타/존재하지 않는 태그** | `manifest unknown`, `not found` | 태그 확인, `:latest` 의존 지양·고정 태그 사용 |
| **프라이빗 레지스트리 인증 실패 (GHCR)** | `unauthorized`, `denied`, `401/403` | imagePullSecret 생성·연결 (아래) |
| **레지스트리 주소 오타** | `no such host` | 이미지 경로 `ghcr.io/<org>/<repo>:<tag>` 확인 |
| **rate limit / 네트워크** | `toomanyrequests`, timeout | 미러·캐시, 노드 아웃바운드 확인 |

**GHCR 프라이빗 이미지 인증**(프로젝트 기본 패턴):
```bash
# PAT(read:packages 권한)로 docker-registry 시크릿 생성
k create secret docker-registry ghcr-cred \
  --docker-server=ghcr.io \
  --docker-username=<github-username> \
  --docker-password=<PAT> \
  -n app

# 파드/디플로이먼트 spec에 연결
#   spec.imagePullSecrets:
#   - name: ghcr-cred
# 또는 ServiceAccount에 박아두면 그 SA로 뜨는 파드 전부 적용
```
```bash
k patch serviceaccount default -n app \
  -p '{"imagePullSecrets":[{"name":"ghcr-cred"}]}'
```

**containerd 노드에 이미지가 실제로 받아졌는지** 보려면 노드에서 `crictl images`로 확인한다(kubelet은 containerd를 CRI로 쓴다).

## 4. OOMKilled (메모리 초과로 강제 종료) ★★★

컨테이너가 **메모리 limit을 넘어서 커널 OOM killer가 강제 종료**한 경우다. **Exit Code 137(128+9, SIGKILL)**.

진단:
```bash
k describe pod <pod>      # Last State: Terminated, Reason: OOMKilled
k top pod <pod> --containers
```

| 흔한 원인 | 해결 |
|-----------|------|
| limit이 실사용보다 낮음 | `resources.limits.memory` 상향 |
| 메모리 누수 | 앱 프로파일링, 힙 설정(JVM `-Xmx`를 컨테이너 limit에 맞춤) |
| requests만 있고 limit 과소 | limit을 실측 peak 기준으로 재산정 |

**JVM 같은 런타임은 컨테이너 메모리 limit을 인식하도록** 설정해줘야 한다(예: `-XX:MaxRAMPercentage`). requests와 limit을 같게 두면 QoS가 Guaranteed가 되어 가장 늦게 축출(evict)된다.

## 5. Service 연결 실패 (서비스로 트래픽이 안 감) ★★★

파드는 멀쩡한데 Service로 호출하면 닿지 않는 경우다. **셀렉터, 엔드포인트, 포트** 세 가지를 본다.

진단:
```bash
k get svc <svc> -o wide
k get endpointslices -l kubernetes.io/service-name=<svc>   # ★ 백엔드가 비었나
k get endpoints <svc>                                       # 구버전 호환 보기
k describe svc <svc>
# 클러스터 내부에서 직접 때려보기
k run tmp --rm -it --image=nicolaka/netshoot -- \
  curl -v http://<svc>.<ns>.svc.cluster.local:<port>
```

| 흔한 원인 | 단서 | 해결 |
|-----------|------|------|
| **셀렉터가 파드 라벨과 불일치** | Endpoints/EndpointSlice가 **비어 있음** | `svc.spec.selector` ↔ 파드 라벨 일치시키기 |
| **targetPort ≠ 컨테이너 포트** | 연결은 되는데 거부/timeout | `targetPort`를 컨테이너 실제 listen 포트로 |
| **파드가 Ready 아님** | Endpoint에서 빠짐 | readinessProbe·파드 상태 확인 |
| **NetworkPolicy 차단** | curl timeout | 해당 트래픽 허용 정책 추가 |
| **named port 불일치** | 매칭 안 됨 | 컨테이너 `ports.name` ↔ Service `targetPort` 이름 일치 |

**EndpointSlice가 비어 있으면 99%는 셀렉터/라벨 불일치, 아니면 readiness 미통과다.** Service는 **Ready 상태인 파드만** 엔드포인트에 넣기 때문이다. Flannel 같은 CNI 환경이라면 노드 간 통신 자체가 막혔는지(파드 IP로 직접 ping) 한 번 확인해본다.

## 6. DNS 실패 (이름 해석 안 됨, CoreDNS) ★★

서비스 이름으로는 안 되는데 ClusterIP로는 되는 경우 → **DNS 문제**.

진단:
```bash
k run tmp --rm -it --image=nicolaka/netshoot -- \
  nslookup <svc>.<ns>.svc.cluster.local

k get pods -n kube-system -l k8s-app=kube-dns       # CoreDNS 파드 상태
k logs -n kube-system -l k8s-app=kube-dns
k get svc -n kube-system kube-dns                   # ClusterIP(보통 10.x.0.10)
```

| 흔한 원인 | 해결 |
|-----------|------|
| CoreDNS 파드가 죽음/부족 | CoreDNS 파드·로그 확인, 재시작·스케일 |
| 잘못된 FQDN | `<svc>.<ns>.svc.cluster.local` 형식 확인 |
| 파드 `/etc/resolv.conf` 이상 | dnsPolicy(`ClusterFirst`) 확인 |
| 외부 도메인 해석 실패 | CoreDNS `forward` 업스트림 확인 |

**같은 네임스페이스면 짧은 이름(`<svc>`)으로, 다른 네임스페이스면 `<svc>.<ns>`** 로 닿는다. 외부 도메인(ggang.cloud 등)이 안 되면 CoreDNS의 업스트림 포워딩을 본다.

## 7. 인증서 / HTTPS 미동작 (cert-manager · Gateway API) ★★

HTTPS가 안 붙거나 브라우저가 인증서 경고를 내는 경우.

진단:
```bash
k get certificate -A                       # READY=True 여야 정상
k describe certificate <name>              # Events에 발급 실패 사유
k get certificaterequest,order,challenge -A   # ACME 발급 파이프라인 추적
k describe challenge <name>                 # HTTP-01/DNS-01 검증 실패 사유
k get gateway,httproute -A                  # Gateway/Route 상태(PROGRAMMED/Accepted)
k describe gateway <name>
```

| 흔한 원인 | 단서 | 해결 |
|-----------|------|------|
| **ACME 도메인 검증 실패** | challenge가 pending/실패 | DNS A레코드(ggang.cloud)가 LB IP를 가리키는지, HTTP-01 경로 도달성 확인 |
| **Issuer/ClusterIssuer 미설정** | certificate Events에 issuer 못 찾음 | issuerRef 이름·종류 확인 |
| **rate limit (Let's Encrypt)** | "too many certificates" | staging issuer로 먼저 테스트 후 prod 전환 |
| **Gateway listener에 cert 미연결** | Gateway가 PROGRAMMED 아님 | listener의 `tls.certificateRefs`가 생성된 Secret 가리키는지 |
| **HTTPRoute가 Gateway에 미바인딩** | route Accepted=False | `parentRefs`·allowedRoutes 네임스페이스 확인 |

**발급은 Certificate → CertificateRequest → Order → Challenge** 순으로 내려가고, 막힌 단계의 `describe`에 사유가 찍힌다. Gateway API에서는 **Gateway의 `Programmed`, HTTPRoute의 `Accepted`/`ResolvedRefs` 조건**도 같이 봐야 한다.

## 8. RBAC Forbidden (권한 거부) ★★

`Error from server (Forbidden): ... cannot <verb> resource ...`

진단:
```bash
# 누가/무엇을 할 수 있는지 정확히 확인
k auth can-i <verb> <resource> -n <ns>
k auth can-i create deployments --as=system:serviceaccount:app:builder -n app
k get rolebinding,clusterrolebinding -A | grep <subject>
k describe clusterrole <role>
```

| 흔한 원인 | 해결 |
|-----------|------|
| ServiceAccount에 권한 없음 | 필요한 Role/ClusterRole을 RoleBinding으로 연결 |
| 네임스페이스 범위 착오 | Role(네임스페이스) vs ClusterRole(클러스터) 구분 |
| 잘못된 subject 이름 | `system:serviceaccount:<ns>:<sa>` 형식 확인 |
| 과한 권한 요청 | 최소 권한으로 좁혀 부여 |

**`--as`로 특정 SA를 흉내 내 확인하는** 게 가장 빠르다. CI(예: ArgoCD나 배포 SA)가 Forbidden을 내면 그 SA에 바인딩된 Role을 들여다본다. 원칙은 늘 **최소 권한(least privilege)** 부여다.

## 9. 프로브 실패로 재시작 (probe) ★★

파드가 자꾸 재시작되는데 OOM도 크래시도 아니라면 **헬스체크(probe)** 를 의심한다.

진단:
```bash
k describe pod <pod>     # Events: "Liveness/Readiness probe failed"
```

| 프로브 | 실패 시 효과 | 흔한 원인·해결 |
|--------|--------------|----------------|
| **liveness** | 컨테이너 **재시작** | 시작이 느린데 initialDelay가 짧음 → **startupProbe** 도입, 임계값 완화 |
| **readiness** | 엔드포인트에서 **제외**(트래픽 차단, 재시작은 안 함) | 의존성 미준비, 헬스 경로/포트 오류 |
| **startup** | 시작 완료 전까지 다른 프로브 보류 | 부팅 긴 앱(JVM 등)에 추가 |

| 흔한 원인 | 해결 |
|-----------|------|
| `initialDelaySeconds` 부족 | 늘리거나 startupProbe 사용 |
| 헬스 엔드포인트/포트 오류 | path·port 실제 값과 일치 |
| `failureThreshold`·`timeoutSeconds` 빡빡 | 임계값 상향 |
| readiness가 외부 의존성에 묶임 | liveness와 책임 분리(liveness는 "내가 살아있나"만) |

핵심만 추리면 **liveness는 죽으면 재시작, readiness는 준비되면 트래픽, startup은 초기 부팅 보호다.** 부팅 느린 앱에 liveness만 빡세게 걸면 부팅 도중 계속 죽어서 CrashLoop처럼 보인다.

## 10. 노드 NotReady ★★

노드 한 대가 NotReady가 되면 그 위에 있던 파드들이 축출되고 재스케줄된다.

진단:
```bash
k get nodes
k describe node <node>          # Conditions: MemoryPressure/DiskPressure/Ready 사유
k get pods -A -o wide --field-selector spec.nodeName=<node>
# 노드 접속 가능하면
#   systemctl status kubelet ; journalctl -u kubelet
#   systemctl status containerd
```

| 흔한 원인 | 단서(Conditions) | 해결 |
|-----------|------------------|------|
| **kubelet 다운** | `Ready=Unknown`, 하트비트 끊김 | kubelet 재시작, 로그 확인 |
| **DiskPressure** | `DiskPressure=True` | 디스크 정리(이미지 GC), 볼륨 확장 |
| **MemoryPressure** | `MemoryPressure=True` | 워크로드 분산, 노드 스케일 |
| **컨테이너 런타임 문제** | containerd 비정상 | containerd 재시작 |
| **네트워크/CNI 문제** | NodeNetworkUnavailable | Flannel 등 CNI 파드 상태 확인 |

**매니지드(OKE)에서는 NotReady 노드를 직접 고치기보다 cordon/drain 후 노드를 교체하는** 게 보통이다.
```bash
k cordon <node>      # 새 파드 안 받게
k drain <node> --ignore-daemonsets --delete-emptydir-data
# 노드 교체/재시작 후
k uncordon <node>
```

---

### 한 줄 요약
트러블슈팅은 결국 **STATUS로 단계를 가르고(스케줄 전 Pending/ImagePull → 실행 후 CrashLoop/OOM/probe), `describe`의 Events와 `logs --previous`로 원인 문장을 읽어내는** 일이다. 서비스가 안 되면 **EndpointSlice가 비었는지(셀렉터·readiness)** 부터, HTTPS가 안 되면 **Certificate→Challenge 파이프라인과 Gateway 조건**을, 권한은 **`auth can-i --as`** 로 좁혀 들어간다.
