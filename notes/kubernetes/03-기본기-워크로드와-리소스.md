# 워크로드와 리소스 (Kubernetes Workloads & Resources)

> 쿠버네티스 · 기본기/코어 · 학습내용: Pod의 정의, 워크로드 컨트롤러(ReplicaSet/Deployment/StatefulSet/DaemonSet/Job/CronJob)가 각각 무엇을 보장하는가, Service 타입, 스토리지(PV/PVC/StorageClass), 설정 주입(ConfigMap/Secret)

---

이 문서는 "기본기"다. 면접에서 "이 리소스는 무엇을 보장하나?"에 한 문장으로 답할 수 있을 정도로 **역할과 보장(guarantee)** 만 빠르게 잡는다. 내부 구현(컨트롤러 watch 캐시, etcd 저장 포맷 등)은 다루지 않는다. 모든 리소스는 **선언형(YAML로 원하는 상태를 적으면 컨트롤러가 맞춰준다)** 으로 동작한다.

## 1. Pod — 배포의 최소 단위

**파드(Pod)** 는 쿠버네티스가 다루는 **가장 작은 배포 단위**다. 컨테이너 1개가 아니라 "함께 떠야 하는 컨테이너 묶음 + 공유 자원"이다.

- 같은 파드 안 컨테이너들은 **네트워크 네임스페이스(IP·포트)** 와 **스토리지 볼륨**을 공유한다. 서로 `localhost`로 통신한다.
- 파드는 **일회용(ephemeral)** 이다. 죽으면 같은 파드가 살아나는 게 아니라 **새 파드(새 IP)** 로 교체된다.
- 그래서 실무에서 파드를 직접 만들지 않는다. **컨트롤러**(Deployment 등)에게 "파드를 이렇게 N개 유지해줘"라고 맡긴다.

> ★ "파드 IP는 언제든 바뀐다"가 핵심. 파드를 직접 부르지 않고 **Service**(4절)로 부르는 이유가 여기서 나온다.

대표적인 다중 컨테이너 패턴이 **사이드카(sidecar)** 다. 메인 컨테이너 옆에 보조 컨테이너(로그 수집, 프록시 등)를 같은 파드에 띄운다.

## 2. 워크로드 컨트롤러 — 무엇을 보장하나

파드를 직접 관리하는 대신, 목적에 맞는 컨트롤러를 쓴다. 각 컨트롤러가 **무엇을 보장하는지**가 선택 기준이다.

| 컨트롤러 | 보장하는 것 | 언제 쓰나 |
|----------|-------------|-----------|
| **ReplicaSet** | 지정한 **복제본 수(replicas)** 를 항상 유지 | 보통 직접 안 씀(Deployment가 뒤에서 관리) |
| **Deployment** | 무상태(stateless) 앱의 복제본 유지 + **롤링 업데이트/롤백** | 웹 API, 프런트엔드 등 대부분의 무상태 앱 |
| **StatefulSet** | **안정적인 고유 이름·순서·전용 스토리지** | DB, 카프카 등 상태가 있는 앱 |
| **DaemonSet** | **모든(또는 일부) 노드에 파드 1개씩** | 노드 에이전트(로그/메트릭 수집, CNI 등) |
| **Job** | 작업이 **성공 완료될 때까지** 실행(완료 후 종료) | 배치 작업, 마이그레이션 |
| **CronJob** | **스케줄(cron)** 에 맞춰 Job 생성 | 정기 백업, 정기 리포트 |

> ★★★ 면접 단골: "Deployment와 StatefulSet의 차이는?" → **Deployment는 파드가 서로 구분되지 않는 무상태용**(아무 파드나 죽고 새로 떠도 무방), **StatefulSet은 파드마다 고유 ID(`web-0`, `web-1`)·고정 스토리지·순서 보장**이 필요한 상태 저장용.

### 2.1 Deployment — 롤링 업데이트 / 롤백

Deployment는 내부적으로 ReplicaSet을 만들어 복제본을 관리한다. 이미지 버전을 바꾸면 **새 ReplicaSet을 점진적으로 늘리고 옛 것을 줄이는 롤링 업데이트**를 수행한다. 문제가 생기면 이전 ReplicaSet으로 **롤백**할 수 있다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: web
          image: ghcr.io/example/web:1.2.0
          ports:
            - containerPort: 8080
```

```bash
kubectl set image deploy/web web=ghcr.io/example/web:1.3.0  # 롤링 업데이트
kubectl rollout status deploy/web                            # 진행 상황
kubectl rollout undo deploy/web                              # 롤백
```

### 2.2 나머지 컨트롤러 한 줄씩

- **StatefulSet**: 파드 이름이 `name-0, name-1 …` 로 고정. 각 파드는 자기만의 PVC를 가진다(`volumeClaimTemplates`). 생성·삭제가 순서대로 일어난다.
- **DaemonSet**: 노드가 추가되면 자동으로 그 노드에도 파드를 띄운다. 로그/메트릭 수집기, CNI 데몬 등이 이 방식으로 모든 노드에 깔린다.
- **Job / CronJob**: Job은 "끝나야 하는 일"을 보장(재시도 포함), CronJob은 그 Job을 **주기적으로** 만든다.

## 3. Service — 안정적인 접근점

파드 IP는 바뀌므로, **변하지 않는 가상 주소**로 파드 묶음을 부르게 해주는 것이 **Service** 다. Service는 **셀렉터(label selector)** 로 대상 파드를 고르고, 그 뒤로 트래픽을 분산한다.

| 타입 | 무엇을 하나 | 접근 범위 |
|------|-------------|-----------|
| **ClusterIP** (기본) | 클러스터 내부 전용 가상 IP 부여 | 클러스터 **내부**만 |
| **NodePort** | 모든 노드의 특정 포트(30000~32767)로 노출 | 노드 IP:포트로 **외부 가능**(원시적) |
| **LoadBalancer** | 클라우드 LB를 프로비저닝해 외부 노출 | 외부(클라우드 LB 통해) |
| **Headless** (`clusterIP: None`) | 가상 IP 없이 **파드 IP를 DNS로 직접 반환** | StatefulSet 등 개별 파드 지정 |

- **ClusterIP** 가 가장 기본. 내부 서비스 간 통신은 거의 ClusterIP + CoreDNS(`svc.namespace.svc.cluster.local`)로 한다.
- **LoadBalancer** 타입은 클라우드에 LB를 띄운다. 이 프로젝트에서는 외부 노출을 LoadBalancer Service를 직접 쓰기보다 **Gateway API + OCI NLB** 로 처리한다(Gateway 컨트롤러가 NLB를 프로비저닝).
- **Headless** 는 가상 IP를 만들지 않고, DNS 질의 시 **소속 파드들의 IP를 그대로** 돌려준다. StatefulSet에서 `web-0.web.default.svc...` 처럼 개별 파드를 지목할 때 쓴다.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: ClusterIP
  selector: { app: web }
  ports:
    - port: 80        # 서비스가 받는 포트
      targetPort: 8080  # 파드 컨테이너 포트
```

> ★ Service의 본질: **"파드 IP는 변하니, 변하지 않는 이름/IP로 묶어 부른다"**. 어떤 파드로 보낼지는 셀렉터가 정하고, 트래픽 전달은 노드의 kube-proxy(또는 동등 기능)가 처리한다.

## 4. 스토리지 — PV / PVC / StorageClass

파드는 사라지면 안의 데이터도 사라진다. **영속 데이터**가 필요하면 외부 스토리지를 붙여야 한다. 쿠버네티스는 이를 **요청(claim)과 공급(volume)** 으로 분리한다.

| 리소스 | 역할 | 누가 신경 쓰나 |
|--------|------|----------------|
| **PersistentVolume (PV)** | 실제 스토리지 조각(디스크). 클러스터 자원 | 클러스터/플랫폼 관리자 |
| **PersistentVolumeClaim (PVC)** | "이만큼의 스토리지를 달라"는 **요청** | 앱 개발자 |
| **StorageClass** | PV를 **동적으로 자동 생성**하는 방법(프로비저너) 정의 | 플랫폼 관리자 |

- 개발자는 **PVC만 선언**하면 된다. StorageClass가 지정돼 있으면 그에 맞는 PV가 **동적 프로비저닝**으로 자동 생성·바인딩된다.
- StorageClass는 보통 클라우드 블록스토리지 드라이버(CSI)를 프로비저너로 쓴다.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: standard
  resources:
    requests:
      storage: 10Gi
```

> ★ 면접 한 줄: "**PVC = 요청, PV = 공급, StorageClass = 자동 공급 방법**. 개발자는 PVC만 쓰고 나머지는 동적 프로비저닝에 맡긴다."

## 5. 설정 주입 — ConfigMap / Secret

코드와 설정을 분리하기 위해, 설정값을 이미지에 굽지 않고 **런타임에 주입**한다.

| 리소스 | 용도 | 특징 |
|--------|------|------|
| **ConfigMap** | 민감하지 않은 설정(키-값, 설정 파일) | 평문 |
| **Secret** | 비밀번호·토큰·인증서 등 민감 정보 | base64 인코딩 저장, 접근 제어·암호화 대상 |

- **주의**: Secret은 기본적으로 **base64 인코딩일 뿐 암호화가 아니다**. RBAC으로 접근을 제한하고, 필요하면 etcd 저장 시 암호화(encryption at rest)를 켠다.
- 주입 방식은 두 가지: **환경 변수**로 넣기, **볼륨으로 마운트**해 파일로 넣기.

```yaml
apiVersion: v1
kind: ConfigMap
metadata: { name: app-config }
data:
  LOG_LEVEL: "info"
---
apiVersion: v1
kind: Secret
metadata: { name: db-cred }
type: Opaque
stringData:        # stringData는 평문으로 적으면 자동 인코딩
  DB_PASSWORD: "s3cr3t"
```

```yaml
# 파드에서 주입
envFrom:
  - configMapRef: { name: app-config }
  - secretRef: { name: db-cred }
```

> ★ "ConfigMap은 평문 설정, Secret은 민감 정보. **Secret은 암호화가 아니라 base64**라는 점, 그리고 RBAC로 보호한다는 점"이 면접 포인트다.

### 한 줄 요약
**Pod** 는 일회용 최소 배포 단위라 직접 안 쓰고 **컨트롤러**(무상태=Deployment 롤링/롤백, 상태=StatefulSet, 노드별=DaemonSet, 배치=Job/CronJob)에 맡긴다. 바뀌는 파드 IP는 **Service**(ClusterIP/NodePort/LoadBalancer/Headless)로 묶어 부르고, 영속 데이터는 **PVC→(StorageClass)→PV**, 설정은 **ConfigMap/Secret**으로 주입한다.
