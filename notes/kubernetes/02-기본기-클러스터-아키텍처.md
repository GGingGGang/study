## 1. 쿠버네티스란 / 왜 쓰는가

**쿠버네티스(Kubernetes, k8s)** 는 **컨테이너화된 애플리케이션을 자동으로 배포·확장·운영**하는 오픈소스 **오케스트레이터**다. 여러 대의 머신(노드)을 묶어 하나의 큰 자원 풀처럼 다루고, 그 위에 컨테이너를 배치한다.

왜 쓰는가:
- **스케줄링 자동화**: "어느 노드에 띄울지"를 사람이 안 정해도 된다.
- **자가 치유(self-healing)**: 죽은 컨테이너를 재시작하고, 죽은 노드의 파드를 다른 노드로 옮긴다.
- **선언형 운영**: "원하는 상태"만 적으면 시스템이 그 상태로 수렴시킨다(수동 명령 나열 X).
- **수평 확장**: 부하에 따라 복제본 수를 늘리고 줄인다.
- **서비스 디스커버리·로드밸런싱**: 파드 IP가 바뀌어도 안정적인 이름/주소로 접근.

> ★ **핵심**: 쿠버네티스는 "컨테이너를 어떻게 실행할지"를 명령으로 시키는 게 아니라 **"무엇을 원하는지(원하는 상태)"를 선언**하면 알아서 맞춰주는 시스템이다.

## 2. 선언형 모델 + Reconciliation Loop

쿠버네티스의 작동 원리는 단 두 단어로 요약된다: **선언형(declarative)** 과 **조정 루프(reconciliation loop)**.

- **Desired State(원하는 상태)**: 사용자가 YAML로 선언한다. 예: "이 앱 파드 3개를 항상 띄워라."
- **Current State(현재 상태)**: 클러스터에 실제로 떠 있는 상태. 예: "지금 2개만 떠 있다."
- **Reconciliation Loop**: 컨트롤러가 **desired와 current를 끊임없이 비교**하고, 차이가 있으면 current를 desired로 맞추는 동작을 반복한다. (위 예시에서는 부족한 1개를 새로 띄운다.)

```
  ┌──────────── 무한 반복 ────────────┐
  │                                   │
  desired state  ──비교(diff)──▶  current state
 (etcd에 저장된 선언)              (실제 클러스터)
  │                                   │
  └──── 차이가 있으면 액션 수행 ◀───────┘
        (파드 생성/삭제/재시작 등)
```

> ★★★ **면접 단골**: "쿠버네티스는 명령형이 아니라 선언형이다. 컨트롤러가 desired state와 current state의 차이를 계속 좁히는 **reconciliation loop**로 동작한다." 이 한 문장이 쿠버네티스 전체를 관통한다.

## 3. Control Plane (제어 평면)

**Control Plane** 은 클러스터의 "두뇌"다. 클러스터 전체의 결정(스케줄링, 상태 감지·대응)을 내린다. 일반적으로 가용성을 위해 여러 대로 이중화한다.

| 구성요소 | 역할(무엇을 하나) | 핵심 한 줄 |
|----------|-------------------|------------|
| **kube-apiserver** | 모든 요청의 **단일 진입점**(REST API). 인증·인가·검증 후 상태를 etcd에 저장 | 클러스터의 **정문**이자 유일한 etcd 접근 통로 |
| **etcd** | 클러스터의 **모든 상태**를 저장하는 분산 key-value 저장소 | **유일한 진실의 원천(source of truth)** |
| **kube-scheduler** | 새 파드를 **어느 노드에 둘지** 결정(자원·제약·affinity 고려) | 파드 ↔ 노드 **배치 결정** |
| **kube-controller-manager** | 여러 컨트롤러(Node, ReplicaSet, Job 등)를 실행해 reconciliation 수행 | 각종 **조정 루프의 본체** |
| **cloud-controller-manager** | 클라우드 연동 로직(노드 등록, 로드밸런서, 라우트) 분리 실행 | 클러스터 ↔ **클라우드(예: OCI)** 다리 |

> ★ **kube-apiserver만 etcd와 직접 통신**한다. 다른 모든 구성요소(스케줄러·컨트롤러·kubelet)는 etcd를 직접 건드리지 않고 **apiserver를 통해서만** 상태를 읽고 쓴다. 그래서 apiserver가 허브(hub) 역할을 한다.

OKE(Oracle Container Engine for Kubernetes) 같은 매니지드 환경에서는 control plane을 클라우드가 운영·관리하고, 사용자는 보통 워커 노드만 신경 쓴다.

## 4. 노드 (Worker Node)

**노드(Node)** 는 실제 컨테이너(파드)가 실행되는 워커 머신이다. 각 노드에는 다음 세 요소가 돈다.

| 구성요소 | 역할(무엇을 하나) | 핵심 한 줄 |
|----------|-------------------|------------|
| **kubelet** | 노드의 에이전트. apiserver의 지시대로 파드를 띄우고 상태를 보고 | 노드의 **현장 책임자** |
| **kube-proxy** | Service의 가상 IP(ClusterIP)로 온 트래픽을 실제 파드로 전달(iptables/IPVS 규칙 관리) | **Service 트래픽 라우팅** |
| **컨테이너 런타임 (containerd)** | 실제로 컨테이너를 실행하는 런타임. **CRI(Container Runtime Interface)** 로 kubelet과 통신 | **컨테이너 실행 엔진** |

- **CRI**: kubelet과 런타임 사이의 표준 인터페이스. 덕분에 kubelet은 런타임 종류(containerd, CRI-O 등)에 묶이지 않는다. 이 프로젝트에서는 **containerd** 를 쓴다.
- kubelet은 desired(apiserver가 알려준 파드 스펙)와 current(노드에 실제 떠 있는 컨테이너)를 비교해 노드 수준에서도 reconciliation을 수행한다.

## 5. 네트워킹 한눈에

- **CNI (Container Network Interface)**: 파드에 IP를 부여하고 파드 간 통신을 설정하는 플러그인 표준. 이 프로젝트는 **Flannel**(overlay 방식 CNI)을 사용한다. 모든 파드는 **노드를 넘어서도 서로 직접 IP로 통신**할 수 있어야 한다는 것이 쿠버네티스 네트워크 모델의 전제다.
- **CoreDNS**: 클러스터 내부 DNS. `service.namespace.svc.cluster.local` 형태의 이름으로 Service를 찾을 수 있게 해준다(서비스 디스커버리).
- **kube-proxy**: 위 4절 참고. Service의 ClusterIP로 온 트래픽을 뒤의 파드들로 분산한다.

> ★ 파드 IP는 **언제든 바뀐다**(파드는 일회용). 그래서 안정적인 접근점이 필요하고, 그 역할을 **Service + CoreDNS** 가 한다.

## 6. 전체 흐름 텍스트 다이어그램

```
 사용자 (kubectl apply -f deploy.yaml)
        │
        ▼
┌───────────────────── Control Plane ─────────────────────┐
│                                                          │
│   kube-apiserver ──▶ etcd (모든 상태 저장)               │
│        ▲   │                                             │
│        │   ├──▶ kube-scheduler (어느 노드?)              │
│        │   ├──▶ controller-manager (reconcile)           │
│        │   └──▶ cloud-controller-manager (클라우드 연동) │
└────────┼─────────────────────────────────────────────────┘
         │ (지시/보고는 모두 apiserver 경유)
   ┌─────┴───────────────┬───────────────────┐
   ▼                     ▼                    ▼
┌─ Node A ─┐        ┌─ Node B ─┐         ┌─ Node C ─┐
│ kubelet  │        │ kubelet  │         │ kubelet  │
│ kube-proxy│       │ kube-proxy│        │ kube-proxy│
│ containerd│       │ containerd│        │ containerd│
│ [Pod][Pod]│       │ [Pod]    │         │ [Pod][Pod]│
└──────────┘        └──────────┘         └──────────┘
        └──── Flannel(CNI)로 파드 간 통신 / CoreDNS로 이름 해석 ────┘
```

### 한 줄 요약
쿠버네티스는 **선언형 + reconciliation loop**(desired vs current를 끊임없이 좁힘)로 컨테이너를 운영하는 오케스트레이터다. 두뇌인 **Control Plane**(apiserver·etcd·scheduler·controller-manager·cloud-controller-manager)이 결정을 내리고, **노드**(kubelet·kube-proxy·containerd+CRI)가 실제로 실행하며, **CNI(Flannel)·CoreDNS** 가 네트워킹을 담당한다.
