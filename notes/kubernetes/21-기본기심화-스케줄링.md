# 스케줄링 (Kubernetes Scheduling)

> 쿠버네티스 · 기본기 심화 · 학습내용: kube-scheduler의 동작 흐름(필터→스코어→바인딩), 강제 배치(nodeName/nodeSelector), 노드 affinity, 파드 affinity·anti-affinity, taint·toleration, topology spread, PriorityClass·preemption, cordon/drain 운영

---

이 문서는 "파드가 어떤 노드에 어떻게 올라가는가"를 다룬다. 스케줄러의 내부 흐름부터 운영자가 배치를 통제하는 모든 수단(affinity, taint, spread, priority)까지 한 편에 정리한다.

## 1. kube-scheduler의 역할과 동작 흐름

**kube-scheduler** 는 아직 노드가 정해지지 않은 파드(`.spec.nodeName`이 비어 있는 파드)를 감시하다가, 가장 적합한 노드를 골라 그 파드에 바인딩하는 Control Plane 컴포넌트다. 스케줄러는 컨테이너를 직접 실행하지 않는다. **"어느 노드에 둘지"만 결정**하고, 실제 실행은 그 노드의 kubelet이 한다.

### 스케줄링 사이클: 필터 → 스코어 → 바인딩

스케줄링은 크게 **필터링(Filtering)** → **스코어링(Scoring)** → **바인딩(Binding)** 3단계로 진행된다.

| 단계 | 다른 이름 | 하는 일 |
|------|-----------|---------|
| **Filtering** | Predicates | 이 파드를 **올릴 수 있는 노드(feasible nodes)** 만 추린다. 자원 부족, taint 미허용, nodeSelector 불일치 등은 여기서 탈락 |
| **Scoring** | Priorities | 통과한 노드들에 **점수(0~100)** 를 매겨 순위를 정한다. 가장 높은 점수의 노드 선택 |
| **Binding** | — | 선택된 노드를 파드의 `.spec.nodeName`에 기록(apiserver에 바인딩 요청). 이후 해당 노드 kubelet이 실행 |

- **Filtering 예시 체크**: 노드에 요청한 CPU/메모리(requests)만큼 여유가 있는가, 노드의 taint를 파드가 toleration으로 견디는가, nodeSelector/affinity 조건에 맞는가, 노드가 cordon(`unschedulable`) 상태는 아닌가.
- **Scoring 예시 체크**: 자원이 골고루 남도록(LeastAllocated) 혹은 빽빽이 채우도록(MostAllocated) 정책, affinity 선호 조건 만족도, topology spread 균형도, 이미지가 이미 노드에 캐시돼 있는지(이미지 로컬리티).
- 필터를 통과한 노드가 **하나도 없으면** 파드는 `Pending` 상태로 남고, `kubectl describe pod`의 Events에 `0/N nodes are available: ...` 메시지가 찍힌다. 면접에서 "파드가 Pending인데 왜죠?"의 80%는 여기서 출발한다.

> ★★★ **면접 단골**: "스케줄러는 Pending 파드를 감시하다가 ① Filtering으로 올릴 수 있는 노드를 추리고 ② Scoring으로 점수를 매겨 최적 노드를 고른 뒤 ③ Binding으로 파드에 노드를 기록한다. 실행은 kubelet이 한다."

### 스케줄러 프레임워크(확장점)

현대 스케줄러는 **Scheduling Framework** 라는 플러그인 구조다. `QueueSort`, `PreFilter`, `Filter`, `Score`, `Reserve`, `Permit`, `Bind` 같은 **확장점(extension point)** 마다 플러그인이 끼어든다. 앞서 본 "필터→스코어→바인딩"은 이 확장점들을 묶은 큰 그림이다. 면접에선 "프레임워크 기반이라 커스텀 플러그인을 붙일 수 있다" 정도만 알면 충분하다. ★

## 2. 강제 배치: nodeName과 nodeSelector

가장 단순한 배치 통제 수단부터 본다.

### nodeName — 스케줄러를 건너뛰는 직접 지정

`.spec.nodeName`에 노드 이름을 직접 박으면 **스케줄러를 거치지 않고** 그 노드로 바로 간다.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pinned-pod
spec:
  nodeName: oke-worker-1   # 스케줄러 무시, 무조건 이 노드
  containers:
    - name: app
      image: nginx:1.27
```

- 자원이 없어도 강제로 보내므로 위험하다. 노드 이름이 틀리면 영영 안 뜬다. 실무에서 거의 안 쓴다(디버깅/특수 상황용).

### nodeSelector — 라벨 기반 가장 단순한 제약

노드에 붙은 **라벨(label)** 과 정확히 일치하는 노드에만 배치한다.

```bash
kubectl label node oke-worker-2 disktype=ssd
```

```yaml
spec:
  nodeSelector:
    disktype: ssd        # 이 라벨을 가진 노드에만
```

- AND 조건만 가능(여러 키를 적으면 전부 만족해야 함). OR이나 "선호" 같은 표현은 못 한다. 그 한계를 푸는 게 다음 절의 **affinity**다.

## 3. 노드 Affinity (Node Affinity)

**노드 affinity** 는 nodeSelector의 강화판이다. 표현식(`In`, `NotIn`, `Exists`, `Gt`, `Lt` 등)을 쓰고 "필수/선호"를 구분한다.

| 종류 | 의미 | 못 맞추면? |
|------|------|-----------|
| `requiredDuringSchedulingIgnoredDuringExecution` | **반드시(hard)** 만족해야 스케줄 | 만족 노드 없으면 **Pending** |
| `preferredDuringSchedulingIgnoredDuringExecution` | **가능하면(soft)** 만족, weight로 선호도 | 못 맞춰도 **다른 노드에 배치됨** |

`IgnoredDuringExecution`은 "스케줄 시점에만 따지고, 이미 실행 중인 파드는 라벨이 바뀌어도 쫓아내지 않는다"는 뜻이다. ★

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values: ["ap-seoul-1", "ap-seoul-2"]   # 이 두 가용영역만
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 80
          preference:
            matchExpressions:
              - key: disktype
                operator: In
                values: ["ssd"]                          # SSD면 가산점
```

- `required`는 `nodeSelectorTerms`가 OR(여러 term 중 하나), term 안의 `matchExpressions`는 AND다.
- `preferred`는 `weight`(1~100)로 점수에 기여한다. 여러 preferred의 weight 합이 Scoring에 반영된다.

## 4. 파드 Affinity / Anti-Affinity

노드가 아니라 **다른 파드의 위치를 기준**으로 배치를 정한다. "같이 두기(affinity)"와 "떼어놓기(anti-affinity)"다.

- **podAffinity**: 특정 라벨의 파드가 있는 토폴로지(노드/존)에 **같이** 배치(예: 캐시와 앱을 같은 노드에).
- **podAntiAffinity**: 같은 라벨 파드와 **떨어뜨려** 배치(예: 같은 앱 복제본을 노드별로 분산해 단일 노드 장애 대비).

핵심은 **`topologyKey`** 다. "어느 단위로 같이/따로 두느냐"의 기준 라벨이다.

| topologyKey | 분산/집중 단위 |
|-------------|---------------|
| `kubernetes.io/hostname` | 노드 단위 |
| `topology.kubernetes.io/zone` | 가용영역(존) 단위 |

```yaml
# 같은 app=web 라벨끼리 서로 다른 노드에 떨어뜨림 (hard)
spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels:
              app: web
          topologyKey: kubernetes.io/hostname
```

```yaml
# 가능하면 web 파드가 있는 노드에 cache를 같이 (soft)
spec:
  affinity:
    podAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          podAffinityTerm:
            labelSelector:
              matchLabels:
                app: web
            topologyKey: kubernetes.io/hostname
```

> ★ **함정**: `required` podAntiAffinity로 "복제본 3개를 서로 다른 노드에"를 걸었는데 노드가 2개뿐이면, 3번째 파드는 **영영 Pending**이다. 가용 노드 수보다 많은 분산 요구는 hard로 걸지 말고 `preferred`나 다음 절의 topology spread를 쓴다.
>
> 또한 pod affinity/anti-affinity는 **계산 비용이 크다**(모든 후보 노드 × 모든 매칭 파드). 노드가 수백 대 규모면 스케줄링이 느려진다.

## 5. Taint와 Toleration

affinity가 "파드가 노드를 고르는" 끌어당김이라면, **taint/toleration** 은 "노드가 파드를 밀어내는" 메커니즘이다.

- **Taint(노드에 붙임)**: "이 노드는 특정 파드만 받겠다"는 거부 표식.
- **Toleration(파드에 붙임)**: "그 거부를 견딜 수 있다"는 허가증. taint를 견디는 toleration이 있어야 그 노드에 올라갈 수 있다.

```bash
kubectl taint nodes gpu-node-1 dedicated=gpu:NoSchedule
```

taint는 `key=value:effect` 형태이고, **effect**가 동작을 결정한다.

| effect | 동작 |
|--------|------|
| **NoSchedule** | toleration 없는 파드는 **새로 스케줄 안 됨**. 이미 떠 있는 파드는 그대로 둠 |
| **PreferNoSchedule** | 가능하면 피함(soft). 다른 데 없으면 올림 |
| **NoExecute** | 새 스케줄 막는 건 물론, **이미 실행 중인 toleration 없는 파드도 쫓아냄(evict)** |

```yaml
# gpu-node-1의 taint를 견디는 파드
spec:
  tolerations:
    - key: dedicated
      operator: Equal
      value: gpu
      effect: NoSchedule
```

- `NoExecute` toleration에는 `tolerationSeconds`를 줄 수 있는데, "taint가 붙어도 N초는 버티다 쫓겨난다"는 유예 시간이다. 쿠버네티스는 노드가 NotReady가 되면 `node.kubernetes.io/not-ready:NoExecute` taint를 자동으로 붙이는데, 기본 toleration(보통 300초)이 있어 파드가 곧바로 쫓겨나지 않고 5분 정도 버틴다. ★
- **중요**: toleration은 "올라가도 된다"는 허가일 뿐, "올라가라"는 강제가 아니다. 특정 노드 전용으로 쓰려면 **taint(밀어냄) + nodeAffinity/nodeSelector(끌어당김)** 를 함께 걸어야 한다. toleration만 있으면 그 파드는 다른 일반 노드에도 갈 수 있다.

> ★★★ **면접 단골 비교**: "affinity는 파드 입장에서 노드를 고르는 끌어당김, taint는 노드 입장에서 파드를 막는 밀어냄이다. 전용 노드(GPU/시스템)는 taint로 일반 파드를 막고, 전용 파드에는 toleration을 줘서 그 노드에만 모은다."

## 6. Topology Spread Constraints

복제본을 **존/노드에 골고루 분산**하는 표준 방법이다. anti-affinity보다 "균형(skew)"을 정밀하게 제어한다.

```yaml
spec:
  topologySpreadConstraints:
    - maxSkew: 1                                  # 토폴로지 간 파드 수 차이 최대 1
      topologyKey: topology.kubernetes.io/zone   # 존 단위로
      whenUnsatisfiable: DoNotSchedule           # 못 맞추면 Pending
      labelSelector:
        matchLabels:
          app: web
```

- **maxSkew**: 가장 많은 토폴로지와 가장 적은 토폴로지의 파드 수 차이 허용치. 작을수록 빡빡하게 균등.
- **whenUnsatisfiable**: `DoNotSchedule`(hard, 못 맞추면 Pending) vs `ScheduleAnyway`(soft, 균형을 점수로만 반영).
- anti-affinity는 "같은 노드에 두 개 두지 마"처럼 이분법인 반면, spread는 "차이 1까지는 허용"처럼 균형 정도를 조절한다. 다중 존 HA에서 표준으로 쓴다.

## 7. PriorityClass와 Preemption(선점)

자원이 부족할 때 **누구를 먼저 살릴지** 정하는 장치다.

- **PriorityClass**: 우선순위 값(정수)을 정의한 클러스터 리소스. 파드는 `priorityClassName`으로 참조한다.
- **Preemption(선점)**: 높은 우선순위 파드가 Pending인데 올릴 노드가 없으면, 스케줄러가 **낮은 우선순위 파드를 쫓아내(evict)** 자리를 만든다.

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000
globalDefault: false
description: "결제 등 핵심 서비스용"
---
apiVersion: v1
kind: Pod
metadata:
  name: payment
spec:
  priorityClassName: high-priority
  containers:
    - name: app
      image: payment:1.0
```

- `value`가 클수록 우선순위가 높다. 쿠버네티스 시스템 컴포넌트는 `system-cluster-critical`, `system-node-critical`라는 매우 높은 내장 PriorityClass를 쓴다.
- `preemptionPolicy: Never`로 설정하면 "우선순위는 높지만 남을 쫓아내진 않는" 파드를 만들 수 있다(큐에서 먼저 처리되되 선점은 안 함).

> ★ **함정**: 우선순위를 남발하면 낮은 파드가 계속 쫓겨나는 starvation이 생긴다. 또 선점으로 쫓겨난 파드는 PodDisruptionBudget을 best-effort로만 존중하므로, 핵심 워크로드의 가용성이 흔들릴 수 있다.

## 8. cordon / drain (운영: 노드 유지보수)

노드를 점검/교체할 때 쓰는 운영 명령이다.

| 명령 | 동작 |
|------|------|
| `kubectl cordon <node>` | 노드를 **unschedulable**로 표시. **새 파드만 안 받음**, 기존 파드는 그대로 |
| `kubectl drain <node>` | cordon + **기존 파드를 정상적으로 비움(evict)**. 다른 노드로 재스케줄 |
| `kubectl uncordon <node>` | 다시 스케줄 가능 상태로 복구 |

```bash
# 워커 노드 교체 전 안전하게 비우기
kubectl drain oke-worker-3 --ignore-daemonsets --delete-emptydir-data

# 점검 끝나면 복귀
kubectl uncordon oke-worker-3
```

- `--ignore-daemonsets`: DaemonSet 파드는 어차피 모든 노드에 떠야 하므로 무시(안 주면 drain이 거부됨).
- `--delete-emptydir-data`: emptyDir 볼륨을 쓰는 파드가 있으면 데이터 손실을 동의해야 진행됨.
- drain은 **PodDisruptionBudget(PDB)** 을 존중한다. "최소 2개는 항상 떠 있어야 한다"는 PDB가 걸려 있으면 drain이 그 한도를 지키며 천천히 비우거나, 못 비우고 대기한다. 롤링 유지보수 시 가용성을 지키는 안전장치다. ★

> ★★★ **면접 단골**: "cordon은 새 파드만 막고, drain은 cordon에 더해 기존 파드를 다른 노드로 옮긴다. drain은 PDB를 지키면서 비우므로 무중단 노드 교체가 가능하다."

### 한 줄 요약
스케줄러는 **Filtering(가능한 노드 추리기) → Scoring(점수 매기기) → Binding(노드 기록)** 으로 파드를 배치한다. 운영자는 **nodeSelector/nodeAffinity(끌어당김)**, **taint·toleration(밀어냄)**, **pod (anti)affinity(파드 기준 집중·분산)**, **topology spread(균형 분산)**, **PriorityClass·preemption(우선순위·선점)** 으로 배치를 통제하고, **cordon/drain**(+PDB)으로 노드를 안전하게 비운다.
