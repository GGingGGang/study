# 일반 아키텍처 — MSA와 쿠버네티스 플랫폼 (General Architecture: Microservices & K8s Platform)

> 쿠버네티스 · 아키텍처 기준/일반 · 학습내용: MSA 설계 원칙·패턴·트레이드오프, 일반적인 쿠버네티스 플랫폼 아키텍처 계층(네트워킹·게이트웨이·서비스 메시·관측성·GitOps·보안), 그리고 이를 운영하기 위한 일반 규칙·규범(MUST/SHOULD)

---

이 문서는 특정 클라우드·특정 저장소에 종속되지 않는 **일반론**이다. "어떤 플랫폼이든 MSA를 올린다면 이렇게 생각하고 이런 규칙을 지킨다"는 기준을 잡는다. 규칙은 **MUST(반드시)** / **SHOULD(권장)** 로 표기한다.

## 1. 왜 MSA인가 — 모놀리식과의 비교

**모놀리식(monolith)** 은 하나의 배포 단위 안에 모든 기능이 들어 있다. 초기 개발이 빠르고 단순하지만, 규모가 커지면 ① 작은 변경에도 전체 재배포 ② 일부 기능만 확장 불가(전체를 같이 스케일) ③ 기술 스택 고정 ④ 장애 전파(한 모듈이 전체를 끌어내림) 같은 문제가 생긴다.

**마이크로서비스(MSA)** 는 비즈니스 능력(business capability) 단위로 서비스를 쪼개 **독립 배포·독립 확장·독립 기술 선택**을 얻는다. 그 대가로 **분산 시스템의 복잡성**(네트워크 지연·부분 장애·데이터 일관성·운영 복잡도)을 떠안는다.

| 관점 | 모놀리식 | 마이크로서비스 |
|------|----------|----------------|
| 배포 단위 | 전체 한 덩어리 | 서비스별 독립 |
| 확장 | 전체를 함께 | 병목 서비스만 |
| 기술 선택 | 통일 | 서비스별 자유(polyglot) |
| 장애 격리 | 약함(전파) | 강함(격리 설계 시) |
| 데이터 | 단일 DB·트랜잭션 쉬움 | DB 분산·일관성 어려움 |
| 초기 속도 | 빠름 | 느림(인프라 선투자) |
| 적합 규모 | 소규모·초기 | 조직/도메인이 커질 때 |

> ★★★ **핵심**: MSA는 "기술이 멋져서"가 아니라 **조직과 도메인이 커져 독립 배포·독립 확장이 필요할 때** 선택한다. 작은 팀·작은 도메인에 MSA를 강제하면 분산 복잡성만 떠안는다("분산 모놀리식"이 최악).

- **SHOULD**: 도메인이 충분히 크고 팀이 여러 개로 나뉠 때 MSA를 도입한다. 불확실하면 **모듈러 모놀리스**로 시작해 경계가 또렷해진 뒤 분리한다.

## 2. 서비스 분해 — 경계를 어떻게 긋나

MSA의 성패는 **경계(boundary)** 에서 갈린다. 잘못 그으면 서비스끼리 끊임없이 호출하며 강하게 얽혀 분산 모놀리식이 되고 만다.

### (1) 분해 기준
- **도메인 주도 설계(DDD)의 Bounded Context**: 같은 용어가 같은 의미로 쓰이는 범위를 한 서비스로. (예: "주문" 컨텍스트와 "배송" 컨텍스트 분리)
- **비즈니스 능력(business capability)**: 결제, 카탈로그, 사용자, 알림처럼 "조직이 하는 일" 단위.
- **변경 이유(Single Responsibility)**: 함께 바뀌는 것은 함께 두고, 다른 이유로 바뀌는 것은 분리.

### (2) 좋은 경계의 신호
- 서비스 하나가 **자기 데이터를 소유**하고, 외부는 API로만 접근한다.
- 한 기능 변경이 **한 서비스 안에서** 끝난다(여러 서비스 동시 수정 = 경계 오류 신호).
- 팀이 서비스를 **독립적으로 배포**할 수 있다(콘웨이 법칙: 조직 구조와 아키텍처는 닮는다).

- **MUST**: 서비스는 **자기 데이터스토어를 독점 소유**한다. 다른 서비스의 DB를 직접 읽지 않는다(공유 DB 금지).
- **SHOULD**: 처음부터 잘게 쪼개지 말 것. **굵게 시작해 필요할 때 분리**(over-decomposition은 되돌리기 어렵다).

## 3. 서비스 간 통신 — 동기 vs 비동기

| 방식 | 예 | 장점 | 단점 | 쓰는 곳 |
|------|----|------|------|---------|
| **동기(요청-응답)** | REST/HTTP, gRPC | 단순·직관, 즉시 결과 | **결합·지연 전파**, 호출 체인 장애 | 즉시 응답 필요(조회) |
| **비동기(이벤트/메시지)** | Kafka, RabbitMQ, 큐 | **느슨한 결합**, 버퍼링, 확장성 | 최종 일관성, 디버깅 어려움 | 알림·후속처리·팬아웃 |

- **동기 호출 체인의 위험**: A→B→C→D로 동기 호출이 이어지면 **지연이 누적**되고 D의 장애가 A까지 전파된다. 호출 깊이가 깊을수록 가용성은 곱셈으로 떨어진다(각 99.9% × 4 = 99.6%).
- **gRPC vs REST**: gRPC는 HTTP/2 기반 바이너리(Protobuf)라 **내부 서비스 간 고성능 통신**에 유리하다(스트리밍·계약 명확). REST/JSON은 외부 공개 API·디버깅에 친화적이다.

- **SHOULD**: 동기 호출 체인을 **얕게** 유지하고, 후속 작업·팬아웃은 **이벤트(비동기)** 로 분리한다.
- **MUST**: 모든 동기 호출에 **타임아웃**을 건다(무한 대기 금지). 호출 깊이가 깊은 설계는 재검토한다.

### 이벤트 기반과 데이터 일관성
- 서비스마다 DB가 다르므로 **분산 트랜잭션(2PC)** 은 피한다(가용성·성능 저하).
- 대신 **Saga 패턴**(연쇄 보상 트랜잭션)과 **최종 일관성(eventual consistency)** 을 받아들인다.
- **Outbox 패턴**: 비즈니스 DB 변경과 이벤트 발행을 같은 트랜잭션으로 기록 후 비동기 발행 → 메시지 유실 방지.

> ★ **면접 포인트**: "MSA에서 트랜잭션을 어떻게 보장하나?" → **2PC 대신 Saga + 최종 일관성**, 메시지 신뢰성은 **Outbox**로. "한 글자도 안 틀리는 강한 일관성"이 필요하면 그 부분은 한 서비스로 묶는 게 맞다.

## 4. 회복탄력성(Resilience) 패턴

분산 시스템에서 **부분 장애는 정상**이다. 장애가 전체로 번지지 않게 설계한다.

- **타임아웃(Timeout)**: 응답을 무한정 기다리지 않는다. (MUST)
- **재시도(Retry) + 지수 백오프 + 지터**: 일시적 오류만 재시도. **멱등(idempotent)** 하지 않은 요청은 재시도 금지.
- **서킷 브레이커(Circuit Breaker)**: 실패율이 임계치를 넘으면 호출을 차단(open)해 장애 대상을 쉬게 하고, 빠르게 실패(fail-fast).
- **벌크헤드(Bulkhead)**: 자원(스레드풀·커넥션풀)을 격리해 한 의존성의 포화가 전체를 마비시키지 못하게.
- **폴백(Fallback)/우아한 성능저하**: 의존 서비스가 죽어도 캐시·기본값으로 최소 기능 유지.
- **레이트 리밋(Rate Limit)**: 과부하·악용으로부터 보호.

> ★★★ **핵심**: 재시도는 **양날의 검**이다. 멱등하지 않은 요청을 재시도하면 중복 처리가 생기고, 무분별한 재시도는 장애를 **증폭**(retry storm)한다. 재시도에는 **백오프+지터+상한**, 그리고 가능하면 **서킷 브레이커**를 함께 둔다.

이 패턴들은 코드(라이브러리)로 넣기도 하고, **서비스 메시**가 인프라 레벨에서 제공하기도 한다(7장).

## 5. 일반적인 쿠버네티스 플랫폼 아키텍처 — 계층

MSA를 운영하려면 그 아래 **플랫폼**이 필요하다. 대개 다음 계층으로 짜인다.

```
                    [ 사용자 / 인터넷 ]
                            │
              ┌─────────────────────────────┐
              │  ① 노출/엣지: LB → Ingress/Gateway │  ← 외부 트래픽 진입, TLS, 라우팅
              └─────────────────────────────┘
                            │
              ┌─────────────────────────────┐
              │  ② 서비스 메시(선택): mTLS·트래픽·관측 │  ← 서비스 간 통신을 인프라가 관리
              └─────────────────────────────┘
                            │
   ┌──────────────────────────────────────────────────┐
   │  ③ 워크로드: Deployment/StatefulSet/Service (마이크로서비스들) │
   └──────────────────────────────────────────────────┘
        │                    │                      │
 ┌────────────┐   ┌──────────────────┐   ┌──────────────────┐
 │ ④ 관측성     │   │ ⑤ 배포/GitOps     │   │ ⑥ 보안/시크릿/정책 │
 │ 메트릭·로그·  │   │ Git=진실원본,      │   │ RBAC·NetworkPolicy │
 │ 트레이스     │   │ 자동 동기화        │   │ ·시크릿관리·정책엔진 │
 └────────────┘   └──────────────────┘   └──────────────────┘
                            │
                  ┌──────────────────┐
                  │ ⑦ 인프라/IaC       │  ← 클러스터·네트워크·노드 자체를 코드로
                  └──────────────────┘
```

### ① 노출/엣지 — Ingress와 Gateway API
- 외부 트래픽은 **로드밸런서 → 인그레스(Ingress) 또는 Gateway API** 를 거쳐 내부 Service로 들어온다.
- 여기서 **TLS 종료**, **호스트/경로 기반 라우팅**, **리다이렉트** 등을 처리한다.
- 전통 Ingress는 표현력이 약해 어노테이션에 기댔고, 후속 표준인 **Gateway API**는 역할 분리·표현력을 개선했다.

### ② 서비스 메시(선택)
- 서비스 간(동서, east-west) 통신의 **mTLS·트래픽 제어(재시도/타임아웃/카나리)·관측성**을 **애플리케이션 코드 밖**에서 제공한다.
- 사이드카 프록시나 노드/네임스페이스 레벨 프록시로 구현한다. 작은 시스템엔 과할 수 있다(SHOULD: 서비스 수·보안 요구가 커질 때 도입).

### ③ 워크로드
- 마이크로서비스 각각은 보통 **Deployment(무상태) + Service** 로, 상태 저장이 필요하면 **StatefulSet + 영속 볼륨**으로 배포.

### ④ 관측성(Observability) — 세 기둥
- **메트릭(metrics)**: 수치 시계열(요청수·지연·에러율·자원). 알림·대시보드의 기반.
- **로그(logs)**: 이벤트 기록. 사후 디버깅.
- **트레이스(traces)**: 요청이 여러 서비스를 거치는 **경로와 구간 지연**. 분산 시스템 디버깅의 핵심.
- **MUST**: 서비스는 헬스 상태와 핵심 지표(요청수·에러·지연 = **RED**)를 노출한다. **SHOULD**: 트레이스 컨텍스트(W3C `traceparent`)를 전파한다.

### ⑤ 배포/GitOps
- 선언적 매니페스트를 **Git에 두고 클러스터에 자동 동기화**한다. 변경 이력·롤백·감사가 Git으로 일원화된다.

### ⑥ 보안/정책
- **RBAC**(누가 무엇을 할 수 있나), **NetworkPolicy**(파드 간 통신 제한), **시크릿 관리**, **정책 엔진**(허용 규칙 강제), **Pod 보안 표준**.

### ⑦ 인프라/IaC
- 클러스터·VPC/VCN·노드·DB 같은 **하부 인프라 자체를 코드(IaC)** 로 선언·버전관리.

## 6. 노출 계층 일반 규칙

- **MUST**: 외부 진입점에서 **TLS 종료**, HTTP는 HTTPS로 **리다이렉트**(301/308).
- **MUST**: 외부에 노출하는 호스트만 라우팅을 허용하고, 내부 서비스는 클러스터 외부로 직접 노출하지 않는다.
- **SHOULD**: 인증서는 **자동 발급·자동 갱신**(만료 전 갱신)으로 운영한다. 수동 갱신은 사고의 원천.
- **SHOULD**: 라우팅 규칙(호스트/경로/헤더)과 LB 프로비저닝은 **선언적 리소스**로 관리한다.

## 7. 서비스 메시 일반 규칙

서비스 메시는 다음을 코드 밖에서 제공한다.
- **보안**: 서비스 간 **자동 mTLS**(상호 인증·암호화), 워크로드 신원 기반 **인가**.
- **트래픽**: 가중치 분할(카나리/블루그린), 재시도·타임아웃·서킷브레이커, 폴트 인젝션, 미러링.
- **관측성**: 모든 호출의 표준 메트릭·트레이스·액세스 로그 자동 수집.

- **SHOULD**: 서비스 간 통신은 **mTLS 기본(STRICT)** 로 간다(평문 금지). 점진 도입 시 PERMISSIVE→STRICT.
- **SHOULD**: 회복탄력성(재시도/타임아웃/서킷브레이커)을 메시에서 일괄 적용해 **언어·프레임워크 무관**하게 표준화.
- **주의**: 메시는 운영 복잡도와 약간의 지연을 더한다. **필요할 때** 도입한다.

## 8. 관측성 일반 규칙

- **MUST**: 모든 서비스는 **liveness/readiness 프로브**를 제공한다(8장 일반론, 상세는 워크로드 영역).
- **MUST**: **RED 지표**(Rate 요청수 / Errors 에러율 / Duration 지연)를 노출한다. 자원은 **USE**(Utilization/Saturation/Errors)로 본다.
- **SHOULD**: 로그는 **구조화(JSON)** 하고 표준 출력(stdout)으로 보낸다(수집기가 모은다).
- **SHOULD**: 메트릭 라벨의 **카디널리티**(고유 조합 수)를 통제한다(무한 라벨 = 저장소 폭발).
- **SHOULD**: 알림은 **증상(SLO 위반·사용자 영향)** 기준으로 건다(원인 메트릭 난사 금지).

## 9. 배포/GitOps 일반 규칙

- **MUST**: 배포 대상 상태는 **Git이 단일 진실 원본(single source of truth)**. 운영자가 클러스터에 **직접 수동 변경(kubectl edit) 금지**(드리프트의 원천).
- **MUST**: 모든 변경은 **PR/커밋**으로 남겨 감사·롤백을 보장한다. 롤백은 **git revert**.
- **SHOULD**: CI(빌드·테스트·이미지 생성)와 CD(클러스터 반영)를 **분리**한다.
- **SHOULD**: 이미지는 **불변 태그/다이제스트**로 고정(`latest` 금지).

## 10. 보안 일반 규칙

- **MUST**: **최소 권한**. `cluster-admin` 남발 금지, 가능하면 네임스페이스 범위 권한(Role)으로.
- **MUST**: 컨테이너는 **비루트(non-root)·읽기전용 루트FS·불필요 권한 제거**를 기본으로(Pod 보안 표준 restricted 지향).
- **MUST**: 시크릿을 **Git에 평문 저장 금지**. 외부 시크릿 관리/암호화 패턴 사용.
- **SHOULD**: 서비스 간 통신은 **NetworkPolicy로 기본 차단 후 필요한 것만 허용**(deny-by-default).
- **SHOULD**: 이미지 취약점 스캔·서명 검증·정책 엔진으로 배포 게이트를 둔다.

## 11. IaC 일반 규칙

- **MUST**: 클러스터·네트워크·노드 등 인프라는 **코드로 선언**하고 버전관리한다(수동 콘솔 클릭 금지).
- **SHOULD**: 상태(state)·민감값(자격증명·비밀번호)은 **저장소에 커밋하지 않는다**.
- **SHOULD**: 모듈로 분리해 재사용·가독성을 높인다.

## 12. MSA 도입 시 흔한 함정 (안티패턴)

| 안티패턴 | 증상 | 처방 |
|----------|------|------|
| **분산 모놀리식** | 서비스를 쪼갰는데 서로 동기 호출로 강결합, 같이 배포해야 함 | 경계 재설정, 비동기/이벤트로 결합 완화 |
| **공유 DB** | 여러 서비스가 한 DB 직접 접근 | 서비스별 DB 소유, API/이벤트로만 접근 |
| **과도한 분해** | 너무 잘게 쪼개 운영·통신 비용 폭증 | 굵게 시작, 필요 시 분리 |
| **나노서비스** | 함수 하나가 서비스 | 응집도 기준 재통합 |
| **체인 호출 지옥** | A→B→C→D 동기 깊은 체인 | 체인 단축, 캐시, 이벤트화 |
| **관측성 부재** | 장애 원인 추적 불가 | 메트릭·로그·트레이스 표준화 |

### 한 줄 요약
MSA는 **조직·도메인이 커질 때** 독립 배포·확장을 얻으려고 분산 복잡성을 감수하는 선택이며, 성패는 **경계(서비스별 데이터 소유)** 와 **통신(얕은 동기 + 이벤트 비동기 + 회복탄력성)** 에서 갈린다. 이를 떠받치는 일반적인 쿠버네티스 플랫폼은 **노출(Gateway)·메시·워크로드·관측성·GitOps·보안·IaC** 계층으로 이뤄지고, 각 계층은 *TLS·자동화·mTLS 기본·RED 지표·Git 단일 진실원본·최소 권한·코드형 인프라* 같은 MUST/SHOULD 규범으로 운영한다.
