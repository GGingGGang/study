# 오토스케일 (Autoscaling)

> 쿠버네티스 · 기본기 심화 · 학습내용: HPA(메트릭→목표 복제본 계산, 안정화 윈도, CPU/메모리/커스텀), VPA(개념·HPA 충돌), Cluster Autoscaler, Prometheus Adapter(커스텀/외부 메트릭), 스케일 함정(콜드스타트·플래핑·지연)

---

이 문서는 "부하에 따라 알아서 늘리고 줄이는" 세 축을 다룬다. 파드 개수(HPA), 파드 크기(VPA), 노드 개수(Cluster Autoscaler)의 역할과 충돌, 커스텀 메트릭 경로를 자체 완결로 정리한다.

## 1. 오토스케일의 세 축

쿠버네티스 오토스케일은 **무엇을 늘리느냐**에 따라 세 가지다. 서로 보완하며 같이 돌아간다.

| 종류 | 무엇을 조절 | 대상 |
|------|------------|------|
| **HPA** (Horizontal Pod Autoscaler) | **파드 개수**(replicas) | 가로 확장 |
| **VPA** (Vertical Pod Autoscaler) | **파드의 requests/limits**(크기) | 세로 확장 |
| **Cluster Autoscaler** | **노드 개수** | 클러스터 용량 |

```
부하 증가
  │
  ├─▶ HPA: 파드 3개 → 8개로            (앱 수평 확장)
  │        └─▶ 새 파드 둘 자리가 없으면…
  └────────▶ Cluster Autoscaler: 노드 추가  (인프라 확장)
```

핵심 흐름: **HPA가 파드를 늘리려는데 노드에 자리가 없으면 파드가 Pending → 그걸 Cluster Autoscaler가 감지해 노드를 추가**한다. 둘은 짝으로 동작한다. ★

## 2. HPA: 메트릭 → 목표 복제본 계산

**HPA**는 메트릭(기본은 CPU 사용률)을 주기적으로(기본 15초) 관찰해 복제본 수를 자동 조절한다.

### 목표 복제본 계산식 (★★★ 면접 필수)

```
desiredReplicas = ceil( currentReplicas × ( currentMetric / targetMetric ) )
```

예: 현재 4개 파드, 평균 CPU 사용률 80%, 목표 50%라면
`ceil(4 × (80/50)) = ceil(6.4) = 7개`로 스케일 아웃.

- 비율이 1에 가까우면(±10% 기본 tolerance 안) 스케일하지 않는다 → 미세 진동 방지.
- `currentMetric`은 보통 **모든 파드의 평균**이다. 그래서 일부 파드만 튀어도 평균이 낮으면 안 늘 수 있다.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: web-hpa, namespace: ggang-app }
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60     # 파드 평균 CPU 60% 목표
```

> ★ **함정**: CPU `Utilization`은 **requests 대비 백분율**이다. requests를 설정하지 않으면 HPA가 사용률을 계산할 기준이 없어 동작하지 않는다(`<unknown>`). HPA를 쓰려면 **반드시 대상 컨테이너에 CPU/메모리 requests를 설정**해야 한다.

### CPU / 메모리 / 커스텀 메트릭

`autoscaling/v2`는 4가지 메트릭 타입을 지원한다.

| type | 설명 | 예 |
|------|------|----|
| **Resource** | CPU/메모리 (requests 대비 %) | 평균 CPU 60% |
| **Pods** | 파드당 커스텀 메트릭의 평균 | 파드당 초당 요청 수 |
| **Object** | 단일 오브젝트의 메트릭 | Ingress의 RPS |
| **External** | 클러스터 외부 메트릭 | 큐(SQS/Kafka)의 메시지 수 |

- **메모리 기반 스케일의 함정**: 메모리는 회수가 잘 안 되는(캐시·GC 지연) 특성이라 스케일 인 신호가 늦거나 안 내려간다. 메모리는 HPA 지표로 까다로우며, 보통 CPU나 RPS 같은 커스텀 메트릭이 더 안정적이다. ★

### 안정화 윈도(stabilization window)와 동작 정책

스케일 진동(flapping)을 막기 위해 `behavior`로 속도를 제어한다.

```yaml
spec:
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # 최근 5분간 본 값 중 최댓값 기준 → 천천히 축소
      policies:
        - type: Percent
          value: 50                      # 한 번에 최대 50%만 줄임
          periodSeconds: 60
    scaleUp:
      stabilizationWindowSeconds: 0     # 즉시 확장(스파이크 대응)
      policies:
        - type: Percent
          value: 100                     # 한 번에 2배까지
          periodSeconds: 30
```

- **stabilizationWindow**: 그 시간 동안의 추천값을 모아 (scaleDown은 최댓값, scaleUp은 최솟값을) 채택해 급격한 진동을 흡수한다. **스케일 다운은 보수적으로(긴 윈도), 스케일 업은 공격적으로(짧은 윈도)** 잡는 게 정석이다.

> ★★★ **면접 단골**: "HPA는 `desired = ceil(current × 현재값/목표값)`로 복제본을 계산하고, behavior의 stabilization window로 진동을 막는다. 보통 scale-up은 빠르게, scale-down은 천천히 설정한다."

## 3. VPA: 파드 크기 자동 조정과 HPA 충돌

**VPA(Vertical Pod Autoscaler)** 는 파드 개수가 아니라 **각 파드의 requests/limits를 권장·조정**한다. "이 앱은 메모리 700Mi 정도 필요하더라"를 관찰해 requests를 맞춰준다. (코어 쿠버네티스 기본 내장이 아니라 별도 컴포넌트로 설치한다.)

VPA 모드:
- `Off`: 권장값만 보고(추천만), 실제 적용 안 함 — 사이징 분석용으로 안전.
- `Initial`: 파드 생성 시에만 적용.
- `Auto`/`Recreate`: 권장값에 맞춰 **파드를 재생성**해 적용(현재 in-place 조정은 발전 중이라 보통 재시작 동반).

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata: { name: web-vpa, namespace: ggang-app }
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  updatePolicy:
    updateMode: "Off"        # 우선 추천값만 관찰(안전)
```

> ★★★ **HPA와 VPA 충돌**: **같은 메트릭(CPU/메모리)으로 HPA와 VPA를 동시에 쓰면 안 된다.** HPA는 사용률을 보고 개수를 늘리고, VPA는 같은 사용률을 보고 requests를 키우는데, requests가 바뀌면 HPA가 보는 사용률(=사용량/requests)이 흔들려 서로 싸운다(진동). 안전한 조합은 **HPA=CPU(또는 커스텀), VPA는 메모리만 또는 추천 모드(Off)** 로 분리하는 것이다. ★

## 4. Cluster Autoscaler: 노드 개수 조정

**Cluster Autoscaler(CA)** 는 **노드 풀의 노드 수**를 조절한다.

- **스케일 업**: 자원 부족으로 **Pending인 파드**가 있고, 노드를 추가하면 그 파드가 뜰 수 있을 때 노드를 늘린다.
- **스케일 다운**: 노드 사용률이 낮고, 그 위 파드들을 **다른 노드로 옮길 수 있으면** 노드를 비우고(drain) 제거한다.

OKE 같은 매니지드 환경에서는 노드 풀(node pool)에 min/max를 설정해 CA가 그 범위 안에서 노드를 추가/삭제한다.

CA가 노드를 **못 줄이게 막는** 요인(면접 단골):
- **로컬 스토리지(emptyDir) 사용 파드**, kube-system의 일부 파드, **PDB로 이동 불가**한 파드, 다른 노드에 자리가 없어 옮길 수 없는 파드가 있으면 그 노드는 축소 대상에서 제외된다. ★
- HPA가 만든 Pending 파드를 CA가 보고 노드를 추가하므로, **HPA의 maxReplicas와 노드 풀 max가 함께 충분**해야 실제로 확장된다. 둘 중 하나라도 막히면 거기서 멈춘다.

> ★ **세 축의 협업**: HPA(파드 수) + Cluster Autoscaler(노드 수)는 자연스러운 짝. VPA(파드 크기)는 HPA와 메트릭이 겹치지 않게 조심해서 곁들인다.

## 5. Prometheus Adapter: 커스텀/외부 메트릭

HPA가 CPU/메모리를 넘어 **"초당 요청 수", "큐 길이"** 같은 비즈니스 지표로 스케일하려면, 그 메트릭을 쿠버네티스의 **Metrics API**로 노출해야 한다.

| API | 제공자 | 용도 |
|-----|--------|------|
| **metrics.k8s.io** | **Metrics Server** | CPU/메모리(Resource 타입 HPA의 기본) |
| **custom.metrics.k8s.io** | **Prometheus Adapter** 등 | Pods/Object 타입(앱 메트릭) |
| **external.metrics.k8s.io** | Prometheus Adapter / KEDA 등 | External 타입(클러스터 밖 큐 등) |

흐름:

```
앱이 /metrics 노출 ─▶ Prometheus가 수집·저장
   ─▶ Prometheus Adapter가 custom.metrics.k8s.io API로 변환·노출
   ─▶ HPA가 그 API를 조회해 desired replicas 계산
```

```yaml
# 파드당 초당 요청수(http_requests_per_second)로 스케일
spec:
  metrics:
    - type: Pods
      pods:
        metric:
          name: http_requests_per_second
        target:
          type: AverageValue
          averageValue: "100"        # 파드당 평균 100 RPS 목표
```

- **Metrics Server는 필수**: CPU/메모리 기반 HPA와 `kubectl top`은 Metrics Server가 없으면 동작하지 않는다. 커스텀 메트릭은 그 위에 Prometheus Adapter를 추가로 얹는 구조다.
- 이벤트·큐 기반 스케일을 본격적으로 하려면 **KEDA**가 흔한 선택지(external 메트릭 + scale-to-zero). 면접에선 "커스텀 메트릭 HPA의 경로 = Prometheus → Adapter → custom.metrics.k8s.io → HPA"를 설명할 수 있으면 충분하다. ★

## 6. 스케일링 함정 (운영 핵심)

> ★★★ **콜드 스타트(cold start)**: HPA가 파드 추가를 결정해도, 새 파드는 이미지 풀 → 컨테이너 기동 → readiness 통과까지 시간이 걸린다(수십 초~분). 스파이크는 그보다 빨리 온다. 그래서 **HPA만으로는 급격한 트래픽 급증을 즉시 못 막는다.** 완화책: 여유 있는 `minReplicas`, 짧은 readiness/startup, 이미지 캐시, 미리 띄우는 오버프로비저닝(낮은 우선순위 placeholder 파드).

> ★ **플래핑(flapping/진동)**: 임계값 근처에서 늘렸다 줄였다를 반복. 원인은 짧은 stabilization window, 너무 좁은 min↔max, HPA·VPA 동시 사용. 완화책: scale-down stabilization window를 길게(예 300초), 적절한 tolerance, HPA/VPA 메트릭 분리.

> ★ **지연(lag)의 누적**: 메트릭 수집(15s) → HPA 평가 주기 → 파드 기동(콜드스타트) → readiness까지 **여러 지연이 합산**된다. "왜 스케일이 느리지?"는 보통 단일 원인이 아니라 이 사슬 전체다. 각 단계를 짧게 튜닝하고, 예측 가능한 부하는 사전 스케일(스케줄 기반)을 고려한다.

> ★ **scale-to-zero 한계**: 기본 HPA의 `minReplicas`는 1 이상이라 0으로 못 줄인다(0↔1은 KEDA 등이 필요). 또 메모리 기반 스케일 인은 잘 안 내려가는 점(2절)도 운영 함정이다.

### 한 줄 요약
오토스케일은 **HPA(파드 수)·VPA(파드 크기)·Cluster Autoscaler(노드 수)** 세 축이다. HPA는 `desired = ceil(current × 현재값/목표값)`로 복제본을 계산하고 **stabilization window**로 진동을 막으며(scale-up 빠르게, down 천천히), **CPU/메모리(requests 필수)** 외에 **Prometheus Adapter**로 커스텀/외부 메트릭도 쓴다. **HPA가 만든 Pending 파드를 Cluster Autoscaler가 노드 추가로 받쳐준다.** VPA는 같은 메트릭에서 HPA와 충돌하므로 분리해 쓴다. 운영에선 **콜드스타트·플래핑·지연 누적**이 핵심 함정이다.
