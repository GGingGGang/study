# 클라우드보안 시험 대비 통합 요약

6개 강의의 개별 요약을 강의 순서대로 수록했습니다. 대괄호 시간은 해당 강의 SRT의 위치입니다.

## 시험 직전 핵심 정리

클라우드보안은 **어떤 계층을 누가 관리하고, 어떤 신뢰 경계를 통해 공격이 퍼지며, 어떤 통제로 끊는가**를 연결해 공부한다. 범위는 폴더에 제공된 2~7강이다. 아래 내용은 강의의 개념·사례를 통합했으며, 최신 서비스 사양이나 현행 규정 안내가 아니라 시험 복습 자료다.

### 클라우드의 기본 구조와 서비스 모델

강의 정의의 핵심은 온디맨드 셀프서비스, 구성 가능한 자원, 신속한 프로비저닝, 최소한의 이용자 관리 노력이다. 장점은 필요할 때 자원을 확보하는 속도·확장성·운영 부담 감소, 위험은 인터넷 의존·비용 통제·벤더 락인·보안과 프라이버시·공유 인프라·장애다. 사용량이 많으면 클라우드가 항상 저렴한 것은 아니다. 강의의 3천만 원 GPU와 실행당 10만 원 예에서 단순 교차점은 **300회**이며, 실제 비교는 전력·관리·교체·운영기간 등을 포함해야 한다. 2강 [00:01:45–00:19:32].

| 서비스 모델 | 공급자가 제공·관리하는 범위 | 이용자가 중점 관리할 부분 |
|---|---|---|
| IaaS | 물리 인프라·가상화·가상 컴퓨팅 기반 | 게스트 OS, 앱, 데이터, 계정·권한, 네트워크 설정 |
| PaaS | 인프라에 더해 플랫폼·런타임 등 | 앱·데이터·계정 및 서비스 사용 설정 |
| SaaS | 완성된 애플리케이션까지 | 계정·접근 권한, 데이터 사용·분류, 사용 설정 |

이 표는 강의의 계층 구분이며 실제 책임은 서비스에 따라 세부적으로 달라진다. SaaS라도 고객 책임이 0이 되는 것은 아니다. FaaS는 함수 실행 단위, Security as a Service는 보안 기능, DaaS는 데스크톱 환경 등을 서비스로 제공한다. 2강 [00:21:04–00:32:19], 4강 [00:45:20–00:50:08].

| 배포 모델 | 구별 기준 | 고려할 점 |
|---|---|---|
| 퍼블릭 | CSP의 인프라를 서비스로 사용 | 신속한 확장·공유 환경·제공자 의존 |
| 프라이빗 | 단일 조직용 환경 | 높은 통제와 직접 관리 부담 |
| 하이브리드 | 프라이빗과 퍼블릭을 조합 | 민감 데이터 위치와 외부 자원 활용, 연결·운영 복잡성 |
| 멀티 클라우드 | 강의에서는 둘 이상의 퍼블릭 CSP 사용 | 제공자 종속 완화와 도구·정책의 복잡성 |

하이브리드와 멀티 클라우드는 서로 다른 분류 축이며 이름만으로 같은 구성이 아니다. 3강 [00:00:00–00:10:13].

### 자원과 네트워크를 구별하기

리전 안에는 물리적으로 분리된 가용 영역(AZ)이 있고, 가용성·복구를 위해 자원을 분산한다. 로드밸런서는 **트래픽 분배**, 오토스케일링은 **자원 수 증감**이다. 가용성은 필요할 때 서비스에 접근할 수 있는가, 내구성은 저장한 데이터가 손실되지 않고 유지되는가에 초점을 둔다. 2강 [00:32:19–00:49:35].

| 구분 | 정의·강의 예 |
|---|---|
| 객체 스토리지 | 객체 단위 저장, S3 |
| 파일 스토리지 | 파일·디렉터리 방식, EFS·NAS |
| 블록 스토리지 | 디스크 블록처럼 제공, EBS |
| 아카이브 | 장기 보존, S3 Glacier |
| VPN | 떨어진 위치를 공중망 위의 보호된 사설 연결로 연결 |
| VPC | 클라우드 내 가상 네트워크·서브넷·라우팅·접근 경계 |
| VLAN | L2 태그 기반 논리 분리, 강의의 사용 가능 ID 수 4,094 |
| VXLAN | L2 프레임을 UDP로 캡슐화하는 오버레이, 24비트 VNI로 약 $2^{24}$ 세그먼트 |
| SDN | 네트워크 제어·설정을 소프트웨어로 관리하는 접근 |

LVM은 물리 디스크를 논리 볼륨으로 추상화한다. 씬 프로비저닝은 논리 할당량이 실제 물리 용량보다 커질 수 있어 **실사용량을 감시**해야 한다. 실제 100GB에 VM 두 개 각각 80GB를 할당해도 동시에 많이 사용하면 공간 부족이 난다. RAID는 스트라이핑·미러링·패리티의 차이를 구별한다. 강의에서 RAID 5는 최소 3개 디스크와 1개 장애 복구, RAID 6은 최소 4개를 설명한다. 일부 RAID 번호가 자막에서 어긋나 상세 확인 목록을 참조한다. 2강 [00:49:35–00:57:35], 3강 [00:33:30–00:52:32].

### 가상화와 컨테이너

가상화는 물리 자원을 추상화·분할해 VM별로 할당한다. 핵심 요구는 **동등성·충실도, 자원 통제·격리, 성능**이다. 자원 공유로 효율을 얻어도 서로 간섭하거나 다른 고객 데이터에 접근해서는 안 된다. 3강 [00:14:46–00:22:29], 6강 [00:10:59–00:14:23].

| 구분 | 구조 | 장점과 주의 |
|---|---|---|
| Type 1 하이퍼바이저 | 하드웨어 위 직접 실행 | 서버 운영·효율에 적합한 구조. 오버헤드가 전혀 없다는 뜻은 아님 |
| Type 2 하이퍼바이저 | 호스트 OS 위에서 실행 | 설치·사용 편리, 호스트 OS 계층의 영향과 공격면 추가 |
| 완전 가상화 | 게스트 OS를 수정하지 않고 실행 | 호환성, 명령 처리·지원 방식에 따른 비용 |
| 반가상화 | 게스트 수정과 하이퍼콜로 협력 | 처리 효율과 수정·호환성 부담의 절충 |
| 컨테이너 | 호스트 커널 공유, 격리된 실행 환경 | 게스트 OS를 각각 두는 VM보다 가볍지만 커널 공유 위험 |

**Type 1·2는 배치 위치, 완전·반가상화는 구현 방식**이므로 같은 분류가 아니다. Ring 0은 커널, Ring 3은 사용자 권한이라는 CPU 권한 구분을 배우며, 가상화에서 가로채야 하는 요청은 **VM exit → 하이퍼바이저 처리 → VM entry**로 이어진다. 모든 일반 연산이 하이퍼바이저를 거친다는 뜻은 아니다. 바이너리 트랜슬레이션은 명령을 변환해 안전하게 처리하고, SR-IOV는 물리 I/O 장치를 여러 VM에 제공해 처리 경로를 줄이는 방식으로 소개된다. 6강 [00:14:42–00:41:15].

Docker 이미지는 실행 템플릿, 컨테이너는 실행 인스턴스다. 클라이언트는 명령을 요청하고 데몬이 처리하며 레지스트리는 이미지를 저장·배포한다. **cgroups는 자원 한도·사용량 회계, namespaces는 프로세스와 자원 가시성 격리**다. 3강 [00:52:34–01:02:47].

### 공격과 보안 목표

| 공격 | 강의의 주요 흐름 | 피해·방어에서 볼 점 |
|---|---|---|
| DDoS | 봇넷 구축·제어 → 표적 조사 → 다수 요청 | 가용성 저하. 정상 서비스 접근과 트래픽·자원 고갈을 연결 |
| 랜섬웨어 | 침투 → 암호화·접근 차단 → 백업 삭제 → 몸값 요구 | 원본뿐 아니라 복구 경로까지 공격. 백업 보호·복구 점검 필요 |
| APT | 초기 침투 → 발판 → 권한 상승 → 정찰 → 탈취·파괴·감시 | 장기 은밀 침투, 스피어 피싱·측면 이동·지속 감시 고려 |

| 계정·키 유출 | 유출 자격 증명을 API·CLI로 자동 악용 | 정보 유출뿐 아니라 자원 생성·요금 피해. MFA·임시 자격 증명·최소 권한·감사 |
| 구성·운영 실수 | 잘못된 권한·방화벽 규칙·중요 리소스 삭제 | 설정 검증, 변경 관리, 승인·복구·로그를 함께 설계 |

강의 사례의 연도·피해 수치는 상세본에 보존했으며, 시험 답안에서는 공격 이름뿐 아니라 **침투 경로 → 확산 → 피해 자산 → 대응 통제**를 쓴다. 4강 [00:07:05–00:22:10], 5강 [00:01:45–00:09:10].

클라우드 보안의 다섯 원칙은 **가용성, 기밀성, 무결성, 통제, 감사**다. 데이터 위치·법규 차이, 멀티테넌트 격리, 제공자 지속성, 벤더 락인, 사고 통지·조사 협조, 재해복구·업무 연속성도 고려한다. 4강 [00:35:42–00:43:50].

### 공유 책임 모델

**Security of the Cloud**는 데이터센터·전력·물리 하드웨어·기반 네트워크·가상화 등 클라우드 자체를 보호하는 제공자 책임이다. **Security in the Cloud**는 고객 데이터·계정·권한·앱·고객이 설정하는 보안 규칙 등 사용 환경을 보호하는 고객 책임이다. 서비스 모델별 경계가 달라지는 점이 핵심이다. IaaS의 게스트 OS는 고객이, SaaS의 OS는 제공자가 관리한다는 예를 기억한다. 4강 [00:45:20–00:50:08].

계층은 **데이터 → 워크로드 → 가상 네트워크 → 가상화 관리**로 연결한다. IAM은 신원·접근 권한, 보안 그룹·ACL은 네트워크 접근, KMS·HSM은 키 보호, 로그·리소스 구성 모니터링은 변화와 사고의 관찰을 돕는다. 컨테이너·서버리스에서는 이미지·런타임·오케스트레이션·함수·이벤트의 보안도 필요하다. 4강 [00:51:04–00:56:27].

### 경계 보안과 제로트러스트

경계 모델은 외부를 불신하고 내부를 상대적으로 신뢰한다. 분산 클라우드·원격접속에서 경계가 모호하고, 한번 내부에 들어온 공격자의 측면 이동을 놓치기 쉽다. 제로트러스트는 **네트워크 위치나 과거 인증만으로 신뢰를 부여하지 않고 자원 접근마다 신원·권한·기기 상태·맥락을 평가**한다. 특정 제품을 도입하거나 모든 레거시를 폐기한다는 뜻이 아니다. 5강 [00:21:17–00:43:44].

일곱 원리의 강의상 요지는 모든 서비스·데이터를 자원으로 취급, 위치와 무관한 통신 보호, 세션별 최소 권한, 동적 정책, 자산 상태의 지속 점검, 엄격한 인증·인가와 위험 재평가, 상태·로그 수집을 통한 정책 개선이다. 원문 번호·표현이 불완전한 부분은 확인 목록에 남겼다. 5강 [00:44:10–00:47:13].

| 구성요소 | 역할 |
|---|---|
| PDP | 접근 허용 여부를 결정하는 부분. PE와 PA로 구성 |
| PE | 정책·신뢰 정보·상태로 허용·거부 판단 |
| PA | 판단 결과에 따라 경로를 설정·해제하고 집행을 관리 |
| PEP | 실제 요청을 허용·차단하는 집행 지점 |

CDM, 준수 상태, 위협 정보, 로그가 판단에 들어가며 요청 주체와 자원 사이에서 결정·집행을 분리한다. **결정은 PDP, 실제 집행은 PEP**라는 구별이 중요하다. 5강 [00:47:13–00:51:31].

예측 보안의 **VIA는 Visibility → Intelligence → Automation**이다. 로그가 있어도 관찰 가능한 정보로 만들고 분석해 대응으로 연결하지 않으면 충분하지 않다. 강의의 RMF 흐름은 **분류 → 선택 → 구현 → 평가 → 승인 → 모니터링 → 반복**이다. RMF는 위험 관리에서 무엇을 할지, ZTA는 접근 통제를 어떻게 구성할지에 초점을 두며 서로 보완한다. 5강 [00:12:50–00:15:07; 00:54:17–00:56:52].

클라우드 네이티브는 컨테이너·마이크로서비스·서비스 메시·불변 인프라·선언적 API를 활용한다. 보안은 **Cloud, Cluster, Container, Code** 네 층 전체에 적용한다. 인프라·IAM에서 시작해 클러스터 RBAC·네트워크 정책, 이미지·레지스트리·런타임, 코드·의존성·시크릿과 서비스 간 통신까지 연결한다. 5강 [00:59:15–01:04:44].

| 교차 VM 부채널 | 공유 캐시·메모리·스케줄링·타이밍 등 간접 신호로 정보 추론 | 직접 게스트 침투 없이 정보 유출 가능. 강한 격리·파티셔닝·배치 정책·무작위화·모니터링 |
| VM Migration 공격 | 이동 제어면·전송 데이터·모듈 공격 | 잘못된 목적지, 도청, 중단·DoS. 양 끝 인증·허가·전송 암호화·격리·감사 |

**VM Escape와 Hyperjacking은 강의 사례의 진입 경로 차이를 중심으로 설명**하되 Hyperjacking이 모든 상황에서 Type 2에만 한정된다고 단정하지 않는다. VM Sprawl은 악성 공격이 없어도 생기는 관리 실패다. 부채널은 직접 접근권한을 빼앗지 않고도 정보가 새는 문제이며, 암호화만으로 공유 자원 누출이 자동 해결되는 것은 아니다. 7강 [00:10:00–01:15:17].

Live Migration은 실행 중, Cold Migration은 전원을 끈 상태의 이동이다. 운영·부하분산·복구에 유용해도 전송 중 메모리·상태·키와 제어 경로를 보호해야 한다. 하이퍼바이저 침해는 여러 고객에 파급될 수 있으므로 단일 VM 패치만으로 전체 보안이 완성되지 않는다. 이미지 무결성·재사용 전 잔존 데이터 삭제·변경 관리·정기 패치·관리 계정 보호도 함께 본다. 6강 [00:52:41–01:01:15], 7강 [01:10:22–01:15:17].

### 자가 점검

아래 문항은 복습용이며 교수의 출제 예고가 아니다.

1. **SaaS를 쓰면 보안 책임은 전부 제공자에게 가는가?** 아니다. 계정·권한·데이터 사용·고객 설정 책임이 남는다.
2. **컨테이너와 VM의 핵심 격리 차이는?** VM은 게스트 OS를 포함하고, 컨테이너는 호스트 커널을 공유한다.
3. **cgroups와 namespaces를 바꾸어 설명하면 왜 틀리는가?** 자원 한도·회계와 가시성 격리라는 역할이 다르다.
4. **MFA만 도입하면 제로트러스트인가?** 인증은 일부이며 자원별 인가·최소 권한·상태·동적 정책·지속 관찰이 함께 필요하다.
5. **IDS와 IPS 차이는?** IDS는 탐지·보고, IPS는 차단·예방까지 수행한다.
6. **교차 VM 부채널과 VM Escape 차이는?** 전자는 공유 자원 흔적의 추론, 후자는 격리 경계를 넘는 침해다.
7. **마이그레이션에서 암호화 외에 필요한 것은?** 출발지·목적지 인증, 이동 권한, 관리면 보호, 격리·모니터링이다.

- 강의 중 “교과서적인 내용”이라고 짧게 언급한 패치·보안 구성·모니터링 등은 중요도를 낮춘다는 뜻이 아니라 기본 방어를 반복 적용하라는 맥락으로 정리했다. 교수는 별도의 시험 출제 예고를 하지 않았다.

### 전체 내용

#### 클라우드 컴퓨팅의 정의와 작동 방식

강의는 클라우드 컴퓨팅의 핵심을 사용자가 인터넷을 통해 원할 때 필요한 컴퓨팅 자원을 원하는 사양과 양만큼 받아 쓰는 방식으로 설명한다. 교수는 미국 기관의 정의를 소개하며 네 가지 표현을 강조했다. 온디맨드 셀프서비스(on-demand self-service)는 필요할 때 요청해 자원을 받는 것, 구성 가능한 자원(configurable resources)은 사용 목적에 맞게 사양과 용량을 선택하는 것, 신속한 프로비저닝(rapid provisioning)은 요청 뒤 빠르게 할당되는 것, 최소한의 관리 노력(minimal management effort)은 자동화를 통해 이용자가 직접 해야 할 설정을 줄이는 것이다. 자원은 실제로는 원격 데이터센터의 서버·스토리지 등에 있고, 인터넷으로 연결해 이용한다. 인터넷 연결이 전제다. [00:01:45–00:04:15]

첫 슬라이드의 구름·우산 비유는 클라우드 컴퓨팅의 보안 기능이나 서비스를 이용할 때 구독료를 내는 상황을 빗댄 것이다. 데이터센터가 물리적으로 존재하므로 정전·재해 등으로 장애가 날 수 있고 작업물을 보호해야 한다는 점도 비유에서 이어진다. [00:00:12–00:01:45]

#### 장점, 위험과 온프레미스 비교

장점은 유연성, 초기 비용 절감, 확장성, 백업·복구의 편의, 신뢰성과 가용성이다. 온프레미스는 서버실·랙·네트워크·보안 장비를 직접 마련하고 관리해야 하며, 하드웨어가 노후화되면 교체 비용도 든다. 클라우드는 사용한 만큼 비용을 지불하고 보안 기능을 포함한 여러 서비스를 제공받을 수 있으며, 수요에 맞춰 자원을 늘리거나 줄이기 쉽다. 여러 지역의 데이터센터를 활용하면 한 곳의 장애가 다른 곳의 서비스 제공으로 완화될 가능성도 있다. [00:05:04–00:07:26]

반면 위험과 비용상 주의점도 있다. 특정 CSP에 의존하면 다른 사업자의 기능으로 옮기기 어려운 벤더 락인이 생길 수 있다. 초기 구축비는 낮아도 사용 후 청구되는 종량 비용을 예측·관리하기 어려워질 수 있다. 클라우드 데이터도 물리적 데이터센터에 보관되므로 해킹·프라이버시 위험이 사라지지 않는다. 여러 고객이 물리 서버를 공유하므로 파티셔닝·보호가 부실하면 고객 A가 고객 B의 데이터에 접근할 위험이 있다는 것이 공유 인프라 위험(shared infrastructure risk) 사례다. 데이터센터 재해 등으로 다른 센터 연계가 작동하지 못하면 서비스 다운타임과 기업 손실이 발생할 수 있다. 따라서 클라우드가 늘 저렴하거나 안전하다고 단정할 수 없다. [00:08:16–00:11:48]

비용 비교는 초기 지출과 장기 사용량을 함께 보아야 한다. 온프레미스는 공간 임대와 서버·고성능 GPU 구매로 초기 비용이 크지만, 클라우드는 처음에는 싸게 시작해도 사용량이 늘면서 누적 비용이 커진다. 교수의 단순 예시는 GPU 카드 3천만 원을 사는 대신 AI 모델 실행 1회당 클라우드 비용이 10만 원이면, 300회까지는 클라우드 비용이 3천만 원 이하이고 301회부터는 구매한 GPU가 비용상 유리해질 수 있다는 계산이다. 실제 손익은 하드웨어 성능 저하와 교체 비용, 사용량 및 사용기간에 따라 달라진다. 하드웨어 교체 주기가 짧으면 온프레미스 비용이 다시 늘고 비용 교차 시점도 달라지므로 사업자별로 손익을 따져야 한다. 온프레미스는 직접 구축한 설비에 접근할 때 클라우드보다 인터넷 의존이 낮고, 클라우드는 서비스 이용·설정에 인터넷 연결이 필요하다. [00:16:23–00:20:58]

#### 발전사와 서비스 제공 모델

교수는 발전 흐름을 1980년대 메인프레임·자체 서버실, 1990년대 클라이언트-서버 모델, 2000년대 네트워크 기반 시스템, 2010년 이후 대규모 데이터센터를 통한 클라우드 컴퓨팅으로 설명했다. 뒤로 갈수록 서버가 원격화·대형화되고 다수의 전 세계 이용자에게 자원을 제공하는 규모가 커진다. 온프레미스와 클라우드는 물리 장비를 직접 구축·소유하는 방식과 원격 데이터센터 자원을 인터넷으로 빌려 사용료를 내는 방식의 차이다. [00:11:48–00:16:23]

전통적인 서비스 모델은 온프레미스, IaaS, PaaS, SaaS 순으로 이용자가 관리하는 범위가 줄고 제공자가 관리하는 범위가 커진다.

- 온프레미스: 이용자가 하드웨어부터 직접 구축·관리한다.
- IaaS(Infrastructure as a Service): 제공자가 네트워크·스토리지·서버와 가상화까지 제공하고, 이용자는 OS부터 위쪽을 선택·관리한다. AWS EC2는 가상머신을 할당받아 Linux나 Windows 등을 설치해 쓰는 예다. Azure VMs와 Google Compute Engine도 언급됐다. [00:21:04–00:22:51] [00:24:36–00:26:00]
- PaaS(Platform as a Service): 제공자가 개발 플랫폼과 미들웨어·런타임 등을 준비하고 이용자는 주로 코드 작성과 배포에 집중한다. Java 런타임이 준비된 환경에서 Java 코드만 다루는 예가 설명됐다. Google App Engine, Azure App Service, Red Hat OpenShift가 예시다. [00:22:51–00:23:40] [00:26:00–00:27:01]
- SaaS(Software as a Service): 애플리케이션까지 제공되어 이용자는 웹 등으로 소프트웨어를 사용한다. Google Docs·Slides·Sheets, Microsoft Office 365, 웹 기반 한글이 예시다. 로컬 설치가 불필요하고 여러 사람이 한 파일을 동시에 편집해 파일을 버전별로 주고받는 번거로움을 줄인다. [00:23:40–00:24:36] [00:27:01–00:29:14]

교수는 AWS, Microsoft Azure, Google Cloud를 주요 CSP 3사로 제시하고, 경우에 따라 Alibaba Cloud를 포함해 4대 사업자로 말한다고 설명했다. AWS가 앞서 있어 서비스 기능과 명칭이 다른 CSP에도 대체로 비슷하게 적용된다는 것이 교수의 설명이며, AWS 기반 학습이나 자격증이 타 클라우드로 옮겨갈 때 도움이 될 수 있다고 평가했다. 이는 강의 중 교수의 시장·진로 설명이다. [00:24:46–00:25:26] [00:39:30–00:40:34]

IaaS는 물리 하드웨어를 직접 소유하지 않고 가상 서버를 빌리는 모델이지만 OS 설치 등은 이용자가 한다. PaaS는 개발 생산성에 초점을 두며 데이터베이스 관리 시스템, 개발 도구, 프레임워크 등의 환경을 제공한다. SaaS는 소프트웨어 설치·유지관리 부담을 줄이고 공유·협업을 편하게 한다. [00:25:26–00:29:14]

#### XaaS와 데이터센터

IaaS·PaaS·SaaS 외에 XaaS(Anything/Everything as a Service)처럼 기능을 서비스 단위로 제공하는 확장 흐름도 소개됐다. Function as a Service는 개발자가 작성한 함수 단위 기능을 호출·사용량 기준으로 제공하며, 서버리스 컴퓨팅으로 이어지는 예로 설명됐다. Security as a Service는 방화벽, IDS, IPS 같은 보안 기능을 직접 구성하는 대신 구독형 서비스로 이용하는 방식이다. AI 서비스는 이미 준비된 학습 모델에 이용자 데이터를 넣어 사용하는 형태로 설명됐고 GPU 사용 때문에 비용이 더 들 수 있다고 했다. Desktop as a Service는 가상 데스크톱을 서비스로 제공하는 예다. [00:29:14–00:32:19]

데이터센터에는 서버 랙이 대규모로 설치되며 전력과 열을 많이 발생시킨다. 교수는 입지 선정 시 자연재해 가능성과 냉각 여건을 고려해야 하며, 전력·열 부담으로 데이터센터가 주거지 인근에서 기피 시설이 될 수 있다고 설명했다. Google 데이터센터 분포 지도와 한국 데이터센터 분포를 보여주며 수도권 비중을 약 58.8%라고 언급했으나, 이는 2024년 자료라는 설명과 함께 제시된 수치다. 지역 내에서 물리적으로 분리된 데이터센터 건물 단위를 가용 영역(Availability Zone)으로 설명했고, 존 사이의 빠른 데이터 전송 연결이 중요하다고 했다. [00:32:19–00:37:48]

클라우드 자원 관리 방식은 웹 콘솔, API, CLI로 구분해 소개됐다. 콘솔에서는 리전·존을 선택해 가상머신을 할당하거나 서비스를 배포할 수 있다. API는 프로그램으로 자원을 요청·배치·배포하는 방식이고, CLI는 셸/터미널에서 자원을 생성하거나 해제하는 방식이다. [00:37:48–00:40:34]

#### 클라우드 서비스의 구성 요소와 예시

컴퓨트 서비스는 가상 서버 등 계산 자원을 제공한다. VMware ESXi와 오픈소스 하이퍼바이저 Proxmox가 가상머신 생성에 쓰이는 예로 언급됐다. [00:43:06–00:44:05]

로드 밸런서는 여러 VM에 들어오는 이용자 트래픽을 분산한다. 예를 들어 온라인 쇼핑 서비스에 VM 다섯 대를 운영할 때 시간대·요일·이벤트에 따라 접속량이 몰리면 부하를 나누어 과부하를 줄인다. 오토스케일링은 수요에 맞춰 자원을 자동 증설·축소한다. 티켓팅처럼 정오에 트래픽이 치솟는 경우, 하루 종일 피크 수량의 서버를 켜두면 유휴 자원에도 비용을 내지만 자동 확장·축소로 낭비를 줄일 수 있다. [00:44:05–00:48:15]

스토리지는 데이터 아카이빙·백업·파일 서버 등에 쓰이며 내구성과 가용성이 중요하다고 강조했다. AWS 사례로 S3는 객체 스토리지, EFS는 파일 기반 스토리지, EBS는 블록 스토리지이며 데이터베이스 등 가동 중 성능에 민감한 서비스에 쓰는 예로 설명됐다. S3 Glacier는 자주 열지 않지만 장기 보관해야 하는 자료에 적합한 아카이브 스토리지다. 교수는 경찰 사건 기록을 디지털화해 저장하고 필요할 때 검색하는 사례를 들었다. 세 유형은 저장 단위와 특성이 다르므로 구별해야 한다고 했다. [00:48:15–00:52:12]

네트워크 서비스 중 VPN(Virtual Private Network)은 물리적으로 떨어진 장소의 이용자나 사무실을 사설 네트워크처럼 연결하는 방식이다. 사무실 A와 B가 VPN을 사용해 같은 사무실 네트워크에 있는 것처럼 통신하는 예가 제시됐다. VPC(Virtual Private Cloud)는 클라우드 안에 가상 네트워크를 만들어 접근을 통제하는 구조다. VPC가 없으면 인터넷에서 각 EC2 인스턴스에 직접 연결할 수 있는 반면, VPC 구조에서는 먼저 해당 가상 네트워크에 들어온 뒤 그 안의 인스턴스에 접근한다. 다른 VPC에 들어간 이용자는 별도 연결·권한 없이는 다른 VPC의 인스턴스를 볼 수 없다는 접근 격리 설명도 포함됐다. [00:53:01–00:55:52]

VPC 예시에서는 하나의 리전에 네트워크 범위를 정하고 인터넷 게이트웨이와 라우터를 두며, 서브넷을 나누어 IP 범위에 따라 트래픽을 라우팅한다. 이런 네트워크 분리·접근 통제가 보안에 도움이 된다고 설명했다. CIDR 예시의 주소·마스크는 자막이 손상되어 정확한 값은 확인이 필요하다. [00:55:52–00:57:35]

데이터베이스 서비스는 MySQL 같은 DB를 로컬에 직접 설치하는 대신 서비스로 제공받고 원격 접속해 데이터를 읽고 쓰고 갱신하는 방식이다. AWS 예로 RDS, Aurora, DynamoDB가 소개됐고, 교수는 DynamoDB를 NoSQL 서비스로 설명하며 문서형 사용과 낮은 지연 성능을 언급했다. 온프레미스 시스템을 클라우드로 옮기는 리프트 앤 시프트는 호환성·설정·데이터 이전 등의 마이그레이션 작업을 서비스로 지원하는 방식으로 소개됐다. 데이터 분석 서비스는 Spark·Hadoop을 예로 트래픽·사용량을 분석해 결론을 내는 기능, AI·머신러닝 서비스는 GPU와 모델 환경을 직접 마련하지 않고 사용량에 따라 이용하는 기능으로 설명됐다. #### 1. 클라우드 배포 모델과 선택 기준

관리 복잡성은 퍼블릭 단일 이용이 비교적 낮고, 프라이빗은 사내 IT팀이 환경 설정·자원 할당·회수를 맡아야 한다. 하이브리드는 서로 다른 환경을 연결·운영해야 하고, 멀티 클라우드는 CSP마다 지식과 사용법을 익히고 연동해야 하므로 복잡성이 높아진다. 확장성과 유연성은 퍼블릭의 오토스케일링이 유리한 반면 프라이빗은 보유한 물리 장비의 한계가 있다. 하이브리드는 퍼블릭 자원을 더 쓸 수 있지만 두 환경 연결·관리가 필요하며, 멀티 클라우드는 복수 CSP를 조정해야 한다. [00:01:04–00:02:37]

#### 2. 클라우드 기술 계층과 가상화의 목적

강의는 IaaS를 중심으로 클라우드 구조를 설명한다. 기본적으로 CSP가 가상화 계층까지 제공하고, 그 위에서 이용자는 VM, 컨테이너 런타임, 스토리지 등을 쓴다는 도식이다. PaaS는 미들웨어까지 구성해 제공하므로 사용자는 준비된 플랫폼을 가져다 쓴다. 예로 Hadoop, Spark, Flink와 MySQL·Oracle 같은 SQL 데이터베이스, MongoDB·DynamoDB·Redis·Cassandra 같은 NoSQL 계열을 든다. 미들웨어 범위에 DB와 프레임워크도 포함된다고 설명한다. [00:10:18–00:14:46]

가상화는 물리 하드웨어 하나의 자원을 소프트웨어로 논리적으로 나누고 격리해 여러 사용자(테넌트)가 함께 쓰도록 제공하는 기술이다. 가상화의 핵심 목적은 자원 활용 효율을 높이는 것이다. 한 고객에게 물리 서버 전체를 내주면 사용률이 낮을 때 낭비가 크고 비용도 커진다. 클라우드에서는 물리 자원을 공유하므로 테넌트 사이의 격리가 보안상 중요하다. 강의는 서버·네트워크·스토리지를 대표적인 가상화 대상으로 든다. [00:11:13–00:12:20, 00:14:46–00:16:49]

서버 가상화의 예로, 사용률이 각각 30%인 서비스 세 개를 서로 격리된 VM으로 물리 서버 한 대에 올리는 상황을 든다. 합산 사용량이 약 90%라면 각각 별도의 서버를 두어 70%씩 놀리는 것보다 자원을 효율적으로 쓸 수 있다는 설명이다. 강의는 VM 하나가 종료되어도 다른 VM은 유지되는 격리도 함께 언급한다. 기존 구조는 물리 머신 하나에 OS와 서비스 하나를 두어 자원 활용이 낮고, 서비스 수가 늘면 머신도 늘려야 해 확장에 제약이 있다. 가상화 계층 위에 복수 게스트 OS와 애플리케이션을 두면 하드웨어 활용을 높이고 비용을 줄일 수 있다. [00:16:51–00:20:36]

강의는 올바른 서버 가상화의 조건으로 세 가지를 제시한다. (1) 동등성: 게스트 OS가 자신을 물리 OS처럼 인식해 동작상 차이가 거의 없어야 한다. (2) 성능: 하이퍼바이저 계층이 추가되어 베어메탈보다 오버헤드가 생길 수 있지만, 가상화의 이점이 이를 상회하고 기술 발전으로 오버헤드가 줄어드는 방향이라고 설명한다. (3) 자원 통제·격리: 한 VM이 다른 VM에 간섭하거나 영향을 주지 않도록 하이퍼바이저가 분리해야 한다. [00:20:42–00:22:29]

서버 가상화의 장점으로 서버 통합(consolidation)을 설명한다. 물리적으로 분산된 서버나 스토리지 자원을 하나의 큰 자원처럼 보이게 묶어 관리할 수 있다. 예를 들어 각각 512GB인 네 저장 공간을 총 2TB의 단일 공간처럼 다루면 저장 위치를 따로 관리하는 부담을 줄일 수 있다. VM의 OS·애플리케이션·하드웨어 설정을 파일 단위로 감싸 저장하는 캡슐화는 관리와 이식성을 높인다. 파일을 다른 컴퓨터나 하이퍼바이저로 복사해 유사한 VM을 실행할 수 있다. 고가용성 측면에서는 대기 VM으로 서비스를 전환해 물리 머신 장애보다 빠르게 복구할 수 있다고 설명한다. VM 간 격리는 공유 하드웨어를 사용하면서도 서로 접근·영향을 주지 않도록 하는 장점이다. [00:22:30–00:27:12]

다중 OS를 동시에 사용하거나 여러 버전을 시험할 때도 VM이 유용하다. 윈도우 호스트에서 리눅스 게스트를 실행하면 호스트를 삭제하거나 재부팅해 멀티부팅할 필요 없이 병행할 수 있다. 앱 개발자가 Android 버전별 호환성을 확인하는 크로스 플랫폼 디버깅도 예다. [00:27:12–00:29:04]

#### 3. 하이퍼바이저와 VM

서버 가상화 구성 요소는 물리 머신, CPU의 가상화 지원, 하이퍼바이저, VM 및 그 안의 게스트 OS·가상 하드웨어로 설명한다. VM에는 vCPU, 가상 메모리, 가상 디스크 등이 할당된다. 하이퍼바이저는 VM을 만들고 삭제·설정하며, 물리 자원을 VM이 자기 하드웨어처럼 쓰도록 중개한다. [00:29:04–00:30:31, 00:32:41–00:33:30]

하이퍼바이저는 설치 위치에 따라 두 유형이다. 타입 1(베어메탈)은 하드웨어 위에 직접 설치되며 별도 호스트 OS가 필요 없다. VMware ESXi와 Proxmox가 예로 제시된다. 타입 2는 호스트 OS 위에서 실행되며 VMware Workstation과 VirtualBox가 예다. 강의는 타입 1이 호스트 OS 계층을 거치지 않아 성능이 더 좋고, 타입 2는 설치·삭제·관리가 쉽다고 비교한다. VM은 컨테이너와 달리 각자 게스트 OS를 필요로 한다. [00:29:33–00:32:40]

#### 4. 네트워크 가상화

네트워크 가상화는 물리 NIC 하나를 공유하는 호스트에서도 각 VM에 소프트웨어 NIC(가상 네트워크 인터페이스)를 부여해 개별 IP와 네트워크 통신을 가능하게 한다. 관련 기술로 VLAN, VXLAN, VPN, 소프트웨어 브리지·가상 이더넷, iptables가 나온다. [00:33:30–00:35:58]

VLAN(Virtual LAN)은 패킷의 VLAN 태그를 이용해 같은 물리 스위치에 연결된 기기들을 논리적으로 다른 망으로 나눈다. 강의는 VLAN ID가 4,094개로 제한되어 규모가 커지자 VXLAN(Virtual Extensible LAN)이 등장했다고 설명한다. VXLAN은 UDP 패킷 안에 L2 프레임을 캡슐화해 L3 네트워크 위에서 가상 세그먼트를 확장하며, 24비트 식별자로 약 1,600만(2^24)개 세그먼트를 지원하는 규모라고 설명한다. 클라우드 터널링에서 VXLAN이 널리 쓰인다는 설명도 덧붙인다. [00:34:46–00:35:21, 00:36:00–00:36:24, 00:40:00–00:42:46]

VPN(Virtual Private Network)은 인터넷 같은 외부망을 통해 내부망에 안전하게 연결하는 방식으로 소개된다. 퇴근 후 집에서 회사 내부망에 접속하는 예를 든다. 외부 IP를 직접 열어 접속하지 않고 VPN 터널을 이용하며, 강의는 IPsec 기반 암호화로 패킷을 가로채도 내용을 읽기 어렵게 한다고 설명한다. 언급된 방식·프로토콜 이름은 L2TP/IPsec, OpenVPN, PPTP다. [00:35:21–00:36:58, 00:42:50–00:44:11]

SDN(Software-Defined Networking)은 강의 설명에서 기존 네트워크 장비가 제조사별 폐쇄 플랫폼과 서로 다른 명령 체계에 묶여 유지보수·기능 추가가 번거로운 문제를 줄이려는 접근이다. 공개된 규격과 OpenFlow 등을 이용하고, 소프트웨어에서 네트워크 기능을 구현·제어하는 방향으로 설명한다. 로드밸런서, 방화벽, IDS/IPS 같은 기능을 개발자에게 익숙한 언어로 다룰 수 있고 데이터센터에서 활용된다고 한다. 2020년대 클라우드 네이티브 환경에서는 Docker·containerd·Podman 같은 컨테이너 기반 기술에 맞춘 네트워크 관리가 발전한다고 덧붙인다. [00:37:00–00:39:56]

브리지는 L2에서 MAC 주소를 기준으로 세그먼트를 연결하며, 소프트웨어로도 만들 수 있다. 예로 Docker 브리지와 컨테이너 이더넷 인터페이스를 묶는 구성을 든다. 가상 이더넷은 실제 카드가 아닌 소프트웨어 인터페이스로, 호스트와 컨테이너 사이 연결에 사용된다. iptables는 리눅스의 IP 계층(L3) 기반 패킷 필터링·세그멘테이션 기능으로 구분한다. [00:44:12–00:46:03]

#### 5. 스토리지 가상화와 RAID·네트워크 스토리지

스토리지 가상화는 실제 디스크 구성을 사용자나 VM에 논리적 저장 공간으로 보여준다. LVM(Logical Volume Manager)은 물리 디스크 여러 개를 하나의 논리 볼륨처럼 묶어 관리한다. 예를 들어 100GB SSD 세 개를 300GB 공간처럼 보이게 할 수 있다. 반대로 씬 프로비저닝처럼 실제 용량보다 크게 가상 할당할 수도 있다. 강의 예에서는 실제 100GB에 VM 두 개에 각각 80GB를 할당해도 당장 사용량이 물리 용량을 넘지 않으면 가능하지만, 둘이 실제로 많이 써서 한도를 넘으면 오류가 날 수 있다고 설명한다. [00:46:03–00:48:28]

RAID는 디스크를 묶어 성능·용량·장애 복구 특성을 구성하는 기술로 다룬다. 강의는 데이터 블록을 디스크에 나눠 쓰는 스트라이핑 방식은 디스크 하나가 고장 나면 복구가 어렵고, 미러링은 같은 데이터를 다른 디스크에도 복제해 한쪽 고장 시 복구할 수 있다고 설명한다. RAID 5는 스트라이핑과 패리티로 디스크 한 개 장애를 복구하며 최소 3개 디스크가 필요하다고 한다. RAID 6은 이와 유사하지만 더 진보한 패리티 분산 구성으로 설명하고 최소 4개 디스크를 요구한다고 한다. RAID 번호 중 스트라이핑 방식 설명은 자막의 명칭이 서로 맞지 않아 아래 확인 항목을 참조한다. [00:48:28–00:50:24]

네트워크 기반 스토리지로 NAS와 SAN을 소개하고, 현실에서는 NAS를 흔히 사용한다고 설명한다. NAS는 파일 단위로 원격 저장 공간을 제공하며 Synology 제품을 예로 든다. 개인 NAS는 iCloud나 Naver 클라우드 저장공간 구독보다 초기 구축 비용이 들 수 있지만, CSP 종속과 매월 구독료를 줄이고 데이터를 사적으로 관리할 수 있다는 장점이 있다. 강의는 블록·파일·오브젝트 스토리지를 앞서 다뤘다고 언급하고 이 부분은 넘어간다. [00:50:44–00:52:32]

#### 6. 컨테이너와 Docker

클라우드 네이티브는 애플리케이션을 클라우드 배포를 염두에 두고 개발·배포하는 접근으로 설명하고, 이를 촉진한 기술로 컨테이너를 든다. VM과 컨테이너는 모두 물리 서버와 호스트 OS 위에 놓일 수 있지만, VM은 하이퍼바이저와 VM별 게스트 OS가 필요한 반면 컨테이너는 컨테이너 엔진을 사용하고 호스트 커널을 공유한다. 게스트 OS 계층이 없어 컨테이너가 더 가볍고 실행·배포가 빠르며 유휴 자원을 더 줄일 수 있다. 대신 커널을 공유하므로 VM과 같은 경계로 격리된다고 간주할 수 없고, 보안상 위험이 커질 수 있다는 점을 강의가 강조한다. VM은 OS 단위 가상화, 컨테이너는 OS 수준의 프로세스 격리라는 비교다. [00:52:34–00:56:05]

강의는 컨테이너가 등장하기 전부터 Linux Containers(LXC), cgroups, namespaces가 존재했다고 설명한다. Docker의 기여는 완전히 새로운 개념을 만든 것이 아니라 이런 기능들을 사용하기 편하게 묶고 컨테이너 생성·실행·배포·관리를 쉽게 만든 점이다. 강의에서는 Docker를 오픈소스 엔진으로 소개하고 Go 언어로 작성됐다고 말한다. Docker 구조에서 Docker 데몬은 서버 역할을 하고 Docker 클라이언트는 `docker build`, `docker pull`, `docker run`, `docker exec` 같은 명령을 입력하는 사용자 인터페이스다. 이미지 저장소·레지스트리 예는 Docker Hub다. 이미지는 실행 템플릿(객체지향 언어의 클래스와 비슷함)이고, 컨테이너는 이미지에서 만들어 실행하는 인스턴스다. [00:57:07–01:00:03]

LXC는 Docker 이전의 리눅스 컨테이너 기술이며, 강의는 `chroot` 등을 이용해 컨테이너를 만드는 과정이 수작업 위주라 관리하기 어려웠다고 설명한다. 초기 Docker가 LXC를 사용했고 이후 자체 기술을 발전시켰다는 역사 설명도 제시한다. cgroups(Control Groups)는 프로세스·컨테이너별 CPU, 메모리, 디스크, 네트워크 자원 사용량의 제한과 회계를 관리한다. namespaces는 프로세스·컨테이너가 서로의 프로세스 등 시스템 자원을 보지 못하도록 분리하는 핵심 격리 기능이다. 즉 강의 설명에서 cgroups는 자원 통제, namespaces는 가시성과 실행 공간의 격리를 담당하며, Docker는 리눅스가 제공하던 기능을 결합해 다루기 쉽게 한다. [01:00:05–01:02:47]

### 교수 강조 사항

- 가상화는 클라우드 컴퓨팅의 핵심이며, 자원 효율화와 다중 테넌트 격리를 함께 달성해야 한다. 물리 자원을 공유한다고 VM 간 경계가 무너져서는 안 된다. [00:11:41–00:12:02, 00:15:22–00:16:49]
- 서버 가상화의 세 조건으로 동등성, 성능, 자원 통제를 묶어 설명했다. 하이퍼바이저가 VM 간 간섭을 막는 역할이 핵심이다. [00:20:42–00:22:29]
- 배포 모델은 이름만 외우지 말고 소유·구성, 관리 복잡도, 확장성, 보안, 초기 비용의 차이를 이해해야 한다. 특히 하이브리드는 민감 데이터의 프라이빗 보관과 퍼블릭 연산을 조합하는 취지, 멀티 클라우드는 퍼블릭 CSP 복수 사용이라는 구별이 중요하다. [00:00:18–00:02:37, 00:03:10–00:03:57, 00:09:10–00:10:13]
- VM은 게스트 OS를 포함하고 컨테이너는 호스트 커널을 공유한다. 컨테이너의 가벼움·효율성과 커널 공유에 따른 격리 위험을 함께 기억해야 한다. [00:33:05–00:33:15, 00:54:46–00:55:47]
- 컨테이너에서 cgroups와 namespaces의 역할을 구별한다. 전자는 자원 한도·회계, 후자는 프로세스·자원 가시성 격리를 맡는다. [01:01:00–01:02:47]
- 교수의 명시적 시험 출제 예고는 확인되지 않는다. 위 항목은 반복·핵심 설명을 바탕으로 정리한 강조점이며 출제 확정 정보가 아니다.

#### 1. 사이버 위협 환경의 변화와 클라우드의 부상

강의는 클라우드 보안을 이해하려면 먼저 최근 사이버 위협의 변화와 그것이 클라우드에 미치는 영향을 봐야 한다고 설명한다. 교수는 2024~2025년 사례로 2024년 1월 Microsoft Exchange Server 제로데이 취약점(패치 공개 전 악용되는 취약점), 2024년 5월 CrowdStrike Falcon 업데이트 오류로 인한 전 세계 Windows 블루스크린, 2025년 SK텔레콤의 악성코드 침해를 들었다. 이 사례들을 통해 클라우드 기반 이메일·서버와 대규모 서비스 공급망의 문제가 광범위한 장애로 번질 수 있다고 설명했다. “최근 공격이 대부분 Linux 클라우드 서버에서 문제 된다”는 말도 교수의 강의상 평가다. [00:00:35–00:01:34]

공격의 진화 도식에서 X축은 대규모 피해 가능성, Y축은 공격 복잡성과 노련함을 뜻한다. 단순 침입·시스템 침해·DoS에서 서비스 중단 및 고도화된 DDoS로, 더 나아가 사회 혼란·정치적 목적의 핵티비즘으로 확장되는 흐름을 설명했다. 공격 동기도 개인적 호기심·기술적 도전에서 금전 목적의 사이버 범죄, 사회나 시스템을 마비시키려는 공격, 사회·정치적 대의를 내세우는 핵티비즘으로 넓어졌다. 은밀한 공격은 피해와 파급효과를 키울 수 있다. [00:01:37–00:03:40]

#### 2. 주요 공격 유형·절차·사례

**DDoS(분산 서비스 거부)**는 여러 장치가 동시에 대량 요청을 보내 정상 사용자가 웹사이트·서비스에 접근하지 못하게 하는 공격이다. 도로 정체에 비유했으며, 감염 기기에서 서버로 요청이 몰리면 서버 자원과 대역폭 등이 과부하되어 정상 서비스가 중단된다. 클라우드에서는 한 서비스 장애가 연결된 다른 서비스로 연쇄 전파될 수 있다. DDoS-for-hire 서비스(강의 발음상 “DaaS”)가 시간당 약 10달러에 봇넷을 빌려 공격을 제공한다는 사례도 언급했다. 공격 과정은 ① 컴퓨터·스마트폰·IoT 기기를 감염시켜 봇넷 구성 ② 명령·제어 소프트웨어로 감염 기기를 관리하고 규모 확인 ③ 표적 서버의 취약점·용량 한계·네트워크 인프라 조사 및 공격 패턴 계획 ④ 봇넷에 명령해 CPU·RAM·대역폭·DB 등의 처리 한계를 넘는 요청을 동시 전송 ⑤ 서비스 중단과 사업상·재정적 손실 발생 순이다. [00:10:03–00:13:56]

**랜섬웨어**(ransom+software)는 시스템에 침입해 데이터를 암호화하거나 접근을 막고, 복구 대가로 금전(예: 비트코인)을 요구하는 악성 소프트웨어다. 전형적 과정은 ① 피싱·스팸 메일 첨부 악성 파일 등으로 침투 ② 문서·사진·동영상 등 중요 파일 암호화 ③ 복구용 백업 삭제 ④ 피해 사실과 파일 접근 불가를 알리는 메시지 표시 ⑤ 몸값 요구다. 교수는 티켓 판매 서비스 예스24의 장애와 복구 곤란을 최근 사례로 들었다. 별도의 인터넷 호스팅 업체 사례에서는 사회공학으로 관리자가 악성코드를 내려받게 한 뒤 웹 서버에 악성코드를 심고, 침해 서버를 경유해 호스팅 서버 153곳과 백업 서버까지 랜섬웨어에 감염시켰다고 설명했다. 업체명·시점은 자막에 없다. [00:14:03–00:17:22]

**APT(Advanced Persistent Threat, 지능형 지속 위협)**는 특정 조직·국가를 표적으로 장기간 지속하는 고도화 공격이다. 강의의 5단계는 ① 이메일 첨부·웹 취약점 등을 통한 초기 침투 ② 표적 네트워크 안에 안정적 발판(foothold) 구축 ③ 일반 사용자 계정에서 관리자 권한으로 권한 상승 ④ 네트워크 구조·중요 데이터 위치·보안 체계를 정찰 ⑤ 데이터 탈취, 시스템 파괴 또는 지속 감시 등 목적 수행이다. 장기간 은밀하게 진행되어 발견이 어렵다. [00:17:22–00:18:46]

APT 개인정보 유출 사례에서는 표적 직원에게 스피어 피싱(특정 개인·조직 대상 피싱)을 보내 PC에 악성코드를 설치하고, 감염을 내부 PC들로 확산한 뒤 PC 취약점으로 DB 서버에 침투했다. 이어 기존 연결 상태를 악용해 개인정보를 모아 유출했다. 교수는 유출 정보로 아이디·암호화된 주민번호 및 여러 개인정보 항목을 들었으나 정확한 항목 수는 불명확하다. [00:18:55–00:20:03]

또 다른 중앙관리 시스템 악용 사례는 해외 VPN 16대를 경유해 기업의 중앙 PC 관리 시스템에 침투하고, PC 통합관리 업체의 취약점을 이용해 악성코드 33종을 배포한 뒤 PC·서버에서 방위산업 및 통신설비 자료를 탈취·파괴한 사건으로 제시됐다. 대한항공·SK 계열사·KT 계열사 등이 언급되며, 약 4만 대의 PC·서버 피해와 약 8천억 원 손실이라는 수치도 나왔다. 중앙관리 소프트웨어의 취약점이 한 번 악용되면 다수 시스템에 일괄 확산될 수 있다는 점이 핵심 교훈이다. 사건명·정확한 규모는 원문 확인이 필요하다. [00:20:03–00:22:10]

**웹의 구분과 다크웹**: 검색엔진으로 찾을 수 있는 일반 웹은 표면 웹, 검색되지 않지만 합법적 콘텐츠가 있는 영역은 딥웹, 불법 활동이 이뤄지는 영역은 다크웹이라고 강의에서 구분했다. 다크웹은 Tor 같은 특수 브라우저로 접근하며 익명성이 불법 거래에 악용될 수 있다. 의료·금융 플랫폼에서 유출된 개인정보, 이메일 및 신용카드 거래정보가 다크웹 마켓에서 장기간 노출·거래된 사례를 언급했다. [00:22:14–00:23:28]

#### 3. 공격 대상별 표적 공격과 시장·조직 변화

같은 공격 기법이라도 개인 표적인지 국가 기반시설 표적인지에 따라 대응이 달라진다. 표적 공격은 특정 대상을 정하고 약점을 분석해 맞춤 공격을 한다. 강의에서는 조직 취약점 공략, 특정 기업 직접 공격, 모바일 서비스 공격으로 유형을 나눴다. [00:23:38–00:24:47]

금융회사 사례에서는 중요 데이터를 훔치거나 운영을 마비시키려는 공격자가 내부 접근권이 있는 직원 노트북을 스피어 피싱·악성코드로 장악하고, 장기간 내부 구조·중요 데이터·보안 시스템을 살핀 뒤 핵심 서버 데이터를 삭제하고 서비스를 마비시키는 흐름을 설명했다. 방송사와 금융회사 6곳이 동시에 마비된 사례에서는 PC·서버·ATM 등 약 48,000대가 피해를 입고 복구에 일주일이 걸렸다. 이는 단순 정보 탈취뿐 아니라 시스템 파괴와 복구 지연을 노리는 공격의 운영상 피해를 보여준다. [00:24:54–00:27:03]

모바일 공격 예로 카카오톡 PC 버전을 사칭한 피싱 사이트와 가족을 사칭해 급전을 요구하는 사기를 들었다. 일상과 서비스가 모바일로 옮겨가며 공격 표면이 늘어난다는 설명이다. 2025년 트렌드 키워드 가운데 제로 트러스트, 통합 개인정보 보호·컴플라이언스, 엔드포인트 중심 보안 등 절반 이상이 클라우드와 연관된다고 교수는 설명했다. 클라우드 보안은 일반 사이버보안의 주변 주제가 아니라 핵심 영역으로 자리잡았다는 평가다. [00:27:03–00:28:55]

강의는 클라우드 확산으로 물리적 경계가 약해지고 데이터 위치 파악, 멀티테넌트 공유 인프라, 접근권한 관리가 복잡해졌다고 설명했다. 2025년 기술 전망 조사에서는 클라우드 컴퓨팅이 47.3%로 1위, AI가 2위라고 소개했다. 클라우드 시장 점유율 수치로 AWS 30%, Azure 20%, Google 13%, Alibaba 4%를 제시했다. 클라우드 침해 통계로 데이터 침해 33%, 시스템 다운타임 34%, 사고 원인 중 보안 인식 부족 28%를 들며, 구성 오류 등 기술 취약점만 아니라 관리 실수·인식·투자 부족이 큰 위험이라고 강조했다. 이 수치는 교수의 강의 자료 인용이며 기준·출처는 확인이 필요하다. [00:28:59–00:32:43]

공격 표면과 공급망도 확대된다. 강의 자료에는 조직 50%가 클라우드 네이티브 접근을 채택했지만 전체 공격 표면을 적극 모니터링하는 곳은 9%, 관리되지 않는 공격 표면을 통해 공격을 경험한 비율은 69%라고 제시됐다. 서드파티 의존성·오픈소스 위험, 재택근무의 원격 엔드포인트, IT·IoT 융합과 5G 기기 확산이 공격 표면을 넓힌다. 연결 기기 559억 개 전망도 언급됐으나 시점·근거는 불명확하다. [00:32:46–00:34:00]

조직의 클라우드 전환은 ① 초기(Early Stage): 온프레미스 레거시·경계 기반 보안 모델을 그대로 적용하고 클라우드 통합이 제한적 ② 전환 단계: 온프레미스와 클라우드가 공존하는 하이브리드 환경으로, 레거시와 클라우드 보안의 통합이 복잡하며 워크로드 이전 중 보안 공백 발생 가능 ③ 성숙 단계: 클라우드 네이티브 보안 프레임워크, 클라우드 네이티브 애플리케이션, 고도화된 자동화·오케스트레이션을 갖추는 흐름으로 설명됐다. [00:34:05–00:35:33]

### 교수 강조 사항

- 공격의 목적·대상·규모가 호기심에서 금전 범죄, 조직적·국가적 위협, 핵티비즘으로 변하며 물리적 피해까지 일으킬 수 있다. 공격 표면 확대와 서비스형 공격 도구가 위험을 키운다. [00:01:37–00:03:40, 00:05:39–00:06:59]
- IoT의 기본 비밀번호, 취약한 내부 네트워크, 패치 지연·미적용 펌웨어와 탈취된 원격 접근은 봇넷 구성으로 이어질 수 있다. [00:07:05–00:08:27]
- DDoS·랜섬웨어·APT는 각각 가용성, 데이터·복구, 장기 은밀 침투라는 피해 양상을 보인다. 백업 삭제 및 중앙관리 시스템 악용 사례처럼 복구와 확산 경로를 함께 고려해야 한다. [00:10:17–00:22:10]
- 클라우드 장애는 연결된 서비스에 연쇄 영향을 줄 수 있으며, 네트워크 연결과 대역폭, 중복 연결 확보가 중요하다고 설명했다. [00:11:09–00:11:18, 00:38:41–00:39:28]
- 클라우드는 동적이므로 실시간 모니터링·로그 분석과 보안 설정 검증이 중요하다. 5가지 핵심 원칙은 독립 항목이 아니라 서로 연결되어야 한다. [00:37:36–00:38:29]
- 클라우드 보안은 한 팀만의 업무가 아니다. 공유 책임 모델에서 서비스 모델별 책임을 명확히 이해하고 문서화하지 않으면 보안 공백이 생긴다. SaaS로 갈수록 제공자 책임은 늘어도 고객의 핵심 책임은 남는다. [00:45:01–00:45:20, 00:47:33–00:50:08]
- 클라우드에서는 물리 경계가 사라지고 많은 보안 기능이 소프트웨어로 정의되므로, 온프레미스와 같은 방어 방식을 기계적으로 적용하지 말고 워크로드·가상 네트워크·가상화 관리까지 보호해야 한다. [00:51:04–00:52:38]
- 숫자·연도·사건 평가는 강의에서 제시한 내용으로 귀속한다. 교수의 명시적 시험 출제 예고는 확인되지 않는다. 아래 자가 점검 문항은 요약 내용을 복습하기 위해 작성한 문항이다.

### 이론과 공식 목록

1. **제로데이 취약점**: 보안 패치가 나오기 전에 악용되는 취약점. 강의 사례는 Exchange Server 관련 취약점이다. [00:00:46–00:00:59]
2. **공격 진화 축**: X축=대규모 피해 가능성, Y축=복잡성·노련함. 침입·시스템 침해·DoS에서 고도화 DDoS, 사회·정치 목적 핵티비즘으로 변화한다. [00:01:56–00:02:32]
3. **IoT 공격 경로**: 기본 비밀번호 악용, 내부 네트워크 침투, 미패치 펌웨어 취약점, 원격 접근권한 탈취 → 기기 장악·봇넷·정보 거래. [00:07:33–00:08:20]
4. **DDoS**: 다수 장치의 동시 대량 요청으로 정상 이용자의 서비스 접근을 막는 공격. 절차는 봇넷 구축→제어→표적 조사→동시 요청 실행→서비스 중단·손실. [00:10:17–00:13:56]
5. **랜섬웨어**: 침투→중요 파일 암호화/접근 차단→백업 삭제→피해 통보→몸값 요구. [00:14:03–00:15:54]
6. **APT**: 특정 조직·국가 대상 장기 지속 공격. 초기 침투→발판 구축→권한 상승→내부 정찰→탈취·파괴·감시. 스피어 피싱은 특정 개인·조직을 겨냥한 피싱이다. [00:17:22–00:19:56]
7. **웹의 구분**: 강의는 표면 웹(검색 가능한 일반 웹), 딥웹(검색에 노출되지 않는 콘텐츠), Tor 등 별도 접근 방식의 다크웹을 대비하며 다크웹의 불법 거래 사례를 강조한다. **용어 보충:** 검색 노출 여부와 합법성은 다른 기준이며 딥웹·다크웹 자체가 합법 또는 불법을 결정하는 것은 아니다. [00:22:24–00:23:28]
8. **클라우드 보안 5원칙**: 가용성(필요할 때 접근), 기밀성(데이터 비밀 유지), 무결성(승인되지 않은 손실·수정 방지), 통제(Control; 데이터 사용·노출을 관리하고 부주의·악의적 처리를 방지), 감사(Audit; 환경의 활동을 관찰·기록·모니터링). 동적 환경에서 실시간 모니터링과 로그 분석이 중요하며 원칙은 상호 연결된다. [00:35:42–00:38:29]
9. **클라우드 보안 우려**: 네트워크 가용성 및 대역폭, 제공자 지속 가능성과 벤더 락인(고유 API·구조로 이전이 어렵고 비용이 큼), 재해복구·비즈니스 연속성, 사고 통지·조사 협조, 제공자 내부 정책의 투명성 부족. [00:38:31–00:42:02]
10. **물리 통제권 상실·데이터 위치**: 제공자는 효율·가용성을 위해 데이터를 여러 센터로 옮길 수 있고, 국가별 데이터 보호 법규 차이와 준수 문제가 생길 수 있다. 멀티테넌트 공유 인프라에서는 데이터 분리·공유 인프라의 보안 영향을 고려해야 한다. 새로운 클라우드 특유 공격 표면과 제공자 구현 품질 의존도 대응을 어렵게 한다. [00:42:06–00:43:50]
11. **위협 변화 비교**: 교수 설명상 2016년에는 데이터 침해가 주요 우려였고, 2025년에는 미스컨피규레이션(구성 오류)과 변경 관리 미흡이 두드러진다. 복잡한 환경에서 관리 실수가 보안 격차를 만든다. [00:43:52–00:44:41]
12. **공유 책임 모델**: Security **of** the Cloud(클라우드 자체의 보안)는 제공자 책임: 데이터센터·건물·전력·냉각, 하드웨어, 네트워크 인프라, 하이퍼바이저, 호스트 OS 및 기본 서비스. Security **in** the Cloud(클라우드 안에서 고객이 구성·사용하는 보안)는 고객 책임: 데이터 암호화·분류·백업, 계정·접근권한, 애플리케이션 설정·취약점, 네트워크·방화벽 규칙·보안 그룹. IaaS·PaaS·SaaS에 따라 OS·네트워크 제어·애플리케이션·신원 및 인프라 책임 배분이 달라진다. 강의에서 명시한 예: IaaS의 OS는 고객, SaaS의 OS는 제공자 책임. [00:45:20–00:50:08]
13. **온프레미스와 클라우드 보안 계층**: 온프레미스는 외곽에서 안쪽으로 물리/데이터센터→네트워크→서버·DB→데이터를 방어하는 성벽형 계층 모델. 클라우드는 데이터 보안을 유지하면서 ① 워크로드(서버·DB 보안 대체) ② 가상 네트워크(물리 네트워크 대체) ③ 가상화 관리 보안을 포함한 네 계층으로 설명한다. VM·컨테이너·서버리스 관리가 추가 과제다. [00:51:04–00:52:38]
14. **클라우드 계층별 보호**: 데이터는 전송 중·저장 시·처리 중 암호화. 워크로드는 서버 외 컨테이너 이미지·런타임·오케스트레이션 및 서버리스 함수·이벤트 보호. 가상 네트워크는 SDN(Software-Defined Networking)으로 설정·접근 제어를 소프트웨어화하고 방화벽·로드밸런서·VPN 사용. 가상환경 관리에는 Infrastructure as Code, 자동 보안 검사, 컴플라이언스 모니터링 포함. [00:52:56–00:54:30]
15. **구현 구성요소 비교**: 온프레미스 자체 리소스 관리 vs 클라우드 콘솔(AWS 콘솔 예); SSO 중심 vs 클라우드 계정 기반 IAM(Identity and Access Management); 하드웨어 네트워크 보안 vs 보안 그룹·네트워크 ACL 등 소프트웨어 경계; 키 관리에 KMS(Key Management Service)·HSM(Hardware Security Module); 기존 네트워크·서비스·보안 로그 외 클라우드 리소스 구성 상태 추가 모니터링; 물리 데이터센터 보안은 클라우드 제공자 담당. [00:54:34–00:56:27]

## 클라우드보안 5강 클라우드 보안 구현 사례와 제로트러스트·클라우드 네이티브

### 전체 내용

#### 1. 클라우드 운영에서 발생하는 실수와 계정 악용

클라우드 콘솔에서는 몇 번의 조작으로 중요 리소스를 삭제할 수 있고, 보안 그룹이나 버킷 권한 설정이 잘못되면 데이터가 웹에 공개될 수 있다. 강의의 화면 사례는 중지된 서버만 정리하려던 사용자가 정상 운영 중인 서버까지 함께 삭제한 상황이다. 교수는 클라우드 콘솔 UI가 사용 편의에 초점을 맞추어 설계되어 실수를 막아 주지 않으며, 체크박스 하나의 오조작도 프로덕션 서버 삭제로 이어질 수 있다고 설명했다. 삭제 대응에는 ① 최소 권한에 따른 삭제 권한 제한 및 중요 리소스의 추가 승인, ② 제공자 기능(예: EC2 삭제 방지 기능)과 자동 스냅샷·백업 활용, ③ 보안 설정이 계속 유지되는지와 새 리소스에도 적용되는지 정기 점검, ④ 클라우드 환경에 맞춘 삭제·복구·백업 사고 대응 절차가 필요하다. (00:00:09–00:04:00)

계정 위험은 내부 직원의 리소스 남용·오용(개인 목적 사용, 권한 남용에 따른 비용)과 외부 공격자의 계정 탈취 후 리소스 남용·정보 유출로 나뉜다. 사례에서는 사용자가 AWS 접근 자격 증명을 CSV에 저장하고, 이를 피싱·악성코드·취약한 시스템을 통해 탈취한 공격자가 자격 증명으로 EC2 인스턴스를 다수 생성해 외부 서버와 통신시키며 채굴 등 악의적 활동에 쓴다. CLI/API와 자동화 스크립트를 이용하면 수십~수백 대가 빠르게 만들어지고, 회사는 다음 달 청구서를 받고서야 알아차릴 수 있다. 대응은 장기 유지 액세스 키 사용을 최소화하고 임시 토큰·역할 기반 접근을 택하며 루트 계정 사용을 억제하는 것, 콘솔 MFA·강한 암호 정책·API 접근 제한, 사용자 추가나 권한 변경 시 보안 설정 재점검, 계정별 리소스 사용량과 접근 위치·이상 패턴의 실시간 감사 및 경보를 포함한다. 평소 서울에서 접속하던 계정이 갑자기 해외에서 접속하면 알림을 발생시키는 예가 제시됐다. 강의는 보안 조치를 다섯 가지라고 예고했지만 실제 자막에서 번호가 분명히 드러나는 항목은 네 묶음이다. (00:04:02–00:08:39)

#### 2. 전통적인 경계 보안에서 예측·행동 기반 보안으로

전통적 캐슬(성곽) 모델은 중요한 정보를 중심으로 성벽·성문·내부 방어선을 쌓는다. 방화벽, 침입 방지·탐지 시스템, 서버 보안, 데이터 암호화 등으로 층층이 보호하며 알려진 공격 패턴·시그니처를 찾아 차단하고, 통제된 공간·장비·인원만 접근시키는 방식이다. 이에 비해 클라우드 보안의 지향점은 공격 후 차단에 그치지 않고 위험을 미리 감지·예측해 선제 대응하며, 사고가 발생한 경우에도 실시간 분석·시각화로 담당자가 상황을 이해하고 대응하도록 돕는 것이다. AI 기반 행동 분석은 사용자·엔드포인트·네트워크의 정상 행태를 학습해 알려지지 않은 공격도 찾으려 한다. 예를 들어 평소 오전 9시 서울에서 접속하던 사용자가 새벽 3시 영국에서 로그인하거나, 평소보다 많은 데이터를 내려받거나 접근하지 않던 시스템에 접속하면 이상 징후로 볼 수 있다. (00:09:10–00:12:50)

교수는 예측 보안을 VIA 세 요소로 설명했다. 가시성(Visibility)은 로그를 모으는 데서 그치지 않고 빅데이터 분석·BI·시각화를 통해 위협과 보안 수준을 유의미한 정보로 드러내는 것, 인텔리전스(Intelligence)는 통계·예측 모델·머신러닝·딥러닝 등으로 오류와 분석 지연을 줄이고 로그인·데이터 접근 이상을 분석·예측하는 것, 자동화(Automation)는 위험이 예측되거나 발생했을 때 보호 조치를 지연 없이 실행하는 것이다. 로보틱 프로세스 자동화, 소프트웨어 정의 경계, SOA 등이 예로 언급됐다. 가시성이 지능 분석의 기반이고 지능 분석이 효과적 자동화를 가능하게 하므로 세 요소는 연결되어야 한다. (00:12:50–00:15:07)

현대 클라우드 보안 기술·접근으로 제로트러스트 아키텍처, AI/머신러닝 위협 탐지, 클라우드 네이티브 애플리케이션 보안(CNAPPs로 들리는 약어), 개발·보안·운영 통합(DevSecOps로 들리는 표현), 지속적 모니터링·평가가 소개됐다. 교수는 모든 기술의 성숙도가 같지 않으므로 도입 전 성숙도와 현실 적용 가능성을 평가해야 한다고 강조했다. 가트너 하이프 사이클은 혁신 초기 기술은 위험 부담이 커 파일럿에 적합하고, 가치가 입증되어 안정 운영되는 기술도 구분하며, 성숙까지 걸리는 기간(예: 2년 이내 또는 10년 이상)을 고려해 단기·장기 보안 전략을 세우는 참고 자료로 설명됐다. (00:15:07–00:18:54)

#### 3. 경계 기반 보안의 구조와 한계

교수는 기존 군사 환경의 C4I 아키텍처 같은 체계적 접근을 클라우드에 참고할 수 있다고 소개하고, 클라우드 보안 영역을 위험 관리, 접근 제어, 네트워크 보안, 데이터 보안, 가상화 보안의 다섯 도메인으로 정리했다. 위험 관리는 전체 위험 평가·관리, 접근 제어는 사용자와 시스템의 권한 관리, 네트워크 보안은 클라우드 네트워크 보호를 뜻한다. 데이터·가상화 보안과 클라우드 공통 위협 대응도 별도 보호 대상이라고 덧붙였다. C4I의 정확한 명칭·도식과 도메인 세부 분류는 슬라이드 대조가 필요하다. (00:19:01–00:21:06)

전통적 경계 보안은 인터넷→방화벽→DMZ→네트워크 스위치→내부 시스템의 단계적 구조다. 방화벽은 외부 악성 트래픽을 막는 첫 관문, DMZ는 외부 제공 웹 서비스 등을 두는 완충 구역, IDS는 네트워크 트래픽을 감시하는 침입 탐지 시스템이다. 핵심 가정은 “외부는 위험하고 내부는 안전하다”는 것이다. 따라서 투자는 경계 강화에 집중되고, 내부 사용자·서버 사이 통신은 별도 검증이 약해진다. 공격자가 경계를 한 번 넘으면 내부 이동·확산이 쉬워지는 것이 구조적 약점이다. (00:21:06–00:23:37)

클라우드와 원격 근무로 이 모델의 경계는 흐려졌다. Work From Anywhere, 재택·모바일·태블릿·협력사 접근으로 사무실 네트워크 안팎의 구분이 약해졌고, 리소스는 AWS·Azure·Google Cloud와 전 세계 지사에 분산됐다. IoT 센서와 스마트 기기도 늘어 통제 가능한 단말이라는 전제가 무너졌다. 내부망에 있다는 사실만으로 안전하다고 할 수 없으며 재택 환경이나 협력사를 통해 침입할 수도 있다. (00:23:53–00:26:44)

교수는 경계 모델의 한계를 보여주는 사례로 미국 동부 연료 공급의 약 45%를 담당하는 파이프라인 랜섬웨어 공격(5일 중단, 연료 공급 혼란·가격 상승)을 들었고, 미국 의료 시스템의 약 3분의 1을 처리하는 의료 인프라가 마비되어 병원이 수작업으로 전환하고 환자 치료에 차질이 생긴 사례도 언급했다. 랜섬웨어 공격자는 초기 진입 뒤 내부 시스템을 옮겨 다니며 권한을 넓히고 가능한 많은 시스템을 감염시키려 한다. 자격 증명을 이용해 정상 사용자처럼 들어오거나 소프트웨어 공급망의 정상 업데이트 경로를 악용하면 방화벽·침입 탐지에서 구분하기 어렵다. 강의는 Colonial Pipeline으로 추정되는 파이프라인 사례와 의료 사례의 이름·세부 사실을 자막만으로 확정하지 않으므로 교수 설명으로 귀속한다. (00:26:44–00:31:18)

SolarWinds는 공급망 공격 사례로 제시됐다. 배포되는 소프트웨어에 악성 요소가 들어가면 정상 업데이트와 악성 행위를 경계 장비가 구분하기 어렵고, 설치 후 수개월 동안 탐지되지 않을 수 있다. 내부 시스템을 안전하다고 간주하는 전제가 문제다. 내부자 위협도 경계 보안에 취약하다. 원격 접속·다중 클라우드·분산 업무로 감시 범위가 커지고 로그가 방대해져 비정상 행위를 찾기 어려우며, 악의적 행동의 명확한 정의와 여러 관점의 상관관계 분석도 부족할 수 있다. (00:29:16–00:32:22)

교수가 정리한 경계 모델의 여섯 결함은 ① 내부망 안전 가정에 따른 묵시적 신뢰, ② 신뢰/불신만 나누는 이분법, ③ 경계 침해 후 측면 이동(Lateral Movement) 허용, ④ 내부 활동 모니터링 부족, ⑤ 내부 신뢰 관계를 이용한 권한 상승 용이, ⑥ 정상 행위와 위협 행위의 구별·탐지 복잡성이다. 해법의 출발점은 신뢰를 전제로 하지 않고 의심하며 확인하는 태도다. (00:32:22–00:34:52)

#### 4. 제로트러스트의 원리와 구현 아키텍처

제로트러스트는 “절대 신뢰하지 말고 항상 검증(Never Trust, Always Verify)”하는 보안 철학·패러다임이다. 하나의 큰 경계 안을 신뢰하는 방식과 달리 각 리소스마다 보안 경계를 두며, 리소스에 접근할 때마다 인증·권한을 확인한다. 신뢰의 단위를 조직 경계에서 개별 접근·세션으로 바꾸면 한 시스템이 침해되어도 다른 시스템으로의 확산을 제한할 수 있다. 회사 건물 비유에서 경계 모델은 로비에서 한 번 출입증을 확인한 뒤 내부를 자유롭게 다니는 모습이고, 제로트러스트는 공간별 출입 통제·지속 감시·필요한 저장소 접근을 두는 모습이다. 아이디·방문증으로 한 번 확인하고 끝내는 것이 아니라 신원과 권한을 지속 확인한다. (00:34:52–00:40:23)

제로트러스트와 보안 통제(Security Controls)는 구분된다. 제로트러스트는 보안에 대한 철학·사고방식이고, 통제는 네트워크에서 허용할 경로 등 구체적인 규칙이다. 통제 준수만으로 보안이 완성되지는 않는다. 예를 들어 최소 길이 8자 비밀번호 규칙을 지키더라도 ‘12345678’ 같은 약한 암호는 안전하지 않다. 교수는 규정이 최소 기준선이며, 제로트러스트 문화를 내면화해 지속 인증·행동 분석 등 실제로 안전한 행동을 택하는 것이 중요하다고 설명했다. (00:40:23–00:43:44)

제로트러스트의 일곱 원리는 강의에서 다음 취지로 설명됐다. ① 데이터 원천·컴퓨팅 서비스 등 모든 데이터와 서비스를 보호 대상 리소스로 취급한다(개인 소유 기기도 내부 리소스에 접근한다면 포함). ② 네트워크 위치와 관계없이 모든 통신의 기밀성·무결성을 보호한다. ③ 세션 단위로 접근을 평가하고 업무에 필요한 최소 권한만 준다. ④ 사용자·애플리케이션·요청 자산의 상태·행동·환경 속성을 고려해 동적으로 접근을 결정한다. ⑤ 모든 자산의 무결성과 보안 상태를 지속 모니터링하고 필요하면 패치 등 복구 조치를 한다. ⑥ 엄격한 인증·접근 검사 뒤 허용하고 접근 중에도 위협·위험을 평가하며 신뢰를 재평가한다(다중 인증과 계정/세션 관리가 예로 언급됨). ⑦ 사용자·기기·네트워크·인프라 상태, 트래픽, 접근 요청 정보를 수집·처리해 보안 정책 개선에 쓴다. 일부 원리의 번호·정확한 표현은 자막이 손상되어 취지만 정리했으며 슬라이드 확인이 필요하다. (00:44:10–00:47:13)

제로트러스트 아키텍처(ZTA)는 철학을 구현하는 구조다. 모든 주체(Subject)의 자원 접근 요청은 PEP(Policy Enforcement Point, 정책 시행 지점)를 지나며, PDP(Policy Decision Point, 정책 결정 지점)가 접근 허용 여부를 판단한다. 묵시적 신뢰 구간을 최소화하도록 PDP·PEP를 자원 가까이 둔다. 요청 주체와 판단 지점 사이의 비신뢰 구간은 요청을 신뢰하지 않는 영역이고, PEP를 통과해도 자원까지의 신뢰 구간을 가능한 작게 유지한다. 다섯 핵심 보호 영역으로 신원, 기기, 네트워크, 애플리케이션, 데이터가 언급됐다. (00:47:13–00:49:30)

구성 요소는 네 가지로 소개됐다. PDP는 접근 정책을 결정하는 상위 개념이며 Policy Engine(PE)과 Policy Administrator(PA)로 구성된다. PE는 신뢰 정보를 바탕으로 허용·거부 결정을 계산하고, PA는 그 결정을 받아 주체와 자원 사이 통신 경로를 설정·해제하며 PEP와 연동해 동적 권한을 집행하도록 한다. PEP는 자원 앞의 최종 관문으로 PDP 결정을 실제 접근 제어로 실행한다. CDM(지속적 진단 및 완화), 규정 준수 정보, 위협 인텔리전스, 활동 로그 등이 제어 영역에 입력되고 정책 엔진·관리자가 판단한 결과가 데이터 영역의 PEP를 통해 집행되는 흐름이다. (00:49:30–00:51:31)

제로트러스트는 한 번에 완성되는 제품이 아니라 현재 상태를 평가하고 점진적으로 성숙도를 높이는 여정이다. 강의는 전통적/초기에서 고급·최적 단계로 나아가는 모델과 국내 성숙도 모델 1.0 및 더 세분화된 2.0을 언급했다. 체크 항목으로 현 수준을 평가해 조직 여건과 기술·위협 변화에 맞춰 개선한다. 레거시 기술을 전부 없애야 하는 것은 아니다. 제로트러스트는 특정 기술이 아니라 방향성이므로 기존 기술도 그 원리에 맞게 활용할 수 있고, 성숙도가 낮다고 완전히 ‘비(非) 제로트러스트’로 단정하지 말고 전략적으로 발전시켜야 한다. (00:51:31–00:54:17)

RMF(Risk Management Framework)는 NIST SP 800-37로 들리는 문서에 근거한 조직 차원의 위험 관리 방법론으로 설명됐다. 단계는 분류(자산·정보 체계화), 선택(보안 통제 선택), 구현, 평가, 승인, 모니터링이며 순환적으로 지속 위험 관리를 수행한다. 프레임워크는 “무엇을 해야 하는가”에 답하며 프로세스·절차·역할·평가 방법을 다룬다. 아키텍처는 “어떻게 구현하는가”에 답하며 구조와 메커니즘을 다룬다. RMF는 거버넌스와 위험 기반 의사결정, ZTA는 동적·세분화된 접근 통제의 구현에 초점을 두므로 상호 보완적이다. (00:54:17–00:56:52)

#### 5. 클라우드 네이티브와 계층별 보안

강의에서 인용한 VMware 정의에 따르면 클라우드 네이티브는 클라우드 컴퓨팅 방법·도구, 현대적 아키텍처와 자동화를 활용해 복잡성을 관리하고 개발 속도를 높이는 애플리케이션 개발·배포·실행 방식이다. 핵심은 마이크로서비스·컨테이너와 DevOps·CI/CD다. 발전 흐름은 물리 서버·모놀리식에서 가상 서버를 거쳐 2010년대 이후 컨테이너·마이크로서비스로 이어진다고 설명됐다(중간 연대·약어는 자막 불명확). 마이크로서비스는 큰 앱을 독립 개발·배포 가능한 작은 서비스로 나눠 민첩성과 개발 용이성을 높인다. 컨테이너는 앱과 의존성을 패키지로 묶어 환경 차이로 인한 “내 컴퓨터에서는 되는데 서버에서는 안 되는” 문제를 줄인다. 서비스 메시가 서비스 간 통신을 관리하고, 불변(Immutable) 인프라는 배포 뒤 직접 수정하지 않고 새 인프라를 만들어 교체한다. 선언적 API는 수행 절차보다 원하는 상태를 명시한다. (00:56:52–01:00:38)

교수가 제시한 장점은 트래픽 변화에 따른 동적 확장, 한 서비스 장애에도 다른 서비스가 계속 작동하는 회복성, 기능의 빠른 개발·배포, AWS·Google Cloud·온프레미스 사이의 이식성이다. 클라우드 네이티브 보안은 단일 경계에 의존하지 않고 계층을 아우르는 PO(C)C(Cloud, Cluster, Container, Code) 모델로 설명됐다. ① Cloud: IaaS/PaaS 등 기반 인프라·클라우드 서비스 보안. ② Cluster: Kubernetes·OpenShift 같은 오케스트레이션 플랫폼 보안. RBAC(역할 기반 접근 제어), 정책, 네트워크 정책에 의한 Pod 간 통신 제어, Pod Security Standards와 실행 정책을 다룬다. ③ Container: 런타임·이미지·레지스트리 보안 및 이미지 취약점 스캔. 애플리케이션 코드가 안전해도 베이스 이미지·의존 라이브러리에 취약점이 있을 수 있다. ④ Code: 애플리케이션 코드·비즈니스 로직·민감 데이터 보호. 보안 코딩, 애플리케이션 보안 테스트, API 키·DB 비밀번호 등 비밀정보 관리, 마이크로서비스 간 통신 데이터 보호가 중요하다. 각 층은 독립적으로 끝나는 것이 아니라 전체 환경에서 함께 작동한다. (01:01:34–01:04:44)

### 교수 강조 사항

- 클라우드 콘솔의 작은 조작 실수도 중요 리소스 삭제로 이어질 수 있으므로 권한 제한·추가 승인·백업·복구 절차와 지속 점검이 필요하다. (00:01:45–00:04:00)
- 자격 증명 유출은 자동화된 API/CLI 사용으로 큰 비용·정보 피해로 번질 수 있다. 장기 키와 루트 계정을 줄이고 MFA, 임시 자격 증명, 실시간 사용량·위치 감사를 적용한다. (00:05:16–00:08:39)
- 클라우드 보안은 기술 솔루션 하나로 해결되지 않는다. 예측 보안에서 가시성→인텔리전스→자동화가 이어져야 한다. (00:08:39–00:09:10, 00:12:50–00:15:07)
- 기술 도입은 유행보다 성숙도·현실 적용성·조직의 단기 및 장기 계획을 보고 정한다. 초기 기술은 파일럿으로 검증한다. (00:16:28–00:18:54)
- “내부는 안전하다”는 경계 모델의 묵시적 신뢰가 측면 이동·권한 상승·탐지 지연의 근본 원인이다. (00:22:35–00:23:31, 00:32:22–00:34:52)

### 전체 내용

#### 가상화와 클라우드 인프라

가상화는 주어진 물리 하드웨어 자원으로 실제 머신처럼 동작하는 논리적 머신을 만들고 관리하는 기술이다. 클라우드의 핵심 기반이며, 하이퍼바이저는 컴퓨팅 자원을 VM에 배분하고 VM을 생성·관리한다. 하이퍼바이저는 VMM(Virtual Machine Monitor 또는 Virtual Machine Manager)이라고도 한다. 가상화 전에는 물리 서버마다 OS와 애플리케이션이 있지만, 가상화에서는 하드웨어 위의 가상화 계층이 여러 게스트 OS에 가상 하드웨어를 제공한다. 게스트 OS는 하이퍼바이저를 통하여 물리 자원에 접근하고, VM끼리는 서로 격리되어야 한다. VCPU·VNIC는 실제 CPU·NIC가 VM마다 따로 있다는 뜻이 아니라, 하이퍼바이저가 가상 장치로 제공하는 것이다. VM 구성은 파일로 캡슐화될 수 있어 종료 후 파일을 옮기면 다른 머신에서 같은 VM을 실행(마이그레이션)할 수 있다. [00:00:17]–[00:03:00], [00:07:32]–[00:09:13]

가상화는 CPU·메모리·스토리지 등 물리 자원 풀에서 VM마다 필요한 양을 동적으로 할당해 여러 서버 역할을 한 물리 머신에 통합한다. 물리 서버를 기능마다 사는 것보다 자본지출(CAPEX)을 절감하고 중앙 집중 관리와 증설을 쉽게 할 수 있다. 다만 PCI 슬롯 같은 물리적 증설 한계는 남는다. 클라우드 인프라는 스토리지·계산·분산 콘텐츠 서버와 네트워크(라우터·스위치·AP 등)의 자원 풀을 가상화해 다수 사용자에게 제공한다. 가상화 대상에 따라 서버·데스크톱·애플리케이션·하드웨어 가상화로 분류한다. 교수 설명상 가상 스토리지 할당량은 물리 디스크 크기와 일대일로 같을 필요가 없고, 실제 용량보다 크게 할당할 수도 있다. [00:03:12]–[00:10:11]

#### 하이퍼바이저의 기준과 유형

하이퍼바이저의 세 요구사항은 ① 충실도(fidelity): VM의 OS·애플리케이션이 물리 머신에서와 동일하게 작동(성능 차이는 가능) ② 안전한 격리(isolation): VM 간 및 게스트와 호스트 간 무단 접근 방지 ③ 성능(performance): 계층을 거치며 발생하는 오버헤드 최소화다. [00:10:46]–[00:14:23]

타입 1(네이티브/베어메탈)은 호스트 OS 없이 하드웨어 위에서 직접 실행되어 게스트 OS를 관리한다. 타입 2는 기존 Linux·Windows·macOS 호스트 OS 위에서 일반 애플리케이션처럼 실행된다. 강의 설명상 타입 1은 타입 2보다 오버헤드가 작지만 0은 아니며, 타입 2는 일반 사용자가 설치·관리하기 편리한 대신 호스트 OS 계층이 하나 더 있다. 타입 1 예로 Xen, KVM, VMware ESXi, Proxmox가 언급된다(일부 자막 발음 불명확). 타입 2 예는 VMware Workstation, VirtualBox, macOS용 Parallels다. #### 가상화 방식과 CPU 권한 실행

가상화 방식은 풀 가상화, 반가상화, 하이브리드, OS 레벨로 소개된다. OS 레벨은 Docker 같은 컨테이너 방식이며 이번 강의의 상세 대상에서는 제외한다. 풀 가상화는 게스트 OS를 수정하지 않고 하드웨어를 완전히 가상화하여 게스트가 VM에서 실행되는지 인지하지 못하게 한다. 하드웨어 CPU가 가상화를 지원하면 성능 오버헤드가 줄어든다. 소프트웨어 기반 구현은 명령을 처리·변환하는 부담이 더 크다. Intel VT 계열과 AMD 가상화 지원 CPU가 언급되나 AMD 약어는 자막 확인이 필요하다. [00:18:39]–[00:23:34]

반가상화는 게스트 OS, 특히 커널을 수정해 하이퍼바이저와 직접 통신한다. 일반 시스템 콜 대신 하이퍼콜(hypercall)을 사용하도록 바꾸므로 하이퍼바이저가 매번 명령을 가로채 변환하는 부담을 줄여 성능을 높일 수 있다. 대신 게스트 수정이 필요하고 호환성이 낮다. Xen이 사례다. Xen은 링 0에서 하드웨어 접근을 제어하는 오픈소스 하이퍼바이저로 설명되며, 고성능 실행과 게스트 OS 수정 요구가 함께 언급된다. [00:23:38]–[00:28:42]

권한 링은 숫자가 낮을수록 권한이 높다. 링 0은 커널/최고 권한으로 시스템 제어와 특권 명령 실행이 가능하고, 링 3은 일반 애플리케이션 권한이다. 교수 설명상 링 1·2도 개념상 있지만 Linux에서는 주로 0·3을 쓴다. 일반 OS의 듀얼 모드에서 사용자 모드 애플리케이션은 하드웨어에 직접 접근하지 못한다. 시스템 콜이 트랩을 일으키면 모드 비트가 커널 모드로 전환되고, 작업 후 사용자 모드로 복귀한다. 가상화 환경에서는 게스트가 보는 커널이 가상 커널이므로, 게스트의 특권 동작은 실제 하드웨어로 바로 이어지지 않는다. 설명된 처리 순서는 게스트 요청 → VM exit → 하이퍼바이저의 트랩 처리·에뮬레이션 → 필요한 호스트 자원 작업 → VM entry를 통한 게스트 복귀다. 하이퍼바이저 관점에서 게스트 OS는 논루트 모드에서 도는 대상으로 볼 수 있다. 강의는 가상화 보안 위협을 공격 벡터 기준으로 하이퍼바이저 기반, VM 이미지 기반, VM 기반 공격으로 나누어 개관한다. 가상화 기술의 등장으로 새롭게 생긴 공격과, 원래 존재했지만 가상화 환경에도 피해를 주는 일반 공격을 구분한다. 새 위협의 예로 VM Escape, Hyperjacking, VM Sprawl, Cross-VM Side-Channel Attack을 든다. 공격이 VM 안에서 시작되는지 바깥에서 시작되는지를 나타내는 Inside VM/Outside VM 구분도 소개하며, 이는 공격 유형 그 자체라기보다 범주를 나타내는 표현으로 설명한다. (00:00:00–00:04:30)

- **VM Escape(가상머신 탈출)**: VM 내부 애플리케이션을 침해한 뒤 VM 격리 경계를 넘어 하이퍼바이저나 호스트·물리 시스템에 접근하는 공격이다. VM 안에서 출발해 격리 경계를 넘는다는 점이 핵심이다. (00:01:02–00:01:49, 00:10:00–00:11:22)
- **Hyperjacking(하이퍼재킹)**: 호스트 OS 등을 먼저 침해해 하이퍼바이저의 제어 권한을 빼앗고 가상화 환경을 장악하는 공격이다. 강의는 VM Escape와 달리 공격자가 VM 내부가 아니라 외부 호스트 측에서 시작한다고 구분한다. (00:01:55–00:02:28, 00:32:15–00:34:30)
- **VM Sprawl(스프롤)**: 적절한 관리·감독 없이 VM이 급격히 많이 생성되어 통제되지 않는 상태다. 의도적 공격이 될 수도 있지만, 강의에서는 주로 관리·운영상 문제로 설명한다. (00:02:28–00:02:45, 00:51:45–00:53:30)
- **VM Footprint**: 대상 VM의 게스트 OS와 버전, 제공 중인 서비스, VMware 환경 등 VM 관련 정보를 알아내는 정찰·정보수집 행위로 소개한다. (00:02:45–00:03:18)
- **Cross-VM Side-Channel Attack(교차 VM 부채널 공격)**: 공유 하드웨어 자원에서 발생하는 부수적 신호를 관찰해 다른 VM의 비밀정보를 추론·유출한다. 직접 침투하거나 시스템을 손상시키지 않는 수동적 공격이어서 탐지가 어렵다. (00:04:27–00:05:17, 01:00:00–01:03:15)
- **패치되지 않은 게스트 OS·소프트웨어**: VM 안의 게스트 OS도 일반 OS와 같으므로 오래되었거나 패치가 빠진 OS·패키지가 공격 표면이 된다. 사용자는 업데이트를 지속하고, 복구를 위해 하이퍼바이저의 스냅샷 기능을 주기적으로 활용할 수 있다고 설명한다. (00:06:29–00:07:54)

VM은 하이퍼바이저를 통해 물리 하드웨어 자원을 공유하므로 하나의 VM 침해가 그 VM만의 문제로 끝나지 않을 수 있다. 같은 물리 서버의 다른 VM이나 하이퍼바이저로 공격이 확산될 수 있으며, 특히 여러 고객이 한 클라우드 기반을 공유하는 멀티테넌트 환경에서는 고객 간 격리와 신뢰가 걸려 있어 파급력이 크다. 강의는 Confidential VM(CVM)도 VM 자체를 더 안전하게 만들려는 기술로 언급하지만, 해당 슬라이드 표현은 자막상 확인되지 않는다. (00:08:01–00:09:52)

#### 2. VM Escape의 과정, 영향 및 방어

정상적인 가상화에서는 게스트 OS의 명령이 하이퍼바이저로 전달되고, 하이퍼바이저가 이를 처리해 하드웨어 자원에 접근한다. VM Escape는 취약점을 이용해 이 격리 경계를 넘고 하이퍼바이저·호스트 측으로 접근하는 것이다. 강의 도식 설명에서는 게스트 VM에서 하이퍼바이저로 향하며 호스트 OS를 우회하는 경로를 제시한다. 성공하면 시스템 정보를 훔치거나 호스트 자원·다른 VM에 접근할 수 있다. (00:10:00–00:11:30)

강의에서 설명한 공격 흐름은 다음과 같다. 이는 공격 절차에 대한 강의 설명을 요약한 것이며, 단계명을 자막의 표현에 맞춰 정리했다. (00:11:34–00:14:47)

1. **초기 정찰**: 현재 실행 지점이 게스트 OS 안인지 확인하고, 하이퍼바이저 종류·버전을 식별하며, 호스트와 통신하는 채널을 조사한다. 네트워크 도구가 이용될 수 있다고 설명한다.
2. **취약점 조사**: 하이퍼바이저 구성요소를 분석한다. 오픈소스는 코드를 직접 분석하는 방식, 클로즈드소스는 역공학을 활용하는 방식으로 설명하며, 메모리 손상 가능 지점 등을 찾는다.
3. **익스플로잇 개발**: 발견한 취약점을 작동시키는 입력·코드를 만든다. ROP(Return-Oriented Programming)·JOP(Jump-Oriented Programming) 체인, 버퍼 오버플로와 메모리 입력 조작을 예로 든다. ASLR 같은 보안 완화 기법을 우회하는 개발도 언급한다.
4. **권한 상승**: 침해를 이용해 더 높은 권한, 예컨대 루트나 호스트 시스템 권한을 얻는다.
5. **침해 후 활동**: 확보한 권한으로 호스트 자원이나 다른 VM에 접근하고, 추가 침투를 위해 백도어를 설치할 수 있다.

VM Escape의 결과로는 호스트 시스템 장악, 다른 VM에 대한 접근 및 수평 이동, 데이터 침해와 기밀성 손실, 서비스 중단·DoS, 자원 탈취형 크립토재킹, 멀티테넌트 격리 및 규정 준수 위반, 고객 신뢰 상실을 든다. 호스트 수준의 지속성 확보 뒤에는 하이퍼바이저 수준 악성코드·백도어·루트킷 설치, 보안 도구 종료·탐지 회피, 로그 조작, 다른 물리 머신으로 확장되는 연쇄 공격(APT의 발판)이 가능하다고 설명한다. (00:15:01–00:20:00)

강의는 VM Escape 관련 취약점 사례로 VENOM(QEMU의 버퍼 오버플로, 2015년), VMware Workstation·ESXi의 메모리 관련 취약점(2018년), VirtualBox의 정수 언더플로우 등(2019년), AMD CPU를 사용하는 Linux KVM 구현에서의 레이스 컨디션(2021년)을 든다. 각 취약점의 정확한 식별번호는 강의에서 제시·판독되지 않아 여기서는 적지 않는다. (00:20:45–00:23:00)

방어는 하이퍼바이저의 최신 보안 패치 유지, 불필요한 가상 장치·기능 비활성화, 꼭 필요한 기능만 설치·사용하는 강화(hardening)에서 시작한다. VM 구성에서도 불필요한 하드웨어를 빼고 최소 권한 원칙을 적용한다. 교수는 최소 권한을 Zero Trust와 연결해 설명한다. Zero Trust는 기본적으로 누구도 신뢰하지 않고, 실제로 필요한 기능·권한만 최소 단위로 허용한다는 취지다. 가상 네트워크를 보수적으로 구성하고, 불필요한 게스트 추가 기능을 끄며, VPC 등에서 VM 간 네트워크 세그멘테이션을 세밀하게 해야 침해 후 다른 VM으로의 확산을 제한할 수 있다. VM 간 통신 패턴 모니터링, RBAC(Role-Based Access Control), 최소 권한, 다단계 인증도 제시한다. (00:23:00–00:27:47)

운영 차원의 모범 사례로 자동화된 패치 관리와 공급업체 보안 권고 추적, 정기 취약점 평가, 심층 방어(Defense in Depth), EDR(Endpoint Detection and Response) 및 하이퍼바이저를 인식하는 보안 도구의 배치, 로그 수집·분석을 든다. 예방 통제를 과도하게 적용하면 오버헤드가 커질 수 있으므로 현실적으로는 탐지를 빠르게 해 사후 대응하는 접근도 설명한다. 정상 트래픽·로그의 패턴에서 벗어나는 이상 징후를 AI로 탐지하는 시스템을 예로 들지만 정확도 문제도 남는다고 덧붙인다. 사고 시 해당 VM을 즉시 종료할지, 격리된 전용 머신으로 옮겨 관찰할지 등 대응 절차를 미리 정해야 한다. 아키텍처 차원에서는 Zero Trust 원칙, CVM과 하드웨어 기반 보호, 고보안 워크로드의 베어메탈 배치를 언급하며, 베어메탈은 비용이 더 들 수 있다고 설명한다. (00:27:47–00:32:15)

#### 3. Hyperjacking의 경로, 영향 및 방어

Hyperjacking은 외부 공격자가 호스트 OS를 침해하고 권한을 높인 뒤 하이퍼바이저의 관리·제어 권한을 장악해, 그 위의 VM 전체를 통제하는 공격이다. 하이퍼바이저를 장악하는 것을 일반 OS의 루트 권한 획득에 비유한다. 교수 설명에 따르면 호스트 OS 취약점이 진입점이어서 VMware Workstation·VirtualBox 같은 호스티드 Type 2 가상화가 주요 대상이며, 호스트 OS가 손상되면 그 위에서 동작하는 하이퍼바이저도 위험해진다. (00:32:15–00:34:45)

공격 과정은 ① 호스트 OS 정찰·접근(포트 스캔, OS·버전·취약점 조사, 관리자 대상 피싱·사회공학 등) ② 호스트 OS 권한 상승과 지속성 확보(강의에서는 Windows 레지스트리 수정·예약 작업 등을 예로 들며, 탐지 회피용 루트킷도 언급) ③ 설치된 하이퍼바이저의 종류, 구성 파일·인터페이스·로그 위치 조사 ④ 구성 파일 변경, 악성 모듈·드라이버 설치 또는 인터페이스 가로채기를 통한 침해·제어 ⑤ VM 통신·데이터 흐름 모니터링, VM 생성·중지·이동·차단 등 환경 조작으로 정리된다. (00:34:45–00:38:30)

VM Escape와의 비교에서 교수는 진입점·경로를 핵심 차이로 설명한다. Hyperjacking은 외부에서 호스트 OS 취약점을 타고 들어가며 주로 Type 2를 대상으로 하고, VM Escape는 게스트 VM 내부에서 가상 장치 등의 취약점을 타고 나와 Type 1·Type 2 모두에 해당할 수 있다고 설명한다. VM Escape의 활동은 하이퍼바이저 수준에서 일어나 탐지가 더 어려울 수 있는 반면, Hyperjacking은 먼저 호스트 OS에 침투해야 하므로 호스트의 보안 소프트웨어에 탐지될 여지가 상대적으로 더 있다고 강의에서 비교한다. 영향 범위는 VM 단일 또는 호스트 접근에서 전체 가상화 환경 제어까지 커질 수 있다. (00:38:30–00:40:45)

하이퍼재킹의 영향은 포괄적 인프라 제어, 여러 VM의 연쇄 침해, 멀티테넌트 격리 붕괴, 하이퍼바이저 로그·감사 정보 조작에 따른 포렌식 곤란, 서비스 중단, VM을 무분별하게 만들어 자원 고갈, 오케스트레이션 도구 침해, 데이터 유출·스파이 활동, 장기간 은밀한 APT, 규정 위반, 공급망·신뢰 모델 침해, 백도어 설치 등이다. 교수는 개인 PC 침해와 달리 클라우드 가상화 기반을 장악하면 그 인프라를 공유하는 다수 테넌트가 함께 영향을 받을 수 있어 피해 규모가 커진다고 강조한다. (00:40:16–00:45:00)

사례로 2021년 Apache Log4j의 Log4Shell, VMware vCenter Server 원격 코드 실행(RCE), 2020년 Windows 권한 상승 취약점(자막상 “제로록”), 2019년 Pulse Secure VPN 장비의 코드 실행 취약점, 2017년 Spectre 관련 사례를 든다. 교수는 Log4Shell과 vCenter RCE를 하이퍼재킹 위험을 설명하는 취약점 사례로 언급한다. 연도·영향 관계는 강의 설명에 귀속하며, 일부 이름이나 CVE 식별번호가 자막에서 분명하지 않으므로 원문 확인 대상으로 둔다. (00:45:46–00:47:45)

대응은 호스트 OS 보안 강화와 패치, EDR 배치 및 정기 취약점 점검, 하이퍼바이저 권한의 세분화·최소화, 계정별 필요한 권한만 부여하는 최소 권한 원칙, 위협 모니터링과 로그 관리, 심층 방어 아키텍처 및 Zero Trust를 포함한다. 추가 모범 사례로 관리자 보안 인식 교육, 하이퍼바이저 인식 모니터링, IAM 권한의 실시간 점검, 안전한 백업·복구 절차를 든다. 침해를 가정한 대응 계획에서는 중요한 VM을 우선 안전한 호스트로 신속하게 마이그레이션하는 선택지를 준비한다. (00:48:01–00:51:45)

#### 4. VM Sprawl의 원인, 영향 및 관리

VM Sprawl은 가상머신이 통제되지 않은 채 급증하는 현상이다. 공격자가 의도적으로 만들 수도 있지만, 강의에서는 보통 감독·수명주기 관리의 부재에서 생기는 운영 문제로 설명한다. 핵심 영향은 CPU·메모리·저장공간·네트워크 처리량 등 자원의 낭비이며, 클라우드에서는 사용량이 비용으로 이어져 불필요한 지출을 키운다. 시스템·서버 스프롤은 IT 시스템 또는 물리 서버가 통제 없이 확산되는 더 넓은 현상으로 함께 설명한다. (00:51:45–00:53:30)

구체적 예시는 테스트·개발용으로 임시 생성한 VM을 작업이 끝난 뒤 삭제하지 않고 방치하는 경우다. 애플리케이션이 Ubuntu 24.04, 22.04, 20.04, 18.04 등 여러 OS 버전에서 실행되는지 확인하려고 VM을 여럿 만들 수 있는데, 각 VM을 회수하지 않으면 백그라운드에서 자원과 비용을 계속 소비한다. (00:53:30–00:54:30)

VM Escape와 비교할 때 VM Sprawl은 하이퍼바이저·가상 장치 취약점을 이용하는 침해 공격과 성격이 다르며, 주된 문제는 자원 낭비와 관리 복잡성이다. 교수는 스프롤을 보통 그 자체로 명확한 공격이라기보다 관리 문제라고 구분한다. 자원 사용량이 설명 없이 급증하거나 예측 범위를 벗어나면 모니터링으로 탐지할 수 있다고 한다. (00:54:30–00:55:45)

VM 수가 많아질수록 구성·업데이트 추적, 보안 패치와 취약점 관리, 모니터링 및 사고 대응이 어려워진다. 자동화가 없으면 수십·수백·수천 VM을 수작업으로 관리하기 어렵고, 이상 활동 감지 지연은 피해와 비용을 키울 수 있다. 프라이빗 클라우드에서는 라이선스·전력·냉각 비용도 부담이 된다. 대응의 중심은 지속적·실시간 자원 모니터링, VM별 목적에 따른 예상 사용량 기준 설정, 기준 이탈 탐지, VM 생성부터 회수·폐기까지의 수명주기 관리다. 패치·접근통제·인증 등 기본 관리도 병행한다. (00:55:45–01:00:00)

#### 5. Cross-VM Side-Channel Attack의 원리와 방어

교차 VM 부채널 공격은 같은 물리 자원을 공유하는 VM 간에 발생하는 간접 정보 유출이다. 공격 VM이 목표 VM에 직접 침투하거나 코드를 실행하지 않고, 공유 자원의 사용 흔적을 관찰해 암호 키·비밀번호·사용자 정보 등 민감 데이터를 추론한다. 이런 수동적(passive)·은밀한 공격은 기존 모니터링이 놓치기 쉽다. 멀티테넌트 환경에서 제3자 데이터에 접근하게 되어 기밀성 및 격리 보장을 침해하고, 클라우드 제공자에 대한 신뢰를 훼손할 수 있다. (01:00:00–01:04:46)

강의에서 든 관찰 채널은 다음과 같다. (01:04:46–01:07:50)

- **캐시 기반**: CPU 캐시의 공유·경합 양상을 관찰해 다른 VM의 동작·데이터를 추론한다.
- **메모리·네트워크 기반**: 메모리 버스나 네트워크 동작에서 나타나는 신호를 분석한다.
- **가상 스위치·타이밍**: 하이퍼바이저의 가상 스위치를 오가는 타이밍을 살펴 다른 VM의 데이터 사용 양상을 짐작한다.
- **성능·자원 관찰**: CPU 스케줄링, 성능 카운터, CPU·메모리 사용량, 지연시간(latency) 등을 측정해 정보를 추론한다.
- **전력 소비 패턴**: 자원 사용·전력 패턴을 비교해 실행 중인 하이퍼바이저 종류나 버전을 식별할 수 있다는 예를 든다. 강의 예에서는 VMware Workstation과 VirtualBox가 서로 다른 사용·지연 패턴을 보일 수 있다고 설명한다.

방어의 중심은 하드웨어·VM 간 파티셔닝과 강한 격리다. 추가로 자원 사용 양상을 무작위화하고 노이즈를 주입해 공격자의 추론을 어렵게 만들 수 있다. 민감도에 맞춰 더 안전한 물리 머신에 VM을 배치하고, 중요 데이터는 암호화하며 키를 안전하게 관리한다. 암호화는 성능 오버헤드를 낼 수 있지만 정보 유출 위험과 비교해 선택해야 한다고 설명한다. 하드웨어 기반 격리, 보안이 강화된 하이퍼바이저, 모니터링·탐지도 권고하며, 교수는 여러 대책 가운데 격리가 특히 중요하다고 반복한다. (01:07:50–01:10:22)

#### 6. VM Migration의 활용, 위협 및 보호

VM Migration은 한 물리 호스트에서 다른 호스트로 VM을 옮기는 과정이다. VM이 실행 중인 채 옮기면 **Live Migration**, 전원이 꺼진 상태에서 옮기면 **Cold Migration**이다. 부하 분산과 워크로드 재배치에 쓰이며, 침해가 의심되는 VM을 안전한 곳으로 옮기는 사후 대응, 재해 복구와 비즈니스 연속성에도 활용될 수 있다. (01:10:22–01:11:52)

이동 중의 공격 표면은 세 부분으로 설명된다. ① 관리 통신·오케스트레이션을 겨냥하는 제어 영역(control plane), ② 전송 중 VM 메모리·상태 정보를 가로채는 데이터 영역, ③ 마이그레이션 모듈 자체다. 대표 공격은 다음과 같다. (01:11:55–01:13:30)

- **마이그레이션 하이재킹**: 공격자가 VM 이동을 가로채 안전하지 않거나 악성인 호스트로 보낸다. 겉으로는 이동이 성공한 듯 보여도 실제 목적지가 손상되었을 수 있다.
- **마이그레이션 도청(eavesdropping)**: 전송 트래픽을 수동적으로 분석해 VM 정보나 암호 키 등 민감 정보를 엿본다.
- **강제·무단 마이그레이션 또는 중단, 서비스 거부(DoS)**: 자원 고갈·네트워크 플러딩 등으로 전송을 늦추거나 방해하고, 데이터 손상으로 이어질 수 있다. 공격명 일부는 자막이 불명확하다.

대응책은 모든 마이그레이션 트래픽의 종단 간 암호화(TLS 예시), 양 끝점의 강력한 인증·접근 제어, 이동 경로의 네트워크 보안·격리, 전송 중 악성 행위 모니터링 및 규정 준수 점검이다. 핵심은 제어 영역과 데이터 전송을 함께 보호하고, 허가된 출발지·목적지 사이에서만 이동하도록 관리하는 것이다. (01:14:08–01:15:17)

### 교수 강조 사항

- VM 하나의 침해가 같은 하이퍼바이저·물리 서버의 다른 VM으로 확산될 수 있으며, 멀티테넌트 클라우드에서는 다수 고객의 데이터·서비스에 영향을 주므로 VM 격리는 핵심 보안 경계다. (00:09:00–00:09:52, 00:16:00–00:18:16)
- VM Escape는 게스트 VM 내부에서 시작해 격리 경계를 넘고, Hyperjacking은 호스트 OS 쪽에서 시작해 하이퍼바이저 제어권을 빼앗는다는 차이를 구분할 것. (00:32:15–00:34:30, 00:38:30–00:40:00)
- 최소 권한 원칙·Zero Trust, 세분화된 네트워크 격리, 하이퍼바이저·호스트 OS의 지속적 패치와 모니터링을 여러 대응에서 반복해서 강조한다. (00:24:15–00:27:47, 00:48:01–00:50:31)
- VM Sprawl은 취약점 기반 침해와 같은 공격 유형이라기보다 관리 실패로 생길 수 있는 통제되지 않은 확산이며, 비용·자원 낭비와 패치·대응의 복잡성을 낳는다. 자원 모니터링과 사용 목적·예상량 설정, 수명주기 관리가 중요하다. (00:51:45–00:55:45, 00:58:00–01:00:00)
- 교차 VM 부채널 공격은 직접 침투가 없는 수동 공격이라 탐지가 특히 어렵고, 강의가 가장 중요하게 꼽은 방어는 격리·파티셔닝이다. (01:02:16–01:04:15, 01:07:50–01:10:22)
- VM 이동은 운영·복구에 유용하지만 전송 중 제어 영역, 데이터, 모듈이 각각 공격받을 수 있다. 암호화, 강한 인증, 네트워크 격리와 모니터링을 갖춰야 한다. (01:11:55–01:15:17)
- 강의 중 “교과서적인 내용”이라고 짧게 언급한 패치·보안 구성·모니터링 등은 중요도를 낮춘다는 뜻이 아니라 기본 방어를 반복 적용하라는 맥락으로 정리했다. 교수는 별도의 시험 출제 예고를 하지 않았다.

### 확인이 필요한 부분

- 취약점 사례의 CVE 고유 식별번호는 자막에 나오지 않거나 판독할 수 없어 기록하지 않았다. VENOM, VMware·VirtualBox·Linux KVM 사례의 정확한 번호와 일부 세부 취약점 설명은 원문 슬라이드 확인이 필요하다. (00:20:45–00:23:00)
- Hyperjacking 사례 중 Windows 권한 상승 취약점 명칭은 자막에 “제로록”으로 들린다. 정확한 고유명사와 강의 슬라이드의 표기를 확인할 필요가 있다. (00:47:00–00:47:30)
- Pulse Secure VPN·Spectre 사례는 Hyperjacking과의 구체적 연결 및 취약점 식별번호가 자막만으로 충분히 특정되지 않는다. 교수의 사례 언급으로만 기록했다. (00:47:16–00:47:45)
- VM Escape·Hyperjacking 비교 슬라이드의 표 일부(예시 아키텍처·탐지 난이도 등)는 교수의 구두 설명만 남아 있어 표의 정확한 열 제목과 표현은 슬라이드 확인이 필요하다. (00:38:30–00:40:00)
- 마이그레이션 공격 중 세 번째 공격명은 자막상 “퍼스트 마이그레이션”처럼 들리며 뜻이 불명확하다. 본문에는 무단 마이그레이션·중단 및 DoS라는 설명만 반영했다. (01:13:15–01:14:08)
- 강의 말미 01:15:24 이후는 수업 종료 발화 뒤 자막이 훼손되어 의미를 확인할 수 없다. 본문 요약에서 제외했다. (01:15:17–01:15:50)

### 자가 점검 문항

아래 문항은 요약 내용을 복습하기 위해 새로 만든 문제이며, 교수의 출제 예고나 실제 시험문제가 아니다.

1. VM Escape와 Hyperjacking의 시작 위치와 주요 침해 경로는 어떻게 다른가?  
   **답:** VM Escape는 게스트 VM 내부에서 시작해 취약점을 이용해 격리 경계를 넘는다. Hyperjacking은 외부에서 호스트 OS를 침해하고 권한을 높여 하이퍼바이저 제어권을 장악한다. (00:32:15–00:34:30)
2. VM Escape가 멀티테넌트 클라우드에서 특히 위험한 이유는 무엇인가?  
   **답:** VM들이 같은 하이퍼바이저와 물리 자원을 공유하므로 한 VM 침해가 다른 VM·테넌트로 확산되어 정보 유출, 서비스 중단, 격리·신뢰 위반을 일으킬 수 있기 때문이다. (00:09:00–00:09:52, 00:16:00–00:18:16)
3. VM Sprawl을 침해 공격과 구분하고, 핵심 관리책 두 가지를 말하라.  
   **답:** 스프롤은 흔히 관리 부실로 VM이 통제 없이 늘어나는 현상이며, 핵심은 자원 사용량의 지속 모니터링과 목적이 끝난 VM을 회수하는 수명주기 관리다. (00:51:45–00:55:45, 00:58:00–01:00:00)
4. 교차 VM 부채널 공격이 수동적이고 탐지하기 어려운 이유는 무엇이며, 강의가 우선 강조한 방어는 무엇인가?  
   **답:** 직접 침투·코드 실행 없이 캐시·메모리·타이밍 등 공유 자원의 흔적만 관찰해 정보를 추론하므로 눈에 띄는 손상을 남기기 어렵다. 핵심 방어는 VM·하드웨어 자원의 강한 격리와 파티셔닝이다. (01:02:16–01:04:15, 01:07:50–01:10:22)
5. Live Migration과 Cold Migration의 차이 및 이동 중 대표 위험 하나를 설명하라.  
   **답:** Live는 VM이 실행 중인 상태에서, Cold는 VM을 끈 상태에서 이동한다. 전송 중에는 하이재킹으로 악성 호스트에 보내거나 도청으로 민감 정보를 빼내는 위험 등이 있다. (01:10:22–01:11:03, 01:12:20–01:13:15)
