# 클라우드보안 5강 클라우드 보안 구현 사례와 제로트러스트·클라우드 네이티브

## 전체 내용

### 1. 클라우드 운영에서 발생하는 실수와 계정 악용

클라우드 콘솔에서는 몇 번의 조작으로 중요 리소스를 삭제할 수 있고, 보안 그룹이나 버킷 권한 설정이 잘못되면 데이터가 웹에 공개될 수 있다. 강의의 화면 사례는 중지된 서버만 정리하려던 사용자가 정상 운영 중인 서버까지 함께 삭제한 상황이다. 교수는 클라우드 콘솔 UI가 사용 편의에 초점을 맞추어 설계되어 실수를 막아 주지 않으며, 체크박스 하나의 오조작도 프로덕션 서버 삭제로 이어질 수 있다고 설명했다. 삭제 대응에는 ① 최소 권한에 따른 삭제 권한 제한 및 중요 리소스의 추가 승인, ② 제공자 기능(예: EC2 삭제 방지 기능)과 자동 스냅샷·백업 활용, ③ 보안 설정이 계속 유지되는지와 새 리소스에도 적용되는지 정기 점검, ④ 클라우드 환경에 맞춘 삭제·복구·백업 사고 대응 절차가 필요하다. (00:00:09–00:04:00)

계정 위험은 내부 직원의 리소스 남용·오용(개인 목적 사용, 권한 남용에 따른 비용)과 외부 공격자의 계정 탈취 후 리소스 남용·정보 유출로 나뉜다. 사례에서는 사용자가 AWS 접근 자격 증명을 CSV에 저장하고, 이를 피싱·악성코드·취약한 시스템을 통해 탈취한 공격자가 자격 증명으로 EC2 인스턴스를 다수 생성해 외부 서버와 통신시키며 채굴 등 악의적 활동에 쓴다. CLI/API와 자동화 스크립트를 이용하면 수십~수백 대가 빠르게 만들어지고, 회사는 다음 달 청구서를 받고서야 알아차릴 수 있다. 대응은 장기 유지 액세스 키 사용을 최소화하고 임시 토큰·역할 기반 접근을 택하며 루트 계정 사용을 억제하는 것, 콘솔 MFA·강한 암호 정책·API 접근 제한, 사용자 추가나 권한 변경 시 보안 설정 재점검, 계정별 리소스 사용량과 접근 위치·이상 패턴의 실시간 감사 및 경보를 포함한다. 평소 서울에서 접속하던 계정이 갑자기 해외에서 접속하면 알림을 발생시키는 예가 제시됐다. 강의는 보안 조치를 다섯 가지라고 예고했지만 실제 자막에서 번호가 분명히 드러나는 항목은 네 묶음이다. (00:04:02–00:08:39)

### 2. 전통적인 경계 보안에서 예측·행동 기반 보안으로

전통적 캐슬(성곽) 모델은 중요한 정보를 중심으로 성벽·성문·내부 방어선을 쌓는다. 방화벽, 침입 방지·탐지 시스템, 서버 보안, 데이터 암호화 등으로 층층이 보호하며 알려진 공격 패턴·시그니처를 찾아 차단하고, 통제된 공간·장비·인원만 접근시키는 방식이다. 이에 비해 클라우드 보안의 지향점은 공격 후 차단에 그치지 않고 위험을 미리 감지·예측해 선제 대응하며, 사고가 발생한 경우에도 실시간 분석·시각화로 담당자가 상황을 이해하고 대응하도록 돕는 것이다. AI 기반 행동 분석은 사용자·엔드포인트·네트워크의 정상 행태를 학습해 알려지지 않은 공격도 찾으려 한다. 예를 들어 평소 오전 9시 서울에서 접속하던 사용자가 새벽 3시 영국에서 로그인하거나, 평소보다 많은 데이터를 내려받거나 접근하지 않던 시스템에 접속하면 이상 징후로 볼 수 있다. (00:09:10–00:12:50)

교수는 예측 보안을 VIA 세 요소로 설명했다. 가시성(Visibility)은 로그를 모으는 데서 그치지 않고 빅데이터 분석·BI·시각화를 통해 위협과 보안 수준을 유의미한 정보로 드러내는 것, 인텔리전스(Intelligence)는 통계·예측 모델·머신러닝·딥러닝 등으로 오류와 분석 지연을 줄이고 로그인·데이터 접근 이상을 분석·예측하는 것, 자동화(Automation)는 위험이 예측되거나 발생했을 때 보호 조치를 지연 없이 실행하는 것이다. 로보틱 프로세스 자동화, 소프트웨어 정의 경계, SOA 등이 예로 언급됐다. 가시성이 지능 분석의 기반이고 지능 분석이 효과적 자동화를 가능하게 하므로 세 요소는 연결되어야 한다. (00:12:50–00:15:07)

현대 클라우드 보안 기술·접근으로 제로트러스트 아키텍처, AI/머신러닝 위협 탐지, 클라우드 네이티브 애플리케이션 보안(CNAPPs로 들리는 약어), 개발·보안·운영 통합(DevSecOps로 들리는 표현), 지속적 모니터링·평가가 소개됐다. 교수는 모든 기술의 성숙도가 같지 않으므로 도입 전 성숙도와 현실 적용 가능성을 평가해야 한다고 강조했다. 가트너 하이프 사이클은 혁신 초기 기술은 위험 부담이 커 파일럿에 적합하고, 가치가 입증되어 안정 운영되는 기술도 구분하며, 성숙까지 걸리는 기간(예: 2년 이내 또는 10년 이상)을 고려해 단기·장기 보안 전략을 세우는 참고 자료로 설명됐다. (00:15:07–00:18:54)

### 3. 경계 기반 보안의 구조와 한계

교수는 기존 군사 환경의 C4I 아키텍처 같은 체계적 접근을 클라우드에 참고할 수 있다고 소개하고, 클라우드 보안 영역을 위험 관리, 접근 제어, 네트워크 보안, 데이터 보안, 가상화 보안의 다섯 도메인으로 정리했다. 위험 관리는 전체 위험 평가·관리, 접근 제어는 사용자와 시스템의 권한 관리, 네트워크 보안은 클라우드 네트워크 보호를 뜻한다. 데이터·가상화 보안과 클라우드 공통 위협 대응도 별도 보호 대상이라고 덧붙였다. C4I의 정확한 명칭·도식과 도메인 세부 분류는 슬라이드 대조가 필요하다. (00:19:01–00:21:06)

전통적 경계 보안은 인터넷→방화벽→DMZ→네트워크 스위치→내부 시스템의 단계적 구조다. 방화벽은 외부 악성 트래픽을 막는 첫 관문, DMZ는 외부 제공 웹 서비스 등을 두는 완충 구역, IDS는 네트워크 트래픽을 감시하는 침입 탐지 시스템이다. 핵심 가정은 “외부는 위험하고 내부는 안전하다”는 것이다. 따라서 투자는 경계 강화에 집중되고, 내부 사용자·서버 사이 통신은 별도 검증이 약해진다. 공격자가 경계를 한 번 넘으면 내부 이동·확산이 쉬워지는 것이 구조적 약점이다. (00:21:06–00:23:37)

클라우드와 원격 근무로 이 모델의 경계는 흐려졌다. Work From Anywhere, 재택·모바일·태블릿·협력사 접근으로 사무실 네트워크 안팎의 구분이 약해졌고, 리소스는 AWS·Azure·Google Cloud와 전 세계 지사에 분산됐다. IoT 센서와 스마트 기기도 늘어 통제 가능한 단말이라는 전제가 무너졌다. 내부망에 있다는 사실만으로 안전하다고 할 수 없으며 재택 환경이나 협력사를 통해 침입할 수도 있다. (00:23:53–00:26:44)

교수는 경계 모델의 한계를 보여주는 사례로 미국 동부 연료 공급의 약 45%를 담당하는 파이프라인 랜섬웨어 공격(5일 중단, 연료 공급 혼란·가격 상승)을 들었고, 미국 의료 시스템의 약 3분의 1을 처리하는 의료 인프라가 마비되어 병원이 수작업으로 전환하고 환자 치료에 차질이 생긴 사례도 언급했다. 랜섬웨어 공격자는 초기 진입 뒤 내부 시스템을 옮겨 다니며 권한을 넓히고 가능한 많은 시스템을 감염시키려 한다. 자격 증명을 이용해 정상 사용자처럼 들어오거나 소프트웨어 공급망의 정상 업데이트 경로를 악용하면 방화벽·침입 탐지에서 구분하기 어렵다. 강의는 Colonial Pipeline으로 추정되는 파이프라인 사례와 의료 사례의 이름·세부 사실을 자막만으로 확정하지 않으므로 교수 설명으로 귀속한다. (00:26:44–00:31:18)

SolarWinds는 공급망 공격 사례로 제시됐다. 배포되는 소프트웨어에 악성 요소가 들어가면 정상 업데이트와 악성 행위를 경계 장비가 구분하기 어렵고, 설치 후 수개월 동안 탐지되지 않을 수 있다. 내부 시스템을 안전하다고 간주하는 전제가 문제다. 내부자 위협도 경계 보안에 취약하다. 원격 접속·다중 클라우드·분산 업무로 감시 범위가 커지고 로그가 방대해져 비정상 행위를 찾기 어려우며, 악의적 행동의 명확한 정의와 여러 관점의 상관관계 분석도 부족할 수 있다. (00:29:16–00:32:22)

교수가 정리한 경계 모델의 여섯 결함은 ① 내부망 안전 가정에 따른 묵시적 신뢰, ② 신뢰/불신만 나누는 이분법, ③ 경계 침해 후 측면 이동(Lateral Movement) 허용, ④ 내부 활동 모니터링 부족, ⑤ 내부 신뢰 관계를 이용한 권한 상승 용이, ⑥ 정상 행위와 위협 행위의 구별·탐지 복잡성이다. 해법의 출발점은 신뢰를 전제로 하지 않고 의심하며 확인하는 태도다. (00:32:22–00:34:52)

### 4. 제로트러스트의 원리와 구현 아키텍처

제로트러스트는 “절대 신뢰하지 말고 항상 검증(Never Trust, Always Verify)”하는 보안 철학·패러다임이다. 하나의 큰 경계 안을 신뢰하는 방식과 달리 각 리소스마다 보안 경계를 두며, 리소스에 접근할 때마다 인증·권한을 확인한다. 신뢰의 단위를 조직 경계에서 개별 접근·세션으로 바꾸면 한 시스템이 침해되어도 다른 시스템으로의 확산을 제한할 수 있다. 회사 건물 비유에서 경계 모델은 로비에서 한 번 출입증을 확인한 뒤 내부를 자유롭게 다니는 모습이고, 제로트러스트는 공간별 출입 통제·지속 감시·필요한 저장소 접근을 두는 모습이다. 아이디·방문증으로 한 번 확인하고 끝내는 것이 아니라 신원과 권한을 지속 확인한다. (00:34:52–00:40:23)

제로트러스트와 보안 통제(Security Controls)는 구분된다. 제로트러스트는 보안에 대한 철학·사고방식이고, 통제는 네트워크에서 허용할 경로 등 구체적인 규칙이다. 통제 준수만으로 보안이 완성되지는 않는다. 예를 들어 최소 길이 8자 비밀번호 규칙을 지키더라도 ‘12345678’ 같은 약한 암호는 안전하지 않다. 교수는 규정이 최소 기준선이며, 제로트러스트 문화를 내면화해 지속 인증·행동 분석 등 실제로 안전한 행동을 택하는 것이 중요하다고 설명했다. (00:40:23–00:43:44)

제로트러스트의 일곱 원리는 강의에서 다음 취지로 설명됐다. ① 데이터 원천·컴퓨팅 서비스 등 모든 데이터와 서비스를 보호 대상 리소스로 취급한다(개인 소유 기기도 내부 리소스에 접근한다면 포함). ② 네트워크 위치와 관계없이 모든 통신의 기밀성·무결성을 보호한다. ③ 세션 단위로 접근을 평가하고 업무에 필요한 최소 권한만 준다. ④ 사용자·애플리케이션·요청 자산의 상태·행동·환경 속성을 고려해 동적으로 접근을 결정한다. ⑤ 모든 자산의 무결성과 보안 상태를 지속 모니터링하고 필요하면 패치 등 복구 조치를 한다. ⑥ 엄격한 인증·접근 검사 뒤 허용하고 접근 중에도 위협·위험을 평가하며 신뢰를 재평가한다(다중 인증과 계정/세션 관리가 예로 언급됨). ⑦ 사용자·기기·네트워크·인프라 상태, 트래픽, 접근 요청 정보를 수집·처리해 보안 정책 개선에 쓴다. 일부 원리의 번호·정확한 표현은 자막이 손상되어 취지만 정리했으며 슬라이드 확인이 필요하다. (00:44:10–00:47:13)

제로트러스트 아키텍처(ZTA)는 철학을 구현하는 구조다. 모든 주체(Subject)의 자원 접근 요청은 PEP(Policy Enforcement Point, 정책 시행 지점)를 지나며, PDP(Policy Decision Point, 정책 결정 지점)가 접근 허용 여부를 판단한다. 묵시적 신뢰 구간을 최소화하도록 PDP·PEP를 자원 가까이 둔다. 요청 주체와 판단 지점 사이의 비신뢰 구간은 요청을 신뢰하지 않는 영역이고, PEP를 통과해도 자원까지의 신뢰 구간을 가능한 작게 유지한다. 다섯 핵심 보호 영역으로 신원, 기기, 네트워크, 애플리케이션, 데이터가 언급됐다. (00:47:13–00:49:30)

구성 요소는 네 가지로 소개됐다. PDP는 접근 정책을 결정하는 상위 개념이며 Policy Engine(PE)과 Policy Administrator(PA)로 구성된다. PE는 신뢰 정보를 바탕으로 허용·거부 결정을 계산하고, PA는 그 결정을 받아 주체와 자원 사이 통신 경로를 설정·해제하며 PEP와 연동해 동적 권한을 집행하도록 한다. PEP는 자원 앞의 최종 관문으로 PDP 결정을 실제 접근 제어로 실행한다. CDM(지속적 진단 및 완화), 규정 준수 정보, 위협 인텔리전스, 활동 로그 등이 제어 영역에 입력되고 정책 엔진·관리자가 판단한 결과가 데이터 영역의 PEP를 통해 집행되는 흐름이다. (00:49:30–00:51:31)

제로트러스트는 한 번에 완성되는 제품이 아니라 현재 상태를 평가하고 점진적으로 성숙도를 높이는 여정이다. 강의는 전통적/초기에서 고급·최적 단계로 나아가는 모델과 국내 성숙도 모델 1.0 및 더 세분화된 2.0을 언급했다. 체크 항목으로 현 수준을 평가해 조직 여건과 기술·위협 변화에 맞춰 개선한다. 레거시 기술을 전부 없애야 하는 것은 아니다. 제로트러스트는 특정 기술이 아니라 방향성이므로 기존 기술도 그 원리에 맞게 활용할 수 있고, 성숙도가 낮다고 완전히 ‘비(非) 제로트러스트’로 단정하지 말고 전략적으로 발전시켜야 한다. (00:51:31–00:54:17)

RMF(Risk Management Framework)는 NIST SP 800-37로 들리는 문서에 근거한 조직 차원의 위험 관리 방법론으로 설명됐다. 단계는 분류(자산·정보 체계화), 선택(보안 통제 선택), 구현, 평가, 승인, 모니터링이며 순환적으로 지속 위험 관리를 수행한다. 프레임워크는 “무엇을 해야 하는가”에 답하며 프로세스·절차·역할·평가 방법을 다룬다. 아키텍처는 “어떻게 구현하는가”에 답하며 구조와 메커니즘을 다룬다. RMF는 거버넌스와 위험 기반 의사결정, ZTA는 동적·세분화된 접근 통제의 구현에 초점을 두므로 상호 보완적이다. (00:54:17–00:56:52)

### 5. 클라우드 네이티브와 계층별 보안

강의에서 인용한 VMware 정의에 따르면 클라우드 네이티브는 클라우드 컴퓨팅 방법·도구, 현대적 아키텍처와 자동화를 활용해 복잡성을 관리하고 개발 속도를 높이는 애플리케이션 개발·배포·실행 방식이다. 핵심은 마이크로서비스·컨테이너와 DevOps·CI/CD다. 발전 흐름은 물리 서버·모놀리식에서 가상 서버를 거쳐 2010년대 이후 컨테이너·마이크로서비스로 이어진다고 설명됐다(중간 연대·약어는 자막 불명확). 마이크로서비스는 큰 앱을 독립 개발·배포 가능한 작은 서비스로 나눠 민첩성과 개발 용이성을 높인다. 컨테이너는 앱과 의존성을 패키지로 묶어 환경 차이로 인한 “내 컴퓨터에서는 되는데 서버에서는 안 되는” 문제를 줄인다. 서비스 메시가 서비스 간 통신을 관리하고, 불변(Immutable) 인프라는 배포 뒤 직접 수정하지 않고 새 인프라를 만들어 교체한다. 선언적 API는 수행 절차보다 원하는 상태를 명시한다. (00:56:52–01:00:38)

교수가 제시한 장점은 트래픽 변화에 따른 동적 확장, 한 서비스 장애에도 다른 서비스가 계속 작동하는 회복성, 기능의 빠른 개발·배포, AWS·Google Cloud·온프레미스 사이의 이식성이다. 클라우드 네이티브 보안은 단일 경계에 의존하지 않고 계층을 아우르는 PO(C)C(Cloud, Cluster, Container, Code) 모델로 설명됐다. ① Cloud: IaaS/PaaS 등 기반 인프라·클라우드 서비스 보안. ② Cluster: Kubernetes·OpenShift 같은 오케스트레이션 플랫폼 보안. RBAC(역할 기반 접근 제어), 정책, 네트워크 정책에 의한 Pod 간 통신 제어, Pod Security Standards와 실행 정책을 다룬다. ③ Container: 런타임·이미지·레지스트리 보안 및 이미지 취약점 스캔. 애플리케이션 코드가 안전해도 베이스 이미지·의존 라이브러리에 취약점이 있을 수 있다. ④ Code: 애플리케이션 코드·비즈니스 로직·민감 데이터 보호. 보안 코딩, 애플리케이션 보안 테스트, API 키·DB 비밀번호 등 비밀정보 관리, 마이크로서비스 간 통신 데이터 보호가 중요하다. 각 층은 독립적으로 끝나는 것이 아니라 전체 환경에서 함께 작동한다. (01:01:34–01:04:44)

## 교수 강조 사항

- 클라우드 콘솔의 작은 조작 실수도 중요 리소스 삭제로 이어질 수 있으므로 권한 제한·추가 승인·백업·복구 절차와 지속 점검이 필요하다. (00:01:45–00:04:00)
- 자격 증명 유출은 자동화된 API/CLI 사용으로 큰 비용·정보 피해로 번질 수 있다. 장기 키와 루트 계정을 줄이고 MFA, 임시 자격 증명, 실시간 사용량·위치 감사를 적용한다. (00:05:16–00:08:39)
- 클라우드 보안은 기술 솔루션 하나로 해결되지 않는다. 예측 보안에서 가시성→인텔리전스→자동화가 이어져야 한다. (00:08:39–00:09:10, 00:12:50–00:15:07)
- 기술 도입은 유행보다 성숙도·현실 적용성·조직의 단기 및 장기 계획을 보고 정한다. 초기 기술은 파일럿으로 검증한다. (00:16:28–00:18:54)
- “내부는 안전하다”는 경계 모델의 묵시적 신뢰가 측면 이동·권한 상승·탐지 지연의 근본 원인이다. (00:22:35–00:23:31, 00:32:22–00:34:52)
- 제로트러스트는 특정 제품이나 레거시 제거 계획이 아니라 철학·방향이며, 접근마다 검증하고 조직의 성숙도에 맞춰 점진 개선한다. (00:40:23–00:43:44, 00:51:31–00:54:17)
- 보안 통제를 지키는 것만으로 충분하지 않다. 규정은 최소선이고, 안전한 행동을 뒷받침하는 제로트러스트 문화가 필요하다. (00:41:55–00:43:44)
- RMF와 ZTA를 혼동하지 말 것: RMF는 위험관리에서 무엇을 할지, ZTA는 접근 통제를 어떻게 구현할지 다루며 함께 쓸 수 있다. (00:55:12–00:56:52)
- 클라우드 네이티브는 코드뿐 아니라 클라우드·클러스터·컨테이너·코드 전 계층을 보호해야 한다. (01:01:34–01:04:44)

## 이론과 공식 목록

- 경계/캐슬 모델: 외부 불신·내부 신뢰, 방화벽·DMZ·IDS 등 경계 중심 방어. 클라우드 분산·원격 환경에서 경계가 모호하고 내부 침해 후 측면 이동에 취약. (00:21:17–00:23:51)
- 예측 보안의 VIA: Visibility(로그를 인사이트로 만들고 시각화) → Intelligence(통계·예측·ML/DL로 분석) → Automation(예측/사고 시 보호 조치 자동 실행). (00:13:03–00:15:07)
- 보안 기술 도입 성숙도: 하이프 사이클을 참고해 혁신 초기 기술은 파일럿으로 검증하고, 입증된 운영 기술과 성숙 예상 시점을 전략에 반영. 공식·계산식은 없음. (00:16:28–00:18:54)
- 클라우드 보안 도메인: 위험 관리, 접근 제어, 네트워크 보안, 데이터 보안, 가상화 보안. (00:19:45–00:20:59)
- 제로트러스트: Never Trust, Always Verify. 위치나 기존 신뢰 대신 매 접근·세션에서 신원·권한·기기/자산 상태를 검증하고 최소 권한과 동적 정책을 적용. (00:34:48–00:36:53, 00:44:10–00:47:13)
- ZTA 구성: PDP(PE+PA)가 정책을 판단·관리하고 PEP가 자원 앞에서 집행. CDM·준수 상태·위협 정보·로그가 판단에 입력되며 신뢰 구간을 최소화한다. (00:47:13–00:51:31)
- RMF 순환: 분류 → 선택 → 구현 → 평가 → 승인 → 모니터링 → 반복. 강의에서 NIST SP 800-37로 들리는 출처를 언급. (00:54:17–00:55:12)
- 프레임워크/아키텍처: 각각 보안을 위해 무엇을 할지(거버넌스·절차·역할·평가)와 어떻게 구현할지(구조·메커니즘)를 다룸. RMF와 ZTA는 상호 보완. (00:55:12–00:56:52)
- 클라우드 네이티브 핵심: 컨테이너, 서비스 메시, 마이크로서비스, 불변 인프라, 선언적 API. 이점은 확장성·서비스 회복성·빠른 배포·이식성. (00:59:15–01:01:34)
- 계층 보안 PO(C)C: Cloud, Cluster, Container, Code. 인프라/클라우드 서비스, 오케스트레이션·RBAC·네트워크 정책, 이미지·런타임·레지스트리, 앱 코드·테스트·시크릿·서비스 간 통신을 각 층에서 보호. (01:01:34–01:04:44)

2. 유출된 AWS 자격 증명이 빠르게 큰 피해를 만드는 이유와 대응을 설명하라. — CLI/API 자동화로 다수 인스턴스를 즉시 만들어 채굴·유출에 악용하고 비용도 키울 수 있다. 장기 키·루트 사용을 줄이고 임시 토큰·역할·MFA, 사용량·위치 감사를 적용한다.
3. 경계 보안의 핵심 가정과 대표적 취약점을 말하라. — 외부는 위험하고 내부는 안전하다는 가정. 침입 후 측면 이동·권한 상승이 쉬우며 내부 모니터링이 약하다.
4. VIA 세 요소의 역할과 순서를 설명하라. — 가시성으로 데이터를 이해 가능한 정보로 만들고, 인텔리전스로 위험을 분석·예측하며, 자동화로 대응을 즉시 실행한다.
5. 제로트러스트와 보안 통제의 차이는 무엇인가? — 제로트러스트는 항상 검증하는 사고방식이고, 보안 통제는 이를 구체화한 접근 규칙이다. 통제 준수만으로 안전이 보장되지는 않는다.
6. PDP, PE, PA, PEP의 역할을 구별하라. — PDP는 정책 결정 체계, PE는 허용/거부 판단, PA는 통신 경로 설정·해제, PEP는 결정을 자원 접근에 실제 집행한다.
7. RMF와 ZTA는 어떤 점에서 다르고 어떻게 함께 쓰이는가? — RMF는 위험관리 절차와 해야 할 일을 제시하고, ZTA는 세분화된 접근 통제를 구현한다. RMF 위험 판단을 ZTA 제어로 구현해 보완한다.
8. PO(C)C 네 계층과 각 계층의 보안 예를 연결하라. — Cloud: 인프라, Cluster: Kubernetes 권한·네트워크 정책, Container: 이미지·런타임 취약점, Code: 보안 코딩·테스트·시크릿·서비스 간 통신 보호.
