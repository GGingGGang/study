# 로컬 테스트 환경 (Local Testing Setup)

> 알고리즘 · 실전 · 학습내용: 문제 풀이 작업 폴더 구조, `python3 sol.py < input.txt` 리다이렉션, 로컬일 때만 파일 입력으로 바꾸는 조건부 스니펫, 여러 테스트케이스를 한 번에 돌리는 bash 스크립트와 `diff` 비교, `time` 명령과 `time.perf_counter()`로 실행 시간 측정, `resource`·`tracemalloc`으로 메모리 측정, 공백 무시 비교 옵션, 에디터 편의 설정 개념, 제출용/로컬용 코드 분리

---

## 1. 왜 로컬 테스트 환경인가 ★★★

플래티넘 구간에 오면 **"제출 → 틀림 → 코드 노려보기"** 사이클이 통하지 않는다. 코드가 길고, 예제는 통과하는데 실제로는 틀리는 경우가 대부분이기 때문이다.

| 없을 때 | 있을 때 |
|---|---|
| 예제를 매번 손으로 붙여넣는다 | `< input.txt` 한 번 |
| 케이스 3개면 3번 붙여넣는다 | `./run_tests.sh` 한 번에 전부 |
| "빠른가?"를 제출해서 안다 | `time`으로 로컬에서 안다 |
| 반례를 못 만든다 | 스크립트로 자동 생성·대조 |

> ★★★ **핵심**: 로컬 테스트 환경의 목적은 **"제출 버튼을 디버거로 쓰지 않는 것"** 이다. 채점 서버는 피드백이 느리고 정보가 거의 없다. 반복 주기를 초 단위로 줄이는 게 실력 차를 만든다.

---

## 2. 작업 폴더 구조 ★★

문제 하나당 폴더 하나. 파일 이름은 **모든 문제에서 똑같이** 쓴다. 이름이 고정돼야 스크립트를 재활용할 수 있다.

```
problem/
├── sol.py            # 내 풀이 (이것만 제출한다)
├── input.txt         # 지금 굴려보는 입력 하나
├── run_tests.sh      # tests/ 전체를 돌리는 스크립트
└── tests/
    ├── 1.in          # 문제의 예제 입력
    ├── 1.out         # 문제의 예제 출력
    ├── 2.in          # 내가 만든 경계값 케이스
    ├── 2.out
    └── 3.in
```

**예제 입출력은 보자마자 `tests/1.in`, `tests/1.out`으로 옮겨 붙인다.** 그 뒤에 N=1, 최댓값, 음수 같은 경계 케이스를 `2.in`, `3.in`으로 계속 추가한다.

## 3. 입력 리다이렉션 — 가장 기본 ★★★

**셸의 `<`는 파일 내용을 프로그램의 표준 입력으로 밀어 넣는다.** 코드를 한 글자도 안 고쳐도 된다.

```bash
# 파일을 표준 입력으로
python3 sol.py < input.txt

# 결과를 파일로 저장
python3 sol.py < input.txt > output.txt

# 파이프로 즉석 입력 (짧은 케이스에 편하다)
printf '5\n3 1 4 1 5\n' | python3 sol.py

# heredoc — 여러 줄을 그 자리에서
python3 sol.py <<'EOF'
5
3 1 4 1 5
EOF
```

`sol.py`는 평소처럼 표준 입력만 읽으면 된다.

```python
import sys
input = sys.stdin.readline        # 입력이 많으면 필수

def main():
    n = int(input())
    arr = list(map(int, input().split()))
    print(sum(arr), max(arr))

main()
```

```bash
$ printf '5\n3 1 4 1 5\n' | python3 sol.py
14 5
```

> **함정**: `sys.stdin.readline`은 **개행 문자를 그대로 남긴다.** 숫자는 `int()`가 알아서 처리하지만, **문자열을 읽을 때는 반드시 `.rstrip()`** 을 붙여야 한다. `input().strip()`을 안 해서 문자열 비교가 조용히 실패하는 사고가 흔하다.

## 4. 로컬일 때만 파일 입력으로 바꾸기 ★★★

에디터에서 "실행" 버튼만 누르면 리다이렉션을 못 쓴다. 이럴 때 **로컬에서만 `input.txt`를 표준 입력으로 갈아끼우는** 스니펫을 쓴다. **채점 서버에는 `input.txt`가 없으므로 이 코드는 그냥 지나간다.**

```python
import sys, os

# 로컬(내 PC)에만 있는 input.txt가 보이면 그것을 표준 입력으로 연결한다.
# 채점 서버에는 파일이 없으므로 이 블록은 통과되고 진짜 표준 입력을 읽는다.
if os.path.exists('input.txt'):
    sys.stdin = open('input.txt')

input = sys.stdin.readline

def main():
    n = int(input())
    arr = list(map(int, input().split()))
    print(sum(arr), max(arr))

main()
```

다른 방식들도 있다.

| 방식 | 코드 | 특징 |
|---|---|---|
| 파일 존재로 판별 | `os.path.exists('input.txt')` | **가장 단순·안전. 추천** |
| 환경변수로 판별 | `os.environ.get('LOCAL')` | `LOCAL=1 python3 sol.py` 로 켠다 |
| 인자로 판별 | `len(sys.argv) > 1` | `python3 sol.py input.txt` |

> **함정**: **`input.txt`를 남겨둔 채 `python3 sol.py < tests/2.in`을 돌리면 리다이렉션이 무시된다.** 코드가 `input.txt`를 먼저 열어버리기 때문이다. 실제로 `tests/2.in`의 내용과 전혀 다른 답이 나와 "왜 틀리지?" 하며 시간을 날린다. **일괄 테스트를 돌릴 때는 `input.txt`를 지우거나, 아래 5번처럼 환경변수 방식으로 바꾼다.**

```python
import sys, os

# 일괄 테스트와 충돌하지 않는 버전: LOCAL=1 일 때만 파일을 연다
if os.environ.get('LOCAL') and os.path.exists('input.txt'):
    sys.stdin = open('input.txt')
```

## 5. 여러 테스트케이스 일괄 실행 ★★★

`tests/*.in`을 전부 돌려 `tests/*.out`과 비교하는 스크립트다. **이 파일 하나가 로컬 환경의 심장이다.**

```bash
#!/bin/bash
# run_tests.sh — tests/*.in 을 모두 실행해 tests/*.out 과 비교한다.
SOL=${1:-sol.py}          # 인자로 다른 풀이를 넘길 수도 있다
pass=0; fail=0

for infile in tests/*.in; do
    name=$(basename "$infile" .in)
    expected="tests/$name.out"
    [ -f "$expected" ] || { echo "SKIP $name (정답 파일 없음)"; continue; }

    actual=$(python3 "$SOL" < "$infile")

    # -Z : 줄 끝 공백 무시  /  $(...)가 마지막 개행을 떼주므로 개행 차이도 안전
    if diff -q -Z <(echo "$actual") "$expected" > /dev/null 2>&1; then
        echo "PASS $name"
        pass=$((pass+1))
    else
        echo "FAIL $name"
        echo "  --- 기대 ---"; sed 's/^/  /' "$expected"
        echo "  --- 실제 ---"; echo "$actual" | sed 's/^/  /'
        fail=$((fail+1))
    fi
done

echo "----------------------"
echo "통과 $pass / 실패 $fail"
[ "$fail" -eq 0 ]         # 전부 통과해야 종료 코드 0
```

```bash
$ chmod +x run_tests.sh
$ ./run_tests.sh
PASS 1
PASS 2
PASS 3
----------------------
통과 3 / 실패 0
```

틀린 풀이를 넣으면 **어디가 다른지 바로 보여준다.**

```bash
$ ./run_tests.sh wrong.py
FAIL 1
  --- 기대 ---
  14 5
  --- 실제 ---
  14 1
PASS 2
FAIL 3
  --- 기대 ---
  100005 100000
  --- 실제 ---
  100005 2
----------------------
통과 1 / 실패 2
```

## 6. 출력 비교 — `diff` 옵션 ★★

채점기는 보통 **줄 끝 공백과 마지막 개행을 무시**한다. 로컬 비교도 같은 기준으로 맞춰야 헛된 FAIL이 안 뜬다.

| 명령 | 의미 |
|---|---|
| `diff a.txt b.txt` | 기본 비교 (다른 줄을 보여준다) |
| `diff -q a.txt b.txt` | 다른지 여부만 (스크립트용) |
| `diff -Z a.txt b.txt` | **줄 끝 공백 무시** — 실전에서 가장 많이 쓴다 |
| `diff -w a.txt b.txt` | **모든 공백 무시** (너무 관대하니 주의) |
| `diff -B a.txt b.txt` | 빈 줄 무시 |
| `diff -y a.txt b.txt` | 좌우 나란히 보기 |

```bash
# 실수/부동소수점 답은 diff로 못 잡는다 -> 오차 허용 비교가 필요하다
python3 - "$out" "$exp" <<'EOF'
import sys
a = open(sys.argv[1]).read().split()
b = open(sys.argv[2]).read().split()
ok = len(a) == len(b) and all(abs(float(x) - float(y)) <= 1e-6 for x, y in zip(a, b))
print("OK" if ok else "DIFF")
EOF
```

> **함정**: `diff -w`는 **`1 2 3`과 `123`을 같다고 판정한다.** 공백이 의미를 갖는 문제(행렬 출력 등)에서는 오답을 통과로 착각하게 만드니, 기본은 `-Z`만 쓰는 게 안전하다.

## 7. 실행 시간 측정 ★★★

### 셸의 `time`

```bash
$ time python3 sol.py < tests/big.in > /dev/null

real    0m1.284s      # 실제 걸린 시간 <- 이것이 채점 기준에 가깝다
user    0m1.240s      # CPU가 내 코드를 돈 시간
sys     0m0.040s      # 커널(I/O 등)에 쓴 시간
```

### 코드 안에서 구간별로

```python
import time

t0 = time.perf_counter()
arr = list(range(2_000_000))          # 측정할 구간
total = sum(arr)
elapsed = time.perf_counter() - t0

# 반드시 stderr로! stdout에 찍으면 출력 형식이 깨져 "틀렸습니다"가 된다
import sys
print(f"[{elapsed:.3f}s] total={total}", file=sys.stderr)
```

| 함수 | 용도 |
|---|---|
| `time.perf_counter()` | **경과 시간 측정용 고해상도 시계. 기본은 이것** |
| `time.process_time()` | CPU 시간만 (I/O 대기 제외) |
| `time.time()` | 벽시계 시각. 시스템 시계 변경에 영향받아 측정용으론 부적합 |

> **함정**: 로컬이 채점 서버보다 빠를 수도, 느릴 수도 있다. **로컬 1초가 통과를 보장하지 않는다.** 제한 시간의 **절반 안쪽**에 들어와야 마음이 놓인다.

## 8. 메모리 측정 ★★

```python
import sys, tracemalloc, resource

tracemalloc.start()
arr = list(range(2_000_000))
cur, peak = tracemalloc.get_traced_memory()      # 파이썬 객체가 쓴 힙
tracemalloc.stop()

rss = resource.getrusage(resource.RUSAGE_SELF).ru_maxrss    # 리눅스는 KB 단위
print(f"파이썬 힙 최대: {peak / 1024 / 1024:.1f} MB", file=sys.stderr)
print(f"프로세스 최대 RSS: {rss / 1024:.1f} MB", file=sys.stderr)
```

```
파이썬 힙 최대: 76.3 MB
프로세스 최대 RSS: 270.5 MB
```

**두 숫자가 크게 다른 게 정상이다.** `tracemalloc`은 파이썬 객체만 세고, RSS는 인터프리터 자체와 할당자가 잡아둔 메모리까지 포함한다. **채점기가 보는 건 RSS 쪽**이다.

```bash
# 자식 프로세스의 최대 RSS를 셸에서 확인 (GNU time이 없는 환경에서도 동작)
python3 -c "
import resource, subprocess, sys
subprocess.run([sys.executable, 'sol.py'], stdin=open('input.txt'))
kb = resource.getrusage(resource.RUSAGE_CHILDREN).ru_maxrss
print(f'최대 RSS: {kb/1024:.1f} MB', file=sys.stderr)
"
```

GNU coreutils가 있는 환경이라면 `/usr/bin/time -v python3 sol.py < input.txt` 의 `Maximum resident set size` 줄이 같은 값을 준다.

> **함정**: `tracemalloc`은 **모든 할당을 추적하느라 프로그램을 몇 배 느리게 만든다.** 시간 측정과 메모리 측정은 **따로** 돌려야 한다. 같이 켜두고 "왜 이렇게 느리지?" 하면 안 된다.

## 9. 에디터 편의 설정 개념 ★

에디터마다 방법은 다르지만, 확보해야 할 것은 셋뿐이다.

| 목표 | 방법 |
|---|---|
| **표준 입력을 파일에서** | 4번의 조건부 스니펫, 또는 에디터의 "run with args/stdin" 확장 |
| **한 키로 전체 테스트** | `run_tests.sh`를 태스크(VS Code `tasks.json`)로 등록해 단축키 바인딩 |
| **템플릿 자동 삽입** | 스니펫 기능에 아래 시작 골격을 등록 |

```python
import sys
input = sys.stdin.readline
sys.setrecursionlimit(10 ** 6)

def main():
    n = int(input())
    # 여기부터 작성

main()
```

## 10. 제출용 / 로컬용 코드 분리 ★★★

**디버그 코드가 제출본에 섞여 들어가는 것**이 로컬 환경의 유일한 부작용이자, 실제로 자주 겪는 사고다.

| 원칙 | 이유 |
|---|---|
| 디버그 출력은 **무조건 `stderr`** | `stdout`은 정답 출력 전용. 섞이면 "틀렸습니다"·"출력 초과" |
| 로컬 전용 코드는 **한 블록에 모아 파일 맨 위** | 지울 때 한눈에 보인다 |
| `input.txt` 열기는 **파일 존재/환경변수로 조건부** | 서버에서 `FileNotFoundError`(런타임 에러) 방지 |
| 제출 직전 `grep` 한 번 | 남은 디버그 출력을 기계적으로 잡는다 |

```python
import sys, os

DEBUG = bool(os.environ.get('LOCAL'))     # 로컬에서만 True

def dbg(*args):
    if DEBUG:
        print('[dbg]', *args, file=sys.stderr)   # stdout을 절대 건드리지 않는다

dbg('여기는 로컬에서만 보인다')
print('정답 출력')
```

```bash
# 제출 직전 자동 점검 — 남은 디버그 흔적 찾기
grep -nE 'print\(.*(dbg|debug|테스트|확인)|breakpoint\(|input\.txt' sol.py

# 채점 서버와 같은 조건(LOCAL 없이, input.txt 없이)으로 마지막 실행
env -u LOCAL python3 sol.py < tests/1.in
```

> ★★★ **핵심**: **정답은 `stdout`, 디버그는 `stderr`.** 이 규칙 하나만 지키면 로컬 디버그 코드를 지우지 않고 제출해도 대부분 사고가 나지 않는다. 반대로 이걸 어기면, 로컬에서 완벽히 도는 코드가 채점기에서는 "틀렸습니다"로 돌아온다.

---

### 한 줄 요약
로컬 테스트 환경의 목적은 **제출 버튼을 디버거로 쓰지 않는 것**이고, 출발점은 **`python3 sol.py < input.txt` 리다이렉션**이다. 에디터에서 실행 버튼만 쓴다면 **`os.path.exists('input.txt')` 조건부로 `sys.stdin`을 갈아끼우되**, 그 파일이 남아 있으면 **`< tests/2.in` 리다이렉션이 통째로 무시되는 함정**이 있으므로 일괄 테스트 때는 지우거나 `LOCAL=1` 환경변수 방식으로 바꾼다. 진짜 무기는 **`tests/*.in`을 순회하며 `diff -Z`로 대조하고 실패한 케이스의 기대·실제를 찍어주는 `run_tests.sh`** 이며, 여기에 **`time`·`time.perf_counter()`(반드시 `stderr`로)** 로 속도를, **`tracemalloc`·`resource.getrusage`(두 값은 원래 다르고 채점기는 RSS를 본다)** 로 메모리를 확인한다. 마지막으로 **정답은 `stdout`, 디버그는 `stderr`** 라는 규칙과 제출 직전 `grep` 한 번이 로컬 환경의 유일한 부작용을 막아준다.
