## 1. 입력 크기 → 허용 복잡도 역산표 ★★★

**문제를 읽고 알고리즘을 고르기 전에, N을 보고 "쓸 수 있는 복잡도"부터 정한다.** 이 표 하나가 탐색 방향을 절반으로 줄여준다.

| N의 범위 | 허용 복잡도 | 대표 알고리즘 |
|---|---|---|
| N ≤ 10 | **O(N!)** | 순열 전체 탐색, 외판원 완전탐색 |
| N ≤ 20 | **O(2^N)** | 부분집합 전체 탐색, 비트마스크 DP |
| N ≤ 100 | O(N⁴) | 4중 반복, 작은 그래프 완전탐색 |
| N ≤ 500 | **O(N³)** | 플로이드-워셜, 행렬 곱 |
| N ≤ 5,000 | **O(N²)** | 2중 반복 DP, LIS 기본형 |
| N ≤ 100,000 | **O(N log N)** | 정렬, 이분 탐색, 세그먼트 트리, 다익스트라 |
| N ≤ 10,000,000 | **O(N)** | 투 포인터, 누적 합, 한 번 훑기 |
| N ≥ 10^9 | **O(log N) / O(1)** | 이분 탐색, 분할정복 거듭제곱, 수학 공식 |

> ★★★ **핵심**: **N=20이 보이면 비트마스크, N=500이면 플로이드-워셜, N=10^5면 정렬이나 log가 붙는 자료구조**를 먼저 의심한다. 출제자는 N을 아무렇게나 정하지 않는다 — **N은 의도된 힌트**다.

## 2. 1초 ≈ 1억 연산과 파이썬 보정 ★★★

C/C++ 기준으로 **1초에 대략 1억(10^8)번의 단순 연산**이 통용된다. 문제는 **파이썬이 그 기준에 한참 못 미친다**는 것이다.

| 언어 | 1초당 단순 연산 (대략) | C++ 대비 |
|---|---|---|
| C / C++ | 10^8 ~ 10^9 | 1배 |
| Java | 10^8 정도 | 1~2배 느림 |
| **PyPy3** | 10^7 ~ 10^8 | 3~10배 느림 |
| **Python3 (CPython)** | **10^6 ~ 10^7** | **20~100배 느림** |

즉 **파이썬으로는 "1초에 1천만 번"** 정도로 잡는 게 현실적이다.

```python
import time

t = time.perf_counter()
s = 0
for i in range(10 ** 7):        # 순수 파이썬 반복 1천만 번
    s += i
print(f"파이썬 for 1천만: {time.perf_counter() - t:.2f}s")

t = time.perf_counter()
s = sum(range(10 ** 7))         # 같은 일을 C 구현에 맡기면
print(f"내장 sum 1천만: {time.perf_counter() - t:.2f}s")
```

실행하면 `파이썬 for 1천만: 0.57s` / `내장 sum 1천만: 0.08s` — **같은 일인데 7배 차이가 난다.** 파이썬 최적화의 본질은 **"반복을 C로 구현된 내장 함수에 떠넘기는 것"** 이다.

| 느린 파이썬 | 빠른 대안 |
|---|---|
| `for`로 누적 합산 | `sum()`, `itertools.accumulate` |
| `for`로 최대·최소 | `max()`, `min()` |
| `for`로 형변환 | `map(int, ...)` |
| 문자열 `+=` 반복 | `''.join(리스트)` |
| `print()` 반복 호출 | `sys.stdout.write('\n'.join(...))` |
| 리스트 원소 하나씩 정렬 삽입 | `sorted()`, `bisect.insort` |

> ★★★ **핵심**: 복잡도를 계산했으면 **파이썬 상수를 최소 10배 잡고 다시 본다.** N=10^5에 O(N log N)이면 약 170만 연산이라 여유롭지만, **N=10^5에 O(N²)는 100억**이라 어떤 최적화로도 못 살린다. **상수 최적화로 넘을 수 있는 건 2~3배까지**이고, 그 이상은 알고리즘 자체를 바꿔야 한다.

## 3. PyPy3 vs Python3 선택 기준 ★★★

대부분의 온라인 저지는 두 언어로 따로 제출할 수 있다. **대부분은 PyPy3가 정답**이지만, 예외가 분명하다.

| 상황 | 선택 |
|---|---|
| 반복문이 많은 순수 파이썬 연산 | **PyPy3** (JIT가 수십 배 가속) |
| DP, 완전탐색, 시뮬레이션 | **PyPy3** |
| **메모리 제한이 빡빡함**(예: 128MB) | **Python3** — PyPy는 기본 오버헤드가 크다 |
| **깊은 재귀**를 쓴다 | **Python3** — PyPy는 재귀에서 오히려 느리고 잘 터진다 |
| 큰 정수(파이썬 `int`) 연산이 핵심 | **Python3** — PyPy의 big int가 더 느릴 때가 많다 |
| 입력만 크고 계산은 거의 없음 | 둘 다 비슷 (I/O가 지배) |

> **함정**: **PyPy3는 JIT 예열(warm-up) 시간이 필요하다.** 짧은 루프만 도는 작은 문제에서는 오히려 Python3보다 느릴 수 있다. 그리고 **PyPy3는 메모리를 훨씬 많이 먹어서**, Python3로는 통과하던 코드가 PyPy3에서 메모리 초과가 나기도 한다. **둘 다 실패하면 서로 바꿔 한 번씩 내보는 게 실전 요령이다.**

## 4. 제출 결과별 원인 진단표 ★★★

| 결과 | 흔한 원인 |
|---|---|
| **틀렸습니다** | 경계값(N=1·전부 음수·모두 같은 값), 초기값 `0`, 부동소수점 오차, 출력 형식(대소문자·개행), 문제 조건 오독 |
| **시간 초과** | 복잡도 자체가 큼, `input()` 사용, `print()` 반복, `list.pop(0)`·`in` 리스트 탐색, 불필요한 재계산 |
| **메모리 초과** | 2차원 리스트 과할당, 큰 입력 통째로 저장, 재귀 스택, 방문 배열을 매번 새로 만듦 |
| **런타임 에러 (RecursionError)** | 재귀 깊이 초과 — `sys.setrecursionlimit` 미설정 또는 반복 DFS 미사용 |
| **런타임 에러 (IndexError)** | 0-based/1-based 혼동, 배열 크기 `N` vs `N+1`, 세그먼트 트리 `4N` 미확보 |
| **런타임 에러 (ValueError)** | 빈 리스트에 `max()`/`min()`, 입력 줄이 예상과 다름, `int('')` |
| **런타임 에러 (ZeroDivisionError)** | 0으로 나눔 — 개수가 0인 경우(평균 계산 등)를 안 걸렀다 |
| **런타임 에러 (FileNotFound)** | `open('input.txt')`를 조건 없이 남겨둠 |
| **출력 초과** | 디버그 `print`가 남음, 무한 루프 안에서 출력, 종료 조건 누락 |

```python
# 자주 터지는 세 곳을 한 번에 막는 안전 골격
import sys
input = sys.stdin.readline
sys.setrecursionlimit(10 ** 6)          # RecursionError 예방

def average(nums):
    if not nums:                        # ZeroDivisionError / ValueError 예방
        return 0.0
    return sum(nums) / len(nums)

print(average([1, 2, 3]), average([]))  # 2.0 0.0
```

> **함정**: **`RecursionError`는 "런타임 에러"로만 표시된다.** 어떤 에러인지 안 알려주니, 재귀를 썼는데 런타임 에러가 뜨면 **가장 먼저 재귀 깊이를 의심**한다.

## 5. 시간 초과 대응 체크리스트 ★★★

**위에서부터** 순서대로 확인한다. 아래로 갈수록 비용이 크다.

### (1) 입출력 최적화 — 가장 싸고 효과가 크다

```python
import sys
input = sys.stdin.readline                     # input()보다 몇 배 빠르다

# 입력이 아주 크면 통째로 읽어 토큰으로 쪼갠다
data = sys.stdin.buffer.read().split()
n = int(data[0])
arr = list(map(int, data[1:1 + n]))

# 출력도 모아서 한 번에
out = [str(x) for x in arr]
sys.stdout.write('\n'.join(out) + '\n')
```

### (2) 자료구조 교체 — 잘못 쓰면 복잡도가 통째로 바뀐다

| 느린 코드 | 복잡도 | 빠른 대안 | 복잡도 |
|---|---|---|---|
| `arr.pop(0)` | O(N) | `collections.deque().popleft()` | O(1) |
| `arr.insert(0, x)` | O(N) | `deque().appendleft(x)` | O(1) |
| `x in list` | O(N) | `x in set` | 평균 O(1) |
| `list.index(x)` | O(N) | `dict`로 위치 저장 | 평균 O(1) |
| 매번 `min(arr)` | O(N) | `heapq` | O(log N) |
| 매번 `sorted()` | O(N log N) | `bisect.insort`로 유지 | O(N) 삽입, O(log N) 탐색 |
| 문자열 `s += x` 반복 | O(N²) | `''.join(리스트)` | O(N) |

### (3) 불필요한 재계산 제거

```python
# 나쁨: 루프 안에서 매번 다시 계산한다
# for i in range(n):
#     for j in range(i, n):
#         if sum(arr[i:j+1]) > best: ...      # O(N^3)

# 좋음: 누적 합으로 구간 합을 O(1)에
arr = [3, 1, 4, 1, 5, 9, 2, 6]
n = len(arr)
pre = [0] * (n + 1)
for i, v in enumerate(arr):
    pre[i + 1] = pre[i] + v

best = max(pre[j + 1] - pre[i] for i in range(n) for j in range(i, n))
print(best)                                    # 31 (전체 합)
```

메모이제이션(`functools.cache`), 루프 바깥으로 불변식 빼내기, 속성 조회를 지역 변수로 캐싱(`ap = arr.append`)도 같은 계열이다.

### (4) 복잡도 자체 개선 — 최후이자 근본

O(N²) → O(N log N)은 **정렬 + 투 포인터**, **이분 탐색**, **세그먼트 트리**, **DP 점화식 변형** 중 하나로 내려가는 경우가 대부분이다. **(1)~(3)으로 2~3배밖에 못 줄이므로, 10배 이상 부족하면 여기로 와야 한다.**

## 6. 메모리 최적화 ★★

| 기법 | 방법 |
|---|---|
| **리스트 대신 배열** | 정수만 담으면 `array('i', ...)` — `list`보다 훨씬 조밀하다 |
| **제너레이터 사용** | `[x*2 for x in big]` 대신 `(x*2 for x in big)` |
| **DP 차원 줄이기** | `dp[i][j]`가 `dp[i-1]`만 참조하면 **2줄만 유지**(롤링 배열) |
| **불필요한 저장 제거** | 입력 전체를 리스트로 안 들고 한 줄씩 처리 |
| **`set`/`dict` 대신 리스트** | 키가 0..N 범위 정수면 리스트가 훨씬 가볍다 |
| **문자열 대신 정수** | 비트마스크로 상태 표현 |

```python
from array import array
import sys

n = 1_000_000
lst = [0] * n                                  # 파이썬 객체 포인터 배열
arr = array('i', [0]) * n                      # 4바이트 정수 배열

print(sys.getsizeof(lst) // 1024, 'KB')        # 7812 KB (포인터 8바이트씩)
print(sys.getsizeof(arr) // 1024, 'KB')        # 3906 KB (정수 4바이트씩)
```

```python
# DP 롤링 배열: dp[i]가 dp[i-1]만 쓰면 2줄이면 충분하다
items = [(3, 4), (4, 5), (2, 3)]               # (무게, 가치)
W = 7
prev = [0] * (W + 1)
for w, v in items:
    cur = prev[:]                              # N x W 대신 W짜리 두 줄만
    for c in range(w, W + 1):
        cur[c] = max(prev[c], prev[c - w] + v)
    prev = cur
print(prev[W])                                 # 9
```

> **함정**: `sys.getsizeof(lst)`는 **리스트 자체(포인터 배열)의 크기만** 알려주고, 그 안에 든 정수 객체들의 크기는 빠져 있다. 실제 메모리는 훨씬 크므로, 진짜 사용량은 프로세스 RSS로 확인해야 한다.

## 7. 제출 전 최종 체크리스트 ★★★

제출 버튼을 누르기 전에 **30초만** 이 목록을 훑는다.

**입력 파싱**
- [ ] `input = sys.stdin.readline` 을 넣었는가 (입력이 많다면)
- [ ] 문자열을 읽을 때 `.rstrip()` / `.strip()` 을 했는가
- [ ] 테스트케이스가 여러 개인 문제인가 (첫 줄이 T인가)
- [ ] 한 줄에 여러 값 / 여러 줄에 나뉜 값을 정확히 나눠 읽는가

**경계와 자료형**
- [ ] N = 1, N = 최댓값에서 동작하는가
- [ ] 답이 **음수나 0**일 수 있는가 → 초기값이 `0`이 아니라 `-inf` / `arr[0]` 인가
- [ ] 인덱스가 0-based인지 1-based인지 코드 전체에서 일관적인가
- [ ] 배열 크기를 `N`이 아니라 `N+1`로 잡아야 하는 곳은 없는가
- [ ] 실수 비교를 `==` 로 하고 있지 않은가 (`abs(a-b) < 1e-9`)

**출력 형식**
- [ ] 소수점 자리수 지정이 필요한가 (`f"{x:.6f}"`)
- [ ] `YES/NO` 대소문자, 공백 vs 개행 구분자가 문제와 같은가
- [ ] 답이 없을 때 출력해야 할 값(`-1`, 빈 줄 등)을 처리했는가
- [ ] **디버그 `print`를 전부 지웠는가** (`stderr`로 뺐는가)

**실행 환경**
- [ ] `sys.setrecursionlimit(10**6)` 을 넣었는가 (재귀를 쓴다면)
- [ ] 깊이가 10만을 넘을 수 있으면 **반복 DFS**로 바꿨는가
- [ ] `open('input.txt')` 같은 로컬 전용 코드를 지우거나 조건부로 만들었는가
- [ ] 복잡도를 N 최댓값에 대입해 **파이썬 기준 1천만 연산 안쪽**인지 확인했는가
- [ ] Python3로 빠듯하면 **PyPy3로도 한 번** 내볼 준비가 됐는가

```python
# 제출 직전 자가 점검 스크립트 (sol.py 를 훑어 위험 신호를 찾는다)
import re, sys

CHECKS = [
    (r'^\s*input\s*=\s*sys\.stdin\.readline', '입력 최적화 있음', True),
    (r'setrecursionlimit',                    '재귀 한계 설정 있음', None),
    (r"open\(\s*['\"]input\.txt",             '로컬 파일 열기 남음!', False),
    (r'^\s*print\(.*(dbg|debug|디버그)',       '디버그 출력 남음!',   False),
    (r'\.pop\(0\)',                           'pop(0) 사용 — O(N)!', False),
]
src = open(sys.argv[1] if len(sys.argv) > 1 else 'sol.py', encoding='utf-8').read()
for pat, msg, good in CHECKS:
    hit = bool(re.search(pat, src, re.M))
    if hit and good is False:
        print(f"[경고] {msg}")
    elif hit:
        print(f"[확인] {msg}")
    elif good is True:
        print(f"[주의] {msg.replace('있음', '없음')}")
```

```bash
$ python3 precheck.py sol.py
[확인] 입력 최적화 있음
[경고] 로컬 파일 열기 남음!
[경고] 디버그 출력 남음!
[경고] pop(0) 사용 — O(N)!
```

**`[경고]`가 하나라도 뜨면 제출하지 않는다.** 깨끗한 코드라면 `[확인]` 줄만 나온다.

> ★★★ **핵심**: 이 목록에서 실제로 가장 많이 걸리는 건 **(1) 답이 음수일 수 있는데 초기값이 `0`**, **(2) 디버그 `print` 잔존**, **(3) 재귀 깊이**, **(4) `input()`을 그대로 쓴 시간 초과** 넷이다. 다른 걸 다 못 외워도 이 넷만은 매번 확인하자.

### 한 줄 요약
문제를 읽으면 알고리즘보다 **N을 먼저 보고 허용 복잡도를 역산**한다(N≤20이면 O(2^N), N≤500이면 O(N³), N≤10^5면 O(N log N)) — **N은 출제자가 준 힌트**다. 1초 ≈ 1억 연산은 C++ 기준이고 **파이썬은 20~100배 느려 "1초에 1천만"으로 잡아야** 하며, 파이썬 최적화의 본질은 **반복을 `sum`·`map`·`join` 같은 C 구현 내장 함수에 떠넘기는 것**이다. 제출 결과는 각각 원인이 정해져 있어서 **틀렸습니다는 경계값·초기값·출력 형식**, **시간 초과는 입출력→자료구조→재계산→복잡도 순서**, **런타임 에러는 재귀 깊이·인덱스·0으로 나누기**를 먼저 뒤진다. 대부분 **PyPy3**가 유리하지만 **메모리가 빡빡하거나 깊은 재귀·큰 정수 연산이면 Python3**가 낫다. 마지막으로 제출 직전 30초 체크리스트에서 **답이 음수인데 초기값 `0`, 남은 디버그 `print`, 재귀 한계 미설정, `input()` 그대로 사용** 이 넷만 확인해도 오답의 상당수가 사라진다.
