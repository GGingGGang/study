# 11 — 네트워크: IP에서 HTTP까지

> 학습 목표: 이름 해석·라우팅·리스닝·TCP·HTTP를 분리해 연결 실패를 진단한다.

## 1. 접속 한 번의 흐름

`https://example.com` 접속은 대략 이름 해석 → 대상 IP에 대한 경로 선택 → TCP 연결 → TLS 협상 → HTTP 요청·응답으로 진행된다. 프록시·캐시·연결 재사용이 있으면 일부 단계가 달라진다. 어느 단계가 실패했는지 구분해야 맞는 설정을 고칠 수 있다.

```text
이름(DNS) → 목적지 IP → 라우팅/인터페이스 → TCP 포트
                                            ↓
                                      TLS → HTTP → 애플리케이션
```

IP 주소는 인터페이스의 주소, 포트는 해당 전송 프로토콜에서 통신 끝점을 구분하는 번호다. CIDR의 `/24`는 IPv4 주소 앞 24비트가 네트워크 부분이라는 뜻이다. 기본 경로는 더 구체적으로 일치하는 경로가 없을 때 선택한다. 라우팅은 단순히 “같은 대역이면 무조건 통신 가능”만으로 설명되지 않는다.

```bash
ip -br addr
ip route
ip route get 1.1.1.1
ss -lnt
```

`ip route get`은 경로 선택을 조회하며 해당 목적지로 HTTP 요청을 보내는 명령은 아니다. IPv6도 사용한다면 `ip -6 route`, `ss -lnt`의 IPv6 소켓을 함께 본다.

## 2. 리스닝 주소의 차이

| 주소 | 일반적 의미 |
|---|---|
| `127.0.0.1` | IPv4 루프백, 같은 네트워크 namespace 내부에서 접근 |
| `0.0.0.0` | 모든 로컬 IPv4 인터페이스에서 수신 |
| 특정 사설 IP | 그 주소에서 수신 |
| `::1` | IPv6 루프백 |
| `::` | IPv6 wildcard, IPv4 동시 수신 여부는 설정 의존 |

`0.0.0.0`은 서버가 어디에서 수신할지 지정할 때 쓰는 wildcard이지 클라이언트의 일반적인 목적지 주소가 아니다. 모든 인터페이스에 바인딩해도 방화벽·라우팅·애플리케이션 인증은 별도다.

## 3. DNS와 시스템 이름 조회

```bash
getent ahosts example.com
dig example.com A
```

네트워크와 도구가 있어야 실행된다. `getent`는 NSS 설정에 따라 `/etc/hosts`, DNS 등을 사용하고 `dig`는 DNS 질의를 보낸다. 그래서 결과가 다를 수 있다. DNS TTL과 캐시도 변경 반영 시간에 영향을 준다. Ubuntu에서 `/etc/resolv.conf`는 systemd-resolved 등이 관리하는 링크일 수 있으므로 덮어쓰기 전에 `resolvectl status`와 링크 대상을 확인한다.

## 4. 일반 실습: 루프백 HTTP 서버

python3가 필요하다. 터미널 A에서 실행하고, 실행 중에는 해당 터미널을 유지한다.

```bash
mkdir -p "$HOME/linux-lab/web"
printf 'hello linux\n' > "$HOME/linux-lab/web/index.html"
python3 -m http.server 18080 --bind 127.0.0.1 --directory "$HOME/linux-lab/web"
```

터미널 B에서 다음을 확인한다.

```bash
ss -lnt '( sport = :18080 )'
curl --noproxy '*' --max-time 3 -i http://127.0.0.1:18080/
curl --noproxy '*' --max-time 3 -i http://127.0.0.1:18080/missing
```

첫 요청은 200과 `hello linux`, 두 번째는 404다. **404도 HTTP 서버에 도달했다는 증거**다. curl은 기본적으로 HTTP 404를 전송 실패로 보지 않을 수 있다. 자동화에서 HTTP 오류를 실패 처리하려면 `--fail` 또는 요구에 맞는 상태 코드 검사를 사용한다. `--noproxy '*'`는 이 로컬 실습에서 프록시 경유를 제외한다. 환경의 외부 통신 정책을 우회하는 용도로 사용하지 않는다.

터미널 A에서 Ctrl+C로 멈춘 후 다시 curl하면 연결 실패가 난다. Python 개발용 서버는 인증·운영용 보안 기능을 갖춘 웹 서버 대체물이 아니므로 이번에는 루프백에만 바인딩한다.

## 5. 관찰과 결론의 범위

| 관찰 | 알 수 있는 것 | 아직 모르는 것 |
|---|---|---|
| ping 성공 | ICMP 왕복 가능 | TCP 포트·HTTP 정상 여부 |
| TCP 연결 거부 | 즉각적인 거부 응답 | 리스너 부재인지 방화벽 reject인지 |
| 연결 시간 초과 | 제한 시간 내 연결 불가 | 경로·drop·서버 문제 중 어느 것인지 |
| TLS 오류 | TLS 단계에서 실패 | 시각·인증서·이름·신뢰 체인 원인 |
| HTTP 500 | 서버가 오류 응답 | 애플리케이션 내부 원인 |

`curl -v --connect-timeout 3 --max-time 10 URL`은 단계 확인에 유용하다. TLS 실패를 만났다고 바로 검증을 끄지 말고 접속 이름, 인증서 유효 기간, 시스템 시각, 신뢰 체인을 확인한다. `ss -lntp`의 프로세스 정보는 다른 사용자의 소켓이면 관리자 권한이 필요할 수 있다.

## 연습문제와 해설

1. 서버 안 curl은 되는데 외부에서 안 된다면? → 바인딩 주소부터 확인하고 서버 방화벽·클라우드 보안 규칙·라우팅을 나눠 조사한다.
2. IP로는 되고 이름으로 안 된다면? → 이름 해석을 의심하되 HTTPS 이름·인증서·Host 기반 라우팅 차이도 고려한다.
3. ping 실패만으로 서버 다운을 확정할 수 있는가? → ICMP가 차단될 수 있어 확정할 수 없다. 필요한 프로토콜을 직접 검사한다.
