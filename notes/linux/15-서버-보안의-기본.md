# 15 — 서버 보안의 기본: 노출과 권한을 줄이기

> 학습 목표: 인증·권한·네트워크 정책·업데이트를 별개로 점검하고 변경 후 접속을 검증한다.

## 1. 먼저 서버의 역할을 적는다

보안 설정은 무조건 많은 제한을 켜는 작업이 아니다. 서버가 제공할 기능, 접속할 주체, 보관할 데이터, 복구 방법을 정한다. 개발용 HTTP 서버라면 루프백만으로 충분할 수 있고, 공개 서비스라면 TLS와 애플리케이션 인증·프록시·운영 로그가 추가로 필요하다.

```bash
id
ss -lntup
systemctl --failed
```

열린 포트와 필요한 서비스 목록을 비교한다. `ss`는 리스닝 상태를 보여 주지만 외부에서 도달 가능한지까지 증명하지 않는다. 호스트 방화벽과 클라우드 보안 규칙, NAT, 라우팅도 확인해야 한다. 프로세스 정보는 권한에 따라 생략될 수 있다.

## 2. 최소 권한은 실행 파일의 소유권까지 포함한다

서비스는 필요한 데이터만 읽고 쓰는 계정으로 실행한다. 실행 계정이 서비스 코드와 unit을 수정할 수 있으면 재시작 때 다른 코드를 실행하게 만들 수 있다. `/etc/systemd/system`과 배포 코드의 쓰기 권한을 점검하고 데이터 저장 경로를 분리한다.

`NoNewPrivileges=yes`, `ProtectSystem=`, `ProtectHome=`, `PrivateTmp=` 같은 systemd 제한은 피해 범위를 줄이는 데 도움이 된다. 기능과 충돌할 수 있으므로 지원되는 항목을 확인하고 파일 읽기·쓰기·네트워크 기능을 실제로 검증한다. 제한을 한꺼번에 넣고 실행만 되면 끝이라고 판단하지 않는다.

## 3. 방화벽은 어떤 연결을 허용하는가

Ubuntu에서 UFW는 netfilter 정책을 관리하는 도구다. RHEL 계열은 firewalld를 많이 사용한다. 둘 다 실제 서비스의 인증을 대신하지 않는다. 책에서는 원격 접속 차단을 피하기 위해 방화벽 활성화를 자동 실습하지 않는다.

```bash
sudo ufw status verbose
```

UFW가 설치된 환경에서 현재 상태를 조회한다. 활성화해야 하는 상황이라면 콘솔 복구 경로를 확보하고, 현재 SSH 포트와 허용할 출발지·프로토콜을 확인한 뒤 규칙을 검토한다. 클라우드 인바운드 규칙도 별도다. **설정 후 기존 세션 유지 + 새 세션 접속 성공**으로 검증한다. IPv4만 보지 말고 IPv6 노출도 확인한다.

## 4. DAC 외에 SELinux·AppArmor도 있다

일반 rwx와 ACL은 전통적 임의 접근 제어(DAC)에 해당한다. SELinux와 AppArmor는 정책에 따라 프로세스의 접근을 더 제한하는 MAC 기능이다. 파일이 644인데 거부된다면 상위 경로·실행 사용자·마운트·MAC 정책을 함께 본다.

- Ubuntu에서는 `sudo aa-status`로 AppArmor 상태를 확인할 수 있다.
- SELinux 환경에서는 `getenforce`와 감사 로그, 파일·프로세스 보안 문맥을 확인한다.
- 서비스가 요구하는 경로와 정책의 기대 경로가 맞는지 확인한다.

문제 해결의 첫 조치로 전체 정책을 끄지 않는다. 거부 기록으로 필요한 접근을 파악하고 배포판의 정책 관리 절차로 수정한다. Docker 사용을 위해 사용자를 docker 그룹에 넣는 것도 단순 편의 설정으로 보지 않는다. 일반적인 rootful Docker에서 그 그룹은 호스트의 높은 권한으로 이어질 수 있다.

## 5. 패치, 비밀, 백업

패키지 보안 업데이트의 적용과 서비스 재시작·커널 재부팅 필요 여부를 함께 관리한다. “설치한 버전 번호가 낮다”만으로 취약 여부를 단정하지 않는다. 배포판은 보안 수정을 이전 버전에 backport할 수 있으므로 배포판 보안 공지를 확인한다.

비밀은 Git 저장소·명령행·로그에 남기지 않는다. `.gitignore`는 앞으로의 추적 제외를 돕지만 이미 커밋한 비밀을 회수하지 못한다. 노출했다면 실제 자격 증명을 폐기·회전하고 영향 범위를 조사한다. 파일 권한 600도 root나 해당 계정으로 실행되는 공격까지 막는 것은 아니다.

백업에는 데이터 자체뿐 아니라 계정·권한·접속 정보가 포함될 수 있다. 저장소 분리와 접근 통제를 적용하고 복구 절차를 주기적으로 실행한다. 보호 수단이 복원을 막지 않는지도 확인한다.


## 연습문제와 해설

1. 포트를 숨기거나 번호를 바꾸면 SSH 인증이 필요 없는가? → 아니다. 노출량을 일부 줄일 수 있어도 인증·패치·권한 관리를 대체하지 않는다.
2. 방화벽에서 허용하면 프로그램이 자동으로 리스닝하는가? → 아니다. 정책과 실제 소켓은 다른 상태다.
3. AppArmor를 끄니 동작한다. 수정 완료인가? → 아니다. 거부된 동작을 좁혀 필요한 정책을 검토하고 다시 활성 상태에서 검증한다.
