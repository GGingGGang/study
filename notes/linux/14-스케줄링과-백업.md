# 14 — 스케줄링과 백업: 실행보다 복원이 기준이다

> 학습 목표: tar 백업과 복원을 검증하고 cron·systemd timer의 실행 환경을 이해한다.

## 1. 백업은 다른 이름의 파일 한 개로 끝나지 않는다

원본과 같은 디스크에 만든 압축 파일은 실수 복구 연습에는 좋지만 디스크 고장에는 함께 사라진다. 운영 백업은 별도 매체·위치, 버전 보존, 접근 제어, 암호화, 복원 시간을 함께 설계한다. **RPO**는 감당 가능한 데이터 손실 시점, **RTO**는 복구까지 허용하는 시간이다.

실행 중 DB의 데이터 디렉터리를 tar로 묶는 것만으로 일관된 백업이 보장되지 않는다. DB가 제공하는 논리·물리 백업과 로그 복구 절차를 사용한다. 이번 실습은 정적인 학습 파일만 대상으로 한다.

## 2. 일반 실습: 만들고 별도 경로에 복원하기

```bash
mkdir -p "$HOME/linux-lab/backup-demo/source"
cd "$HOME/linux-lab/backup-demo"
printf 'important data\n' > source/note.txt
tar -czf sample.tar.gz -C source .
tar -tzf sample.tar.gz
mkdir -p restored
tar -xzf sample.tar.gz -C restored
diff -r source restored
```

`-c` 생성, `-x` 추출, `-t` 목록, `-z` gzip, `-f` 아카이브 이름이다. `-C`는 tar가 작업할 디렉터리를 바꿔 절대 경로를 저장하지 않게 한다. 마지막 diff가 출력 없이 0으로 끝나면 내용이 같다. 원본 위에 바로 풀지 말고 빈 복원 경로에서 검증한다. 신뢰하지 않는 아카이브는 경로·링크를 검토하고 관리자 권한으로 풀지 않는다.

소유권·ACL·확장 속성·하드 링크 등 보존 요구가 있으면 도구 옵션과 복원 권한까지 테스트한다. `sha256sum`은 동일성 확인에 도움이 되지만 체크섬 파일도 공격자가 함께 바꿀 수 있다면 출처 인증을 대신하지 못한다.

## 3. 실습용 백업 스크립트

[backup.sh](./labs/backup.sh ':ignore')는 **기존 원본 디렉터리**와 **별도 출력 디렉터리**를 인수로 받는다. GNU 도구와 Bash를 기준으로 작성했다. 저장소 루트에서 다음처럼 실행한다.

```bash
bash notes/linux/labs/backup.sh \
  "$HOME/linux-lab/backup-demo/source" \
  "$HOME/linux-lab/backups"
```

표준 출력 한 줄이 생성된 아카이브의 전체 경로다. 소스 코드를 열어서 다음 동작을 확인한다.

1. 인수 수, 원본 존재 여부, 출력 경로를 검증한다.
2. `/` 전체 또는 원본 안으로 출력하는 요청을 거부한다. 아카이브가 자기 자신을 포함하는 것을 방지한다.
3. umask 077로 새 백업의 접근을 제한하고 고유 임시 파일에 기록한다.
4. tar 생성·gzip 무결성·아카이브 목록 읽기를 확인한다.
5. 성공하면 최종 이름으로 변경하고 실패·중단 시 임시 파일을 정리한다.

이 스크립트는 권한 없는 파일을 강제로 읽거나 오래된 백업을 자동 삭제하지 않는다. `trap`은 SIGKILL·전원 종료를 처리할 수 없어 비정상 종료 후 `.partial-` 파일이 남을 수 있다. 라이브 데이터 일관성, 다른 디스크로의 복제, 동시 원본 변경, 적대적인 공유 디렉터리의 경로 경쟁까지 해결하는 운영 백업 시스템은 아니다. 개인 학습 디렉터리에서 사용한다.

### 복원 검증

```bash
archive=$(bash notes/linux/labs/backup.sh \
  "$HOME/linux-lab/backup-demo/source" "$HOME/linux-lab/backups")
status=$?
printf 'backup status=%s\n' "$status"
```

status가 0인 것을 확인한 뒤, 새로운 빈 디렉터리에서 복원한다.

```bash
restore_dir=$(mktemp -d "$HOME/linux-lab/restore.XXXXXXXX")
tar -xzf "$archive" -C "$restore_dir"
diff -r "$HOME/linux-lab/backup-demo/source" "$restore_dir"
```

실패했는데 뒤의 복원 명령을 계속 실행하지 않는다. 자동화할 때는 if로 성공과 실패 경로를 분기한다.

## 4. cron의 다섯 시간 필드

`crontab -e`는 현재 사용자의 crontab을 편집한다. 아래는 등록 전 검토용 예시이며 `/home/사용자`를 실제 절대 경로로 바꿔야 한다. 실습 경로에 공백이 있다면 인용도 유지한다.

```cron
# 분 시 일 월 요일  명령
15 2 * * * /bin/bash /home/사용자/study/notes/linux/labs/backup.sh /home/사용자/linux-lab/backup-demo/source /home/사용자/linux-lab/backups >> /home/사용자/linux-lab/backup.log 2>&1
```

일반적으로 매일 02:15에 실행하며 시간대는 cron 구현과 설정을 확인한다. 일(day-of-month)과 요일(day-of-week)을 둘 다 제한할 때는 보통 OR 규칙이 적용되므로 확인한다. cron에는 대화형 PATH·작업 디렉터리를 기대하지 않는다. `%`는 cron 명령부에서 특별 취급될 수 있다.

`crontab -l`로 등록을 확인한다. 실습 종료 시 해당 행만 편집해서 제거한다. `crontab -r`은 전체를 지우므로 정리용으로 사용하지 않는다. 실행 시간이 주기보다 길면 겹칠 수 있어 필요하면 `flock` 등으로 중복 실행을 제어한다.

## 5. systemd timer

timer는 실행 시점과 서비스 실행을 나눠 관리하며 journal·상태 조회와 연동된다. `OnCalendar=`는 달력 기반, `OnBootSec=` 등은 단조 시간 기반이다. 달력 타이머의 `Persistent=true`는 비활성 중 놓친 실행을 다시 활성화할 때 처리하는 데 쓰이며 놓친 매번을 전부 재생한다는 뜻은 아니다.

```bash
systemd-analyze calendar '*-*-* 02:15:00'
systemctl list-timers --all
```

이 책에서는 기존 스케줄을 변경하지 않고 표현식과 목록을 관찰한다. 운영 등록에는 실행 사용자, PATH, 소스 접근 권한, 로그·실패 알림을 함께 설계한다.

## 연습문제와 해설

1. tar 생성이 성공하면 복원도 보장되는가? → 아니다. 필요한 파일·권한·일관성과 실제 복원까지 검증해야 한다.
2. 백업 출력을 원본 하위에 두면 왜 곤란한가? → 백업 파일 자신과 이전 아카이브를 다시 읽는 재귀적 포함이 생길 수 있다.
3. 매일 백업 성공 로그가 있는데 파일이 없다면? → 실행 사용자·절대 경로·종료 상태·로그가 어느 실행의 것인지 확인한다. 존재뿐 아니라 복원 가능성도 점검한다.
