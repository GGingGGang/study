# 16 — 컨테이너를 이해하는 리눅스

> 학습 목표: namespace·cgroup·capability를 앞 장의 프로세스·네트워크·파일 개념과 연결한다.

## 1. 컨테이너도 프로세스다

일반적인 Linux 컨테이너는 호스트 커널 위에서 실행되는 프로세스 집합이다. VM은 별도의 게스트 커널을 실행하지만 컨테이너는 주로 namespace로 보이는 자원을 분리하고 cgroup으로 자원을 관리한다. Docker Desktop 등은 내부 VM을 사용할 수 있어 “컨테이너가 공유하는 커널”은 그 Linux VM 커널일 수 있다.

이미지의 사용자 공간이 Ubuntu여도 `uname -r`은 이미지에 설치된 커널이 아니라 실제 실행 커널을 보여 준다. 컨테이너에서 apt로 일반 패키지를 설치하는 것과 호스트 커널 교체는 별개다.

## 2. 격리와 제한은 다른 역할이다

| 기능 | 나누거나 제한하는 대상 | 앞 장과의 연결 |
|---|---|---|
| PID namespace | 프로세스 ID의 보기 | 컨테이너 PID 1과 호스트 PID가 다름 |
| mount namespace | 마운트의 보기 | 같은 경로가 다른 파일을 가리킬 수 있음 |
| network namespace | 인터페이스·라우트·포트 | localhost는 그 namespace 내부 |
| UTS namespace | 호스트명 등 | 컨테이너별 이름 |
| user namespace | UID/GID 매핑 | 내부 root와 외부 UID 매핑이 다를 수 있음 |
| cgroup | 자원 회계·제한·분배 | 메모리·CPU·프로세스 수 관리 |
| capability | root 권한의 세분화 | 네트워크 관리 등 특정 특권 |

namespace를 나눴다고 CPU 사용량이 제한되는 것은 아니다. cgroup 메모리 한도에 걸리면 호스트 전체 메모리에 여유가 있어도 컨테이너 프로세스가 OOM으로 종료될 수 있다. CPU quota로 throttling이 생기면 실행 속도가 느려져도 호스트 사용률이 꽉 차 보이지 않을 수 있다.

## 3. Docker 없이 현재 상태 관찰하기

다음 명령은 현재 환경의 상태를 읽는다. 일반 VM에서도 실행 가능하지만 보이는 경로와 권한은 다를 수 있다.

```bash
ls -l /proc/self/ns
cat /proc/self/cgroup
findmnt -t cgroup,cgroup2
```

namespace 링크의 숫자는 해당 namespace를 식별한다. 다른 프로세스와 같은 namespace인지 비교하는 데 사용할 수 있다. cgroup v2에서는 통합 계층을 사용한다. `cpu.max`, `memory.max`, `memory.events` 같은 파일은 컨트롤러와 위임 상태에 따라 해당 cgroup 경로에서 확인한다. 이번 장에서는 값을 쓰지 않는다.

## 4. localhost가 헷갈리는 이유

컨테이너 A의 `127.0.0.1`은 보통 A가 속한 network namespace다. 별도 namespace를 쓰는 B나 호스트가 아니다. 포트를 호스트에 publish하는 기능은 이 사이의 전달을 구성한다. 컨테이너 안의 프로세스가 127.0.0.1에만 바인딩하면 publish했다고 외부 인터페이스에서 수신하는 것과 같아지지 않는다.

Kubernetes Pod 안의 컨테이너들은 보통 network namespace를 공유하므로 localhost로 통신할 수 있다. 서로 다른 Pod는 같은 의미가 아니다. Service 이름의 DNS, 대상 endpoint, 대상 포트, 애플리케이션 리스닝을 나눠 조사하는 습관은 11장의 계층별 진단과 같다.

## 5. 파일과 권한도 그대로 연결된다

bind mount나 volume은 이미지 안의 경로를 다른 데이터로 가릴 수 있다. 이미지에 파일이 있었는데 실행 후 사라져 보이면 mount를 확인한다. 호스트 디렉터리의 UID/GID와 컨테이너 프로세스의 ID·매핑이 맞지 않으면 접근이 거부될 수 있다. 무조건 777로 바꾸기 전에 실제 숫자 ID를 확인한다.

이미지의 writable layer에만 쓴 데이터는 컨테이너 재생성 시 보존을 기대할 수 없다. 필요한 데이터는 volume 등 수명 정책을 정하고 백업한다. 로그는 stdout/stderr 수집 정책과 회전 정책을 확인한다.

## 6. PID 1과 종료

컨테이너의 PID 1은 자식 회수와 시그널 처리에서 주의가 필요하다. 셸 래퍼가 애플리케이션에 종료 시그널을 전달하지 못하면 정상 종료가 지연될 수 있다. 단순 래퍼에서는 마지막 명령을 `exec 프로그램`으로 교체하는 방식이 유용하며 여러 프로세스를 관리하면 적절한 init·감독 구조를 검토한다.

컨테이너 내부 root가 언제나 호스트 root와 완전히 같은 것은 아니지만, 그 사실을 안전 보장으로 삼으면 안 된다. user namespace·capability·마운트·런타임 설정에 따라 영향이 달라진다. `--privileged`나 호스트 관리 소켓 전달은 강한 권한을 제공하므로 목적과 범위를 명확히 한다.

## 연습문제와 해설

1. 컨테이너의 메모리 부족인데 호스트 free는 여유롭다. 가능한가? → cgroup 한도 때문에 가능하다. 메모리 이벤트와 설정을 본다.
2. 호스트와 컨테이너가 같은 경로 문자열을 읽으면 같은 파일인가? → mount namespace와 마운트에 따라 다르다.
3. Kubernetes 서비스 장애에 리눅스가 필요한 이유는? → 최종적으로 프로세스·소켓·경로·권한·자원 한도로 동작하기 때문이다.
