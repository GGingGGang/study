# 17 — 트러블슈팅 훈련: 6가지 장애를 순서대로 조사하기

> 학습 목표: 증상과 원인을 구분하고, 관찰 → 가설 → 검증 → 최소 수정 → 재검증을 기록한다.

## 1. 공통 조사 순서

장애가 나면 먼저 발생 시각·영향 범위·최근 변경·정상 기준을 적는다. 운영 중에는 복구가 먼저일 수 있지만 가능하면 재시작 전에 로그와 상태를 보존한다. 한 번에 여러 설정을 바꾸면 어떤 변경이 원인인지 알기 어려워진다.

```text
증상: 특정 요청이 언제부터 어떻게 실패하는가?
관찰: 명령, 출력, 종료 상태, 시각은 무엇인가?
가설: 이 관찰을 설명하는 원인은 무엇인가?
검증: 다른 원인과 구분할 가장 작은 확인은 무엇인가?
수정: 어떤 변경을 왜 하는가? 되돌리는 방법은?
재검증: 원래 실패한 요청과 관련 기능이 정상인가?
```

## 2. 파일을 읽지 못한다

**증상:** 서비스가 설정 파일을 열지 못한다.

1. 오류가 “없음”인지 “접근 거부”인지 정확히 읽는다.
2. 서비스 실행 사용자와 실제 경로를 확인한다. 상대 경로라면 작업 디렉터리도 본다.
3. `ls -l 파일`, `namei -l /전체/경로`로 각 상위 디렉터리의 x 권한을 확인한다.
4. ACL, 읽기 전용 마운트, AppArmor·SELinux, systemd의 ProtectHome 등을 조사한다.
5. 필요한 읽기·탐색 권한만 고친 뒤 **실제 서비스 계정**으로 다시 검증한다.

관리자 계정의 `cat` 성공은 서비스 계정의 접근 성공을 증명하지 않는다. 프로그램이 접근 거부를 404 등 다른 메시지로 표현할 수도 있으므로 로그와 경로 상태를 함께 본다.

## 3. 서비스가 시작되지 않는다

**증상:** `systemctl start`가 실패한다.

```bash
systemctl status 서비스명 --no-pager
sudo journalctl -u 서비스명 -b -n 50 --no-pager
systemctl cat 서비스명
```

위 `서비스명`은 대상 unit으로 바꾸는 자리표시자다. 실행 파일·인수·사용자·WorkingDirectory·환경을 확인하고, 포트 사용 충돌과 의존성도 본다. 실행 경로가 틀렸다면 재시작 횟수를 늘려도 해결되지 않는다. restart 제한에 걸렸다면 원인을 고친 뒤 필요할 때 `reset-failed`하고 다시 시작한다.

## 4. HTTP 접속이 안 된다

**증상:** 브라우저에서 사이트를 열 수 없다.

1. 서버 로컬에서 `ss -lntp`로 주소·포트를 확인한다.
2. 루프백이나 실제 바인딩 주소에 curl을 보내고 TCP·TLS·HTTP 어느 단계인지 분리한다.
3. 로컬이 정상이면 클라이언트에서 DNS, 경로, 방화벽·클라우드 규칙을 확인한다.
4. HTTP 오류 응답이면 웹 서버·프록시·애플리케이션·의존 서비스 로그로 좁힌다.

404에 대해 방화벽을 바꾸거나, 이름 해석 실패에 대해 웹 서버를 재시작하는 것은 증거와 맞지 않는 조치다. 실패 지점을 먼저 찾는다.

## 5. 디스크 공간이 부족하다

```bash
df -h /문제/경로
df -i /문제/경로
du -xhd1 /문제/경로
sudo lsof +L1
```

경로는 실제 대상으로 바꾼다. `du -x`는 다른 파일시스템으로 내려가지 않는다. 서비스가 계속 기록하는 파일을 임의로 지우지 말고 데이터 유형·보존 정책·열린 파일 여부를 확인한다. `lsof +L1`은 링크 수가 1 미만인 열린 파일을 찾는 데 도움이 된다. 공간이 급해도 DB·패키지 관리 파일을 크다는 이유만으로 삭제하지 않는다.

## 6. 스크립트가 수동 실행에서만 된다

**증상:** 터미널에서는 성공하지만 cron·systemd에서는 실패한다.

실행 사용자, PATH, 작업 디렉터리, 인터프리터, 환경변수, 읽기·쓰기 경로를 비교한다. crontab이 해당 사용자에게 등록됐는지, stdout/stderr가 어디로 가는지, 이전 작업과 겹치는지도 확인한다. 비대화형 환경에는 입력 프롬프트를 기대하지 않는다.

최소한의 환경에서 실행하는 방법도 있지만 필요한 변수까지 제거하면 새로운 오류를 만들 수 있다. 실제 서비스 환경을 명시적으로 구성하고 동일 조건에서 재현한다. 디버깅 출력에 비밀 값을 남기지 않는다.

## 7. 프로세스가 갑자기 사라졌다

애플리케이션 자체 종료, 서비스 관리자 정책, 관리 작업, 시그널, OOM 등 여러 가능성이 있다. 종료 코드와 서비스 journal, 커널 OOM 기록, 배포·재시작 시각, cgroup 한도를 비교한다. `137`은 흔히 SIGKILL의 셸 상태 표현이지만 **OOM이라고 단정할 수 없다**. 누가 어떤 이유로 SIGKILL을 보냈는지는 별도 증거가 필요하다.

## 훈련 문제와 해설

1. 파일 644, 부모 디렉터리 700, 서비스 계정은 다른 사용자다. 무엇을 먼저 보는가?
   - 부모의 탐색 권한이다. 파일에 777을 줘도 부모 접근이 막히면 해결되지 않는다.
2. 서버의 curl은 200인데 외부는 timeout이다. 애플리케이션 버그라고 확정할 수 있는가?
   - 아니다. 바인딩 주소, 외부 경로, 각 방화벽 계층을 조사한다.
3. 백업 로그의 마지막 줄이 성공인데 오늘 백업이 없다. 충분한 증거인가?
   - 로그의 실행 시각과 해당 실행의 종료 상태, 출력 경로를 확인해야 한다. 이전 실행의 성공일 수 있다.
4. 재시작 뒤 정상이다. 보고서에는 무엇을 남기는가?
   - 복구 시각과 영향, 확보한 관찰, 미확정 원인, 재발 시 수집할 정보와 후속 조치를 구분한다.
