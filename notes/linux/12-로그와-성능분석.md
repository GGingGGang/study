# 12 — 로그와 성능 분석: 숫자로 가설 세우기

> 학습 목표: 시간·로그·CPU·메모리·I/O 관찰을 연결하고 한 가지 수치만으로 결론 내리지 않는다.

## 1. 장애 기록에는 시간이 먼저다

“느리다”는 관찰을 시작 시각, 대상 요청, 정상 기준, 발생 범위로 구체화한다. 여러 서버의 로그를 비교할 때는 시간대와 동기화 상태가 맞아야 한다.

```bash
date --iso-8601=seconds
timedatectl status
uptime
```

최소 환경에는 timedatectl이 없을 수 있다. 서비스 로그는 journal, 파일, 중앙 수집 시스템 중 어디에 있는지 확인한다. `journalctl` 조회 범위는 권한에 따라 제한될 수 있으므로 시스템 로그에는 sudo가 필요할 수 있다.

```bash
sudo journalctl -b -p warning --no-pager -n 50
sudo journalctl -k -b --no-pager -n 50
```

`-b`는 현재 부팅, `-k`는 커널 로그다. `-p warning`은 warning 이상 심각도의 항목을 선택한다. 정보 수준으로 기록된 유용한 진단도 있으므로 이것만으로 모든 문제를 찾을 수는 없다. 서비스 단위와 시간 범위를 지정해 좁힌다.

## 2. CPU와 load average

```bash
uptime
getconf _NPROCESSORS_ONLN
vmstat 1 5
ps -eo pid,comm,%cpu,%mem --sort=-%cpu | head -n 10
```

Linux load average는 실행 가능한 작업과 인터럽트 불가 대기 작업 등을 반영한 1·5·15분 지표다. CPU 사용률 그 자체가 아니다. 코어 수가 다른 시스템에서 같은 load를 동일하게 판단하지 않는다. I/O 대기 때문에 load가 높을 수도 있다.

`vmstat`의 첫 보고는 대체로 부팅 이후 평균이 섞여 있으므로 이후 구간을 함께 본다. `r`은 실행 대기, `b`는 블록 대기, `us/sy/id/wa`는 사용자·커널·유휴·I/O 대기 관련 CPU 시간이다. `ps %CPU`도 순간 CPU 게이지가 아니라 프로세스 수명 기준 비율이므로 top 등의 구간 지표와 다를 수 있다.

## 3. 메모리는 free 하나로 판단하지 않는다

```bash
free -h
vmstat 1 5
```

리눅스는 남는 메모리를 캐시로 활용한다. `free`가 적어도 캐시 회수 등을 고려한 `available`이 충분하면 곧바로 메모리 부족이라고 할 수 없다. 반대로 swap 사용량이 존재한다는 사실만으로 현재 스왑 입출력이 심하다고 판단하지 않는다. `vmstat`의 `si/so`와 지연, 추세를 함께 본다.

RSS는 프로세스가 사용하는 상주 메모리 지표지만 공유 페이지 때문에 여러 프로세스의 RSS 합이 실제 물리 사용량과 일치하지 않을 수 있다. 가상 메모리(VSZ)는 예약된 주소 공간도 포함하므로 그대로 실제 RAM 사용량으로 읽지 않는다.

갑자기 종료된 프로그램은 애플리케이션 오류뿐 아니라 OOM kill 가능성도 조사한다. 커널 journal에서 OOM 관련 기록, 서비스의 종료 원인, 컨테이너·cgroup의 메모리 한도를 함께 확인한다.

## 4. 디스크 I/O와 파일 공간

```bash
df -h
df -i
iostat -xz 1 3
```

`iostat`는 sysstat 패키지에 있다. 첫 보고는 부팅 이후 집계일 수 있으므로 이후 구간을 비교한다. 처리량·요청 지연·큐를 함께 본다. `%util=100`만으로 모든 SSD·RAID·가상 장치가 한계 성능이라고 단정하지 않는다. 장치의 병렬성과 가상화 계층에 따라 해석이 달라진다.

공간 부족과 I/O 지연도 다르다. 디스크 사용률 90%가 곧 90%의 I/O 부하를 뜻하지 않는다. 서비스가 쓰는 경로의 소속 파일시스템과 실제 지연 구간을 확인한다.

## 5. 로그를 남기고 회전시키기

`tail -F 파일`은 이름을 따라가며 파일 교체를 고려하고, `tail -f`는 기본적으로 열린 파일 디스크립터를 따른다. 로그 회전 시 차이가 나타날 수 있다. journal의 영구 저장 여부와 보존량은 journald 설정에 따라 다르므로 재부팅 전 로그가 항상 남는다고 가정하지 않는다.

텍스트 로그는 보통 logrotate와 프로그램의 재열기 동작을 조합한다. 파일 이름만 바꿔도 프로그램이 새 파일을 자동으로 여는 것은 아니다. 열린 삭제 파일이 크다면 프로그램이 지원하는 로그 재열기 절차를 확인한다. 로그에는 토큰·암호·개인정보를 남기지 않도록 설계한다.

## 실습: 관찰 보고서와 해설

부하를 인위적으로 만들지 말고 현재 환경에서 다음을 기록한다.

1. CPU 개수, load average, 가장 CPU를 많이 사용한 프로세스.
2. available 메모리, swap 사용량, `si/so`가 관찰 구간에 발생했는지.
3. 홈 경로의 파일시스템, 블록과 inode 사용률.
4. 최근 warning 한 건의 시각과 추가 조사가 필요한 이유.

모범 결론은 “현재 5초 관찰에서 swap 입출력은 없었고 available 메모리가 이 정도였다”처럼 **관찰 기간과 범위**를 포함한다. “메모리는 항상 정상”처럼 증거보다 넓은 결론은 피한다.

## 연습문제와 해설

1. load가 높은데 CPU가 여유롭다. 가능한 이유는? → D 상태 작업과 I/O 대기를 조사한다. 단일 코어 병목이나 수집 시점 차이도 확인한다.
2. swap 사용량이 1GB면 지금 디스크 병목인가? → 누적된 사용량만으로는 모른다. 현재 si/so와 지연을 봐야 한다.
3. 재시작으로 증상이 사라졌으면 원인 분석은 끝인가? → 복구와 원인 규명은 다르다. 재발을 위해 로그·지표·변경 기록이 필요하다.
