# 03 — 셸과 입출력: 인용, 확장, 파이프

> 학습 목표: 셸이 인수를 만드는 과정을 이해하고, 표준 출력·오류와 종료 상태를 구분한다.

## 1. 프로그램이 받는 것은 명령 문자열 전체가 아니다

Bash는 입력을 문법에 따라 나누고 변수·와일드카드 등을 확장한 뒤 프로그램에 인수 목록을 전달한다. 따라서 입력한 글자와 프로그램이 받는 인수는 다를 수 있다. **데이터로 전달할 문자열은 큰따옴표로 감싼다**는 습관부터 만든다.

```bash
name='Linux learner'
printf '<%s>\n' "$name"
printf '<%s>\n' $name
printf '%s\n' '$name'
```

첫 명령은 `<Linux learner>` 한 줄, 두 번째는 `<Linux>`와 `<learner>` 두 줄이다. 인용하지 않은 변수는 이 예에서 공백으로 나뉜다. 작은따옴표 안에서는 변수도 확장하지 않아 마지막은 `$name` 그대로 출력한다.

| 표기 | 동작 | 예 |
|---|---|---|
| `'문자열'` | 내용 그대로 | 정규식·고정 문자열 |
| `"문자열"` | 변수·명령 치환 허용, 단어 분리·경로 확장 억제 | `"$HOME/a b.txt"` |
| `*`, `?`, `[...]` | 파일 이름 패턴(glob) | `*.log` |
| `$(명령)` | 표준 출력을 문자열로 치환 | `today=$(date +%F)` |

glob은 정규식과 다르다. glob의 `*`는 파일 이름의 여러 문자이고 정규식의 `*`는 앞 표현의 반복이다. Bash 기본 설정에서 glob이 일치하지 않으면 `*.log` 문자열이 그대로 남을 수 있다. 파일 목록이 비어 있는 경우까지 다뤄야 하는 자동화에서는 `find`나 `nullglob`의 의미를 검토한다.

## 2. 파일 디스크립터와 리다이렉션

프로그램의 기본 FD는 0(stdin), 1(stdout), 2(stderr)다. 셸은 프로그램 실행 전에 이 연결을 바꾼다.

```bash
mkdir -p "$HOME/linux-lab/io"
cd "$HOME/linux-lab/io"
printf 'first\n' > out.txt
printf 'second\n' >> out.txt
cat < out.txt
ls /etc/hosts /definitely-not-here > ok.txt 2> error.txt
cat ok.txt
cat error.txt
```

`>`는 파일을 만들거나 **기존 내용을 비운다**. `>>`는 뒤에 붙인다. 위 `ls`는 하나를 출력하더라도 실패한 대상이 있으므로 종료 상태가 0이 아니다. stderr를 파일로 보냈다고 실패가 성공으로 바뀌지 않는다.

리다이렉션은 왼쪽부터 적용된다. 두 스트림을 같은 파일에 모으려면 다음처럼 쓴다.

```bash
ls /etc/hosts /definitely-not-here > combined.txt 2>&1
```

`2>&1`은 “이 시점의 stdout과 같은 대상으로 stderr를 연결”한다. 순서를 바꿔 `2>&1 > combined.txt`라고 쓰면 stderr는 기존 터미널에 남는다. `sudo 명령 > /etc/파일`의 `>`는 일반 사용자 셸이 처리하므로 쓰기 권한이 생기지 않는다. 관리자 파일 쓰기는 필요성을 확인한 뒤 `sudo tee` 등을 사용한다.

## 3. 파이프는 데이터를 연결한다

```bash
printf 'pear\napple\npear\n' | sort | uniq -c
```

앞 프로그램의 stdout이 다음 프로그램의 stdin으로 연결된다. 결과는 `apple` 1개, `pear` 2개다. 기본 파이프는 stderr를 전달하지 않는다. 또한 “첫 명령 전체 실행 후 임시 파일을 다음에 전달”하는 구조가 아니라 여러 프로세스가 제한된 버퍼를 통해 동시에 흐름을 주고받을 수 있다.

같은 파일을 읽으면서 덮어쓰는 `sort data.txt > data.txt`는 피한다. 프로그램이 읽기 전에 셸이 파일을 비울 수 있다. 다른 파일에 출력하고 결과를 확인한 뒤 교체한다.

## 4. 성공 여부와 조건 실행

종료 상태 0은 성공이고 0이 아닌 값은 프로그램이 정의한 다른 결과다. 예를 들어 `grep`은 일치가 없으면 1, 실행 오류면 보통 2를 반환한다. 마지막 상태는 `$?`이며 다음 명령이 실행되면 바뀐다.

```bash
false
printf 'status=%s\n' "$?"
true && printf 'success\n'
false || printf 'fallback\n'
```

`&&`는 앞이 성공할 때 다음 명령, `||`는 앞이 실패할 때 다음 명령을 실행한다. 일반적인 `a && b || c`는 완전한 if/else 대체물이 아니다. `a`가 성공해도 `b`가 실패하면 `c`가 실행된다.

기본 Bash 파이프의 상태는 마지막 명령 기준이다. 실패를 전파해야 하는 스크립트에서는 `set -o pipefail`을 검토한다. 그러면 파이프 중 실패가 있을 때 가장 오른쪽의 실패 상태를 돌려준다. 의도적인 조기 종료(`head` 등) 때문에 SIGPIPE가 생기는 경우도 고려한다.

## 실습: 출력과 상태를 별도로 기록하기

```bash
cd "$HOME/linux-lab/io"
ls /definitely-not-here > result.txt 2> failure.txt
status=$?
printf 'exit=%s\n' "$status"
wc -c result.txt failure.txt
```

예상: stdout 파일은 비어 있고 stderr 파일에 설명이 있다. `status`는 0이 아니다. 숫자는 프로그램과 환경에 따라 달라도 이 관계가 핵심이다.

## 연습문제와 해설

1. `echo '$HOME'`과 `echo "$HOME"`의 차이는? → 전자는 글자 그대로, 후자는 홈 경로다.
2. `command 2>/dev/null`은 실패를 없애는가? → 오류 출력만 버린다. 종료 상태는 별도다. 원인 분석 중에는 오류를 보존한다.
3. `cat a.txt | grep ERROR`에서 a.txt가 없어도 기본 파이프 상태로 첫 실패를 판별할 수 있는가? → 일반적으로 불충분하다. 기본 상태는 grep 기준이며 pipefail이나 각 단계 관찰이 필요하다.
