# k6 (부하 + E2E 테스트)

## 1. Why — 왜 쓰는가

Grafana Labs의 load testing 도구. JavaScript로 시나리오 작성, Go로 실행 → 가벼움 + 빠름. 본 프로젝트의 Phase 6-D 테스트 전략 핵심.

**부하 테스트가 필요한 이유**:
- HPA + Pod 패턴이 실제로 동작하는지 검증 (트래픽 폭증 시 스케일 아웃)
- 인스턴스 NIC 또는 NAT Gateway 병목이 어느 RPS에서 시작되는지 측정 (NLB는 hardware-based로 LB 자체 병목 거의 없음)
- P99 latency가 target 만족하는지 객관 측정
- 사고 시뮬레이션 (브로커 죽으면 어떻게 되나)

**대체재**:
- **JMeter**: GUI 기반, 무거움, 학습곡선
- **Gatling**: Scala 기반, 강력하나 학습곡선
- **Locust**: Python 기반, 가벼움
- **k6**: JavaScript + Go 런타임. 가장 가볍고 Grafana 생태계 통합 (Prometheus remote_write, Grafana dashboard).
- 본 프로젝트는 k6 — Grafana 정합 + JavaScript 친숙성.

## 2. Architecture — 어떻게 구성되는가

**k6 실행 방식**:
- **단일 binary**: 로컬 또는 외부 VM에서 실행. 본 프로젝트.
- **k6 operator**: k8s에서 실행. CR로 정의. 대규모 분산 부하용.
- **Grafana Cloud k6**: SaaS, 유료.

**핵심 추상화**:
- **Scenario**: 부하 패턴 (ramp-up, constant, spike 등)
- **VU** (Virtual User): 동시 사용자 시뮬레이션 단위
- **Iteration**: 한 VU의 한 사이클 실행
- **Threshold**: pass/fail 기준 (예: P95 < 500ms)

**실행 위치 결정**:
- 클러스터 내부 (k6 operator): 자기 자신 죽이는 위험. 같은 노드 자원 경합.
- **외부**: 권장. Always Free AMD VM(1/8 OCPU, 1GB) 활용 가능.
- 로컬 머신: 개발 환경 빠른 검증.

## 3. Mechanism — 어떻게 돌아가는가

**실행 흐름**:
1. JavaScript 시나리오 작성 (`script.js`)
2. `k6 run script.js` 실행
3. k6 runtime이 시나리오 파싱 → VU 생성
4. 각 VU가 시나리오의 default 함수 반복 실행
5. 모든 HTTP 요청 메트릭 수집 (latency, status, throughput)
6. Threshold 평가 → pass/fail 결정
7. 결과 stdout + Prometheus remote_write (옵션) + Grafana 대시보드 (옵션)

**부하 패턴 종류**:
- **ramping-vus**: VU 점진 증가/감소
- **constant-vus**: 일정 VU 유지
- **per-vu-iterations**: VU당 정해진 횟수
- **constant-arrival-rate**: 초당 정해진 RPS 유지 (open model)
- **ramping-arrival-rate**: RPS 점진 증가

## 4. Integration — 어떻게 연결하는가

- **OCI Always Free AMD VM** — k6 실행 위치 (권장)
- **Prometheus** — k6 메트릭 remote_write
- **Grafana** — k6 공식 대시보드
- **Jenkins** — staging 배포 후 자동 실행
- **앱 (Login/Core/Batch)** — 부하 대상

**환경 분리**:
- dev/staging만 부하 테스트
- prod는 smoke test 수준 (단순 health check 정도)
- 사유: 단일 노드 풀 + 단일 `app` 환경 → 부하가 운영 트래픽에 영향. NLB는 hardware-based라 LB 자체 병목은 없음.

**시나리오 예시** (Login → Core 흐름):

```javascript
// scenarios/login-core-flow.js
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Trend } from 'k6/metrics';

const loginLatency = new Trend('login_latency');
const coreLatency = new Trend('core_latency');

export const options = {
  scenarios: {
    smoke: {
      executor: 'constant-vus',
      vus: 10,
      duration: '1m',
    },
    load: {
      executor: 'ramping-vus',
      stages: [
        { duration: '2m', target: 50 },   // ramp up to 50
        { duration: '5m', target: 50 },   // stay at 50
        { duration: '2m', target: 0 },    // ramp down
      ],
      startTime: '1m',
    },
  },
  thresholds: {
    'http_req_duration': ['p(95)<500', 'p(99)<1000'],
    'http_req_failed': ['rate<0.01'],
    'login_latency': ['p(99)<300'],
  },
};

export default function () {
  // Login
  const loginRes = http.post('https://login.ggang.cloud/api/login', JSON.stringify({
    username: 'testuser',
    password: 'testpass',
  }), {
    headers: { 'Content-Type': 'application/json' },
  });
  
  check(loginRes, {
    'login status 200': (r) => r.status === 200,
    'login has token': (r) => r.json('token') !== undefined,
  });
  loginLatency.add(loginRes.timings.duration);
  
  const token = loginRes.json('token');
  
  // Core API 호출
  const coreRes = http.get('https://core.ggang.cloud/api/account', {
    headers: { 'Authorization': `Bearer ${token}` },
  });
  
  check(coreRes, {
    'core status 200': (r) => r.status === 200,
  });
  coreLatency.add(coreRes.timings.duration);
  
  sleep(1);  // think time
}
```

**실행**:

## 6. Configuration — 어떤 설정이 있는가

**Threshold 옵션**:
- `http_req_duration: ['p(95)<500']` — P95 latency < 500ms
- `http_req_failed: ['rate<0.01']` — 실패율 < 1%
- `checks: ['rate>0.99']` — check 통과율
- 위반 시 exit code != 0 → CI fail

**Executor 종류**:
- `shared-iterations`: 정해진 횟수를 VU들이 분담
- `constant-vus`: 일정 VU 유지 (closed model)
- `constant-arrival-rate`: 일정 RPS (open model, 부하 정확)
- `ramping-arrival-rate`: RPS 점진 증가
- 본 프로젝트는 ramping-vus + constant-vus 조합

**환경변수**:
- `BASE_URL`, `TEST_USER` 등 동적 주입
- `K6_VUS`, `K6_DURATION` 명령행에서 override

**출력 옵션**:
- stdout (default, table)
- JSON / CSV
- Prometheus remote_write (Grafana 대시보드)
- InfluxDB

## 7. Compatibility — 어떤 호환성이 요구되는가

- **k6 0.50+** (2026-05 권장)
- **Node.js 시나리오 불가**: k6는 자체 JavaScript runtime (Goja, ES6+ 일부 미지원)
- **외부 라이브러리**: k6 내장 모듈 + JSLib (k6-jslib-aws 등)
- **Prometheus remote_write**: experimental, k6 0.42+

## 8. 면접 예상 질문 & 답변

**Q1. 왜 k6를 골랐어요? JMeter 안 쓰고.**
> 세 가지 이유. (1) 가벼움 — k6는 단일 Go binary, JMeter는 JVM + GUI라 무거움. 외부 VM에서 실행해야 하는 본 프로젝트에 적합. (2) JavaScript 시나리오 — 개발자 친숙. (3) Grafana 생태계 통합 — Prometheus remote_write로 메트릭이 본 프로젝트 모니터링 스택에 자동 통합되어 Grafana 대시보드로 시각화. JMeter는 GUI + XML 시나리오 + JVM 부담이 본 프로젝트의 가벼운 self-host 컨셉과 안 맞습니다.

**Q2. k6를 클러스터 외부에서 실행하는 이유는?**
> 클러스터 내부에서 실행하면 자기 자신을 죽일 위험입니다. 부하 테스트는 의도적으로 시스템 자원을 소진시키는데, 같은 노드에 k6 Pod이 떠있으면 (1) k6 Pod 자체가 OOM 되거나, (2) 다른 앱 Pod의 자원을 경합으로 빼앗아서 측정이 부정확. 외부에서 부하 주면 진짜 외부 사용자 트래픽 시뮬레이션이 됨 + LB 병목까지 정확히 측정. 본 프로젝트는 OCI Always Free AMD VM(1/8 OCPU, 1GB)을 k6 실행 전용으로 사용.

**Q3. prod에 부하 테스트 안 하는 이유는?**
> 본 프로젝트는 NLB(L4 TCP passthrough)라 LB 자체 병목은 없지만 (1) 단일 노드 풀 + 단일 `app` 환경이라 부하가 운영 트래픽에 직접 영향, (2) 인스턴스 NIC와 NAT Gateway가 실제 병목 — 부하 테스트가 외부 의존성 호출 막을 수 있음. 그래서 prod는 smoke test(/health, /metrics 확인) 수준. production 환경에서는 별도 staging 클러스터 또는 트래픽 mirroring(Istio mirror filter) 패턴으로 prod 영향 없이 부하 테스트.

**Q4. Closed model vs Open model 차이는?**
> Closed model(constant-vus 등)은 VU가 응답 받고 다음 요청 보내는 방식 — 실제 응답이 늦으면 RPS도 자연 감소. Open model(constant-arrival-rate)은 정해진 RPS를 응답과 무관하게 발사 — 시스템 한계 정확 측정. 본 프로젝트는 일반 부하 테스트는 closed model(constant-vus로 사용자 시뮬레이션), 한계 테스트는 open model(constant-arrival-rate)로 분리.

**Q5. Threshold가 뭐고 왜 중요해요?**
> 부하 테스트의 pass/fail 기준입니다. `http_req_duration: ['p(95)<500']`처럼 P95 latency 500ms 미만 같은 명시적 SLO. 위반 시 k6가 exit code 1로 종료 → Jenkins가 빌드 fail → prod 배포 차단. 결과적으로 성능 회귀(performance regression)를 prod 도달 전에 감지. 본 프로젝트는 staging 배포 후 자동 k6 실행 + threshold 위반 시 prod 배포 차단.

**Q6. k6 메트릭을 Grafana로 어떻게 봐요?**
> `--out experimental-prometheus-rw=http://prometheus/api/v1/write` 옵션으로 k6가 Prometheus에 직접 push. Grafana는 평소처럼 Prometheus DataSource로 메트릭 조회. Grafana Labs 공식 k6 대시보드가 있어서 import만 하면 VU 수, RPS, latency 분포 등 시각화 완료. 본 프로젝트 narrative: "부하 테스트 결과가 일상 모니터링 스택에 자동 통합되어 SRE가 한 곳에서 운영 + 성능 검증".

**Q7. 부하 테스트로 어떤 사고 시나리오 검증하나요?**
> 본 프로젝트의 5가지 시나리오. (1) HPA 검증 — 트래픽 ramp-up 시 Pod replicas가 실제로 늘어나는지. (2) LB 병목 — 어느 RPS에서 LB 10Mbps 도달하는지. (3) DB connection pool 한계 — 동시 connection 증가 시 503 발생 시점. (4) Kafka consumer lag — produce 폭증 시 Batch가 따라잡는지. (5) Pod 재시작 시 in-flight 처리 — rolling update 중 부하 주면서 connection reset 발생 여부. 각 시나리오를 별도 k6 스크립트로 자동화.

**Q8. k6가 OCI VM 단일에서 충분히 큰 부하 주나요?**
> 본 프로젝트는 NLB라 LB 자체 한계는 거의 없지만 (인스턴스 NIC 2 Gbps), 단일 노드 풀 + 24GB RAM 제약상 부하 자체가 클 필요 없습니다. 작은 JSON 응답 기준 수천 RPS는 k6 단일 인스턴스로 충분히 발사 가능. 만약 부하가 부족하면 k6 distributed mode 또는 k6 Operator로 k8s에 분산 실행하지만 본 프로젝트 환경에선 over-engineering. 면접에서 "production 환경에서 대규모 부하 필요하면 k6 Operator로 분산 또는 Grafana Cloud k6 검토" narrative.

**Q9. 부하 테스트 시나리오를 어떻게 설계해요?**
> 세 단계. (1) Smoke test — 10 VU, 1분. 기본 동작 확인. (2) Load test — ramp 50 VU, 5분 유지. 일반 부하. (3) Stress test — 200 VU 이상, 점진 증가. 한계 발견. (4) Spike test — 1초 안에 500 VU 폭증. burst 대응. 본 프로젝트는 smoke + load만 자동 (Jenkins), stress + spike는 수동 (capacity planning 시점). 각 시나리오의 threshold가 다름.

**Q10. k6 결과를 누구한테 보여줘요?**
> 면접 차원에서는 (1) GitHub README에 부하 테스트 결과 그래프 1개 — "이 시스템이 N RPS까지 P99 < 500ms 보장", (2) 트러블슈팅 블로그 1개 — "Flexible LB(L7) 대신 NLB(L4) 선택한 사유 + 부하 측정 narrative", (3) Grafana 대시보드 스크린샷. 운영 차원에서는 SLO/SLI 정의 + error budget 추적의 baseline 데이터. 본 프로젝트의 SLO 99.9%는 k6 측정 기반.
