# 18. 트러블슈팅 I — 클러스터와 노드

> 도메인: 트러블슈팅 (30%) — **최대 배점 영역**
> 시험 포인트: "클러스터/노드 트러블슈팅", "클러스터 컴포넌트 트러블슈팅". 노드 NotReady 복구와 컨트롤 플레인 static pod 오류 찾기가 양대 단골.

---

## 1. 진단의 대원칙

1. **describe의 Events부터 본다** — 답의 80%가 거기 있다
2. 계층 순서로 좁힌다: 클러스터 → 노드 → kubelet/런타임 → Pod → 컨테이너
3. 컨트롤 플레인이 죽어 kubectl이 안 되면 → **노드에서 crictl과 로그 파일**로 내려간다

## 2. 노드 NotReady — 표준 진단 루틴 (암기)

```bash
# 1) 상태와 원인 확인
kubectl get nodes
kubectl describe node node01        # Conditions 섹션 + Events
# Conditions: MemoryPressure / DiskPressure / PIDPressure / Ready
# "Kubelet stopped posting node status" → kubelet 문제일 확률 높음

# 2) 해당 노드 접속
ssh node01

# 3) kubelet 상태
sudo systemctl status kubelet
sudo journalctl -u kubelet -f --no-pager | tail -50    # 에러 메시지 정독

# 4) 원인별 조치
sudo systemctl start kubelet          # 그냥 죽어 있으면
sudo systemctl enable --now kubelet   # 부팅 시 시작 설정까지

# 5) 컨테이너 런타임 확인
sudo systemctl status containerd
sudo crictl ps
```

### kubelet이 시작 실패하는 흔한 원인 (journalctl에서 찾기)
| 로그 단서 | 원인/조치 |
|---|---|
| `failed to load kubelet config file` | `/var/lib/kubelet/config.yaml` 오타/경로 |
| `unable to load client CA file` | 설정 파일 안 인증서 경로 오타 (`/etc/kubernetes/pki/ca.crt`) |
| `connection refused ...:6443` | apiserver 문제 또는 `/etc/kubernetes/kubelet.conf`의 server 주소/포트 오타 |
| `swap on is not supported` | `swapoff -a` |
| `certificate has expired` | 인증서 만료 → `kubeadm certs renew` |
| 실행 파일 경로 오류 | systemd 유닛 파일(`/usr/lib/systemd/system/kubelet.service.d/10-kubeadm.conf`) 확인 후 `systemctl daemon-reload && systemctl restart kubelet` |

### 점검 파일 3종 세트
```bash
/var/lib/kubelet/config.yaml      # kubelet 자체 설정 (staticPodPath, CA 경로...)
/etc/kubernetes/kubelet.conf      # apiserver 접속 kubeconfig (server: https://IP:6443)
/var/lib/kubelet/kubeadm-flags.env  # kubelet 기동 플래그
```

## 3. 컨트롤 플레인 컴포넌트 장애

**증상: kubectl 자체가 안 됨 (`connection refused`)** → apiserver 문제.

```bash
# 컨트롤 플레인 노드에서
ssh controlplane
sudo crictl ps -a | grep -E "apiserver|etcd|scheduler|controller"   # 컨테이너 상태
sudo crictl logs <container-id>                                     # 죽는 이유

# kubectl 없이 로그 보기
ls /var/log/pods/                       # kube-system_kube-apiserver-... 디렉터리
sudo tail -f /var/log/pods/kube-system_kube-apiserver-*/kube-apiserver/*.log
```

### static pod 매니페스트 오류 찾기 (초빈출 유형)
문제 유형: "누군가 apiserver/scheduler 설정을 망가뜨렸다. 고쳐라."
```bash
cd /etc/kubernetes/manifests/
sudo vim kube-apiserver.yaml     # 의심 포인트를 순서대로 확인
```
확인 순서:
1. **이미지 태그** 오타 (`kube-apiserver:v1.35.0` 등)
2. **명령 플래그** 오타 (`--etcd-servers=...` 포트, 인증서 경로)
3. **인증서 경로** — `/etc/kubernetes/pki/` 실제 파일과 대조 (`ls`로 존재 확인)
4. **볼륨/마운트 경로** 오타
5. livenessProbe 포트 오타

수정 후 kubelet이 자동 재기동 (약 30초~1분). 안 올라오면:
```bash
sudo systemctl restart kubelet
watch sudo crictl ps
```

### scheduler / controller-manager 장애 증상 구분
| 증상 | 의심 컴포넌트 |
|---|---|
| Pod가 생성은 되는데 **Pending에 nodeName이 안 붙음** (이벤트도 없음) | kube-scheduler |
| Deployment를 만들어도 **ReplicaSet/Pod가 안 생김**, scale 무반응 | kube-controller-manager |
| kubectl 자체 불통 | kube-apiserver (또는 etcd) |
| apiserver가 crash loop, 로그에 etcd 연결 오류 | etcd |

## 4. etcd 장애

```bash
sudo crictl ps -a | grep etcd
sudo crictl logs <etcd-id>
# 흔한 원인: 데이터 디렉터리 권한/경로, 인증서 경로 오타, 2379 포트 충돌, 디스크 가득참
sudo vim /etc/kubernetes/manifests/etcd.yaml
df -h /var/lib/etcd        # 디스크 확인
```

## 5. 노드 리소스 압박

```bash
kubectl describe node node01 | grep -A5 Conditions
# DiskPressure → 노드에서: df -h, crictl rmi --prune (미사용 이미지 정리), 로그 정리
# MemoryPressure → 큰 Pod 퇴거됨(Evicted). kubectl top nodes로 확인
kubectl top nodes
kubectl get pods -A --field-selector=status.phase=Failed   # Evicted Pod 정리 대상
```

## 6. 인증서 문제

```bash
sudo kubeadm certs check-expiration
# 만료 시
sudo kubeadm certs renew all
# 이후 컨트롤 플레인 재시작 + admin.conf 재복사
sudo cp /etc/kubernetes/admin.conf ~/.kube/config
```
```bash
# 개별 인증서 수동 확인
openssl x509 -in /etc/kubernetes/pki/apiserver.crt -noout -dates -subject
```

## 7. 워커 노드 join 문제

| 증상 | 조치 |
|---|---|
| token expired | `kubeadm token create --print-join-command` (컨트롤 플레인에서) |
| ca cert hash mismatch | 위 명령으로 통째로 재발급 |
| 6443 접근 불가 | 방화벽/보안그룹, apiserver 기동 여부 |
| 이미 조인된 흔적 | `kubeadm reset` 후 재조인 |

## 8. 종합 시나리오 연습 (킬러 유형)

**"node01이 NotReady다. Ready로 만들어라."**
```bash
kubectl describe node node01              # ① 원인 힌트
ssh node01
sudo systemctl status kubelet             # ② inactive면 start
sudo journalctl -u kubelet --no-pager | tail -30   # ③ 시작 실패면 로그
sudo vim /var/lib/kubelet/config.yaml     # ④ 로그가 가리키는 파일 수정
sudo systemctl restart kubelet
exit
kubectl get nodes                         # ⑤ Ready 확인 (반드시!)
```

**"컨트롤 플레인이 응답하지 않는다."**
```bash
ssh controlplane
sudo crictl ps -a                         # ① 죽은 컴포넌트 식별
sudo crictl logs <id>                     # ② 원인 (또는 /var/log/pods)
sudo vim /etc/kubernetes/manifests/<컴포넌트>.yaml   # ③ 수정
watch sudo crictl ps                      # ④ 재기동 확인
kubectl get nodes                         # ⑤ 최종 검증
```
