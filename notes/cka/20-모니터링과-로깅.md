# 20. 모니터링과 로깅

> 도메인: 트러블슈팅 (30%)
> 시험 포인트: "클러스터와 애플리케이션 리소스 사용량 모니터링", "컨테이너 출력 스트림 관리". `kubectl top`의 정렬 옵션과 결과를 파일로 저장하는 유형이 자주 나온다.

---

## 1. metrics-server

- 클러스터 리소스 메트릭(CPU/메모리)의 표준 소스. kubelet에서 수집해 **Metrics API**(`metrics.k8s.io`)로 제공
- `kubectl top`과 HPA가 의존. **저장 없음**(실시간 스냅샷) — 이력이 필요하면 Prometheus 등
- 설치 확인:
```bash
kubectl get pods -n kube-system | grep metrics-server
kubectl get apiservices | grep metrics       # v1beta1.metrics.k8s.io True?
kubectl top nodes                            # 동작 검증
```
- 설치 (실습 환경):
```bash
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
# kubeadm 로컬 클러스터는 TLS로 실패할 수 있음 → deployment args에 --kubelet-insecure-tls 추가
```

## 2. kubectl top (빈출 옵션까지)

```bash
kubectl top nodes
kubectl top nodes --sort-by=cpu                 # cpu | memory
kubectl top pods -A
kubectl top pods -n dev --sort-by=memory
kubectl top pods --containers                   # 컨테이너 단위 분해
kubectl top pods -l app=web
```

### 시험 유형: "CPU를 가장 많이 쓰는 Pod 이름을 파일에 저장하라"
```bash
kubectl top pods -A --sort-by=cpu | head -2
# 맨 위 Pod 이름을
echo "<pod-name>" > /opt/answer.txt
```
> 문제가 요구하는 형식(이름만? 네임스페이스 포함?)을 정확히 읽을 것.

## 3. 컨테이너 로그 (kubectl logs 완전판)

컨테이너의 **stdout/stderr**가 로그의 원천. kubelet이 노드 디스크에 저장하고 kubectl이 읽어온다.

```bash
kubectl logs <pod>                          # 단일 컨테이너
kubectl logs <pod> -c <container>           # 멀티 컨테이너 (지정 안 하면 에러)
kubectl logs <pod> --all-containers
kubectl logs <pod> --previous              # 재시작 전 인스턴스 (CrashLoop!)
kubectl logs -f <pod>                       # 팔로우
kubectl logs <pod> --tail=100 --since=1h
kubectl logs <pod> --timestamps
kubectl logs deploy/web                     # 워크로드 지정 (Pod 하나 골라줌)
kubectl logs -l app=web --prefix            # 레이블 셀렉터 + Pod명 접두
```

### 시험 유형: "에러 로그를 추출해 파일로 저장"
```bash
kubectl logs <pod> | grep -i error > /opt/error.log
kubectl logs <pod> --previous > /opt/crash.log
```

## 4. 노드 레벨 로그 위치

kubectl이 안 될 때(컨트롤 플레인 장애) 또는 노드에서 직접 확인할 때:

| 경로 | 내용 |
|---|---|
| `/var/log/pods/<ns>_<pod>_<uid>/<container>/*.log` | 컨테이너 로그 원본 |
| `/var/log/containers/*.log` | 위 파일로의 심링크 (`<pod>_<ns>_<container>-<id>.log`) |
| `journalctl -u kubelet` | kubelet 로그 |
| `journalctl -u containerd` | 런타임 로그 |
| `crictl logs <container-id>` | 런타임 경유 컨테이너 로그 |

## 5. 이벤트

```bash
kubectl get events -n dev --sort-by=.metadata.creationTimestamp
kubectl get events -A --field-selector type=Warning
kubectl get events --field-selector involvedObject.name=mypod
kubectl events --for pod/mypod             # 신형 명령 (v1.27+)
```
- 이벤트 보존은 기본 **1시간** — 오래된 문제는 이벤트가 없을 수 있다

## 6. 로깅 아키텍처 패턴 (개념 문제 대비)

1. **노드 레벨 (기본)**: stdout → kubelet이 파일 저장 → `kubectl logs`
2. **노드 에이전트**: DaemonSet(fluent-bit 등)이 `/var/log/pods`를 수집해 중앙 저장소로 — 클러스터 표준 패턴
3. **사이드카**:
   - 앱이 파일에만 로그를 쓸 때, 사이드카가 `tail -f`로 stdout에 흘려보냄 (emptyDir 공유)
   - init 컨테이너 + `restartPolicy: Always` (v1.33 GA 사이드카)
4. **앱 직접 전송**: 앱이 로깅 백엔드로 직접 push

### 사이드카 로그 스트리밍 예 (시험에 나올 수 있는 구성)
```yaml
spec:
  containers:
  - name: app
    image: myapp
    volumeMounts:
    - { name: logs, mountPath: /var/log/app }
  - name: log-streamer                      # 사이드카
    image: busybox
    command: ["sh", "-c", "tail -F /var/log/app/app.log"]
    volumeMounts:
    - { name: logs, mountPath: /var/log/app }
  volumes:
  - name: logs
    emptyDir: {}
```
이후 `kubectl logs <pod> -c log-streamer`로 확인.

## 7. 리소스 사용량 종합 점검 루틴

```bash
kubectl top nodes                                  # 노드 수준 병목?
kubectl describe node <node> | grep -A10 "Allocated resources"   # requests/limits 합계
kubectl top pods -A --sort-by=memory | head        # 과소비 Pod
kubectl get pods -A --field-selector=status.phase=Failed          # Evicted 확인
```

## 8. 체크리스트

- [ ] metrics-server의 역할과 `kubectl top`의 `--sort-by`, `--containers`를 안다
- [ ] logs의 `-c`, `--previous`, `--tail`, `-l` 옵션이 손에 익었다
- [ ] `/var/log/pods`와 `crictl logs`로 kubectl 없이 로그를 볼 수 있다
- [ ] 이벤트 정렬/필터 명령을 안다
- [ ] 사이드카 로그 스트리밍 패턴을 구성할 수 있다
- [ ] 결과를 지정된 파일 경로에 저장하는 문제 형식에 익숙하다
