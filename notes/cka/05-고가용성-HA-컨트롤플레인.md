# 05. 고가용성(HA) 컨트롤 플레인

> 도메인: 클러스터 아키텍처, 설치 및 구성 (25%)
> 시험 포인트: 2025 개정판에 "고가용성 컨트롤 플레인 구현 및 구성"이 명시됨. 전체를 직접 구축하는 문제보다는 구조 이해와 컨트롤 플레인 추가 join이 나올 가능성이 높다.

---

## 1. 왜 HA인가

- 컨트롤 플레인이 1대면 그 노드 장애 = 클러스터 관리 불능 (기존 워크로드는 돌지만 배포/복구/스케줄링 불가)
- HA = **컨트롤 플레인 노드 여러 대 + apiserver 앞의 로드밸런서**

## 2. 두 가지 토폴로지

### 2-1. Stacked etcd (일반적, kubeadm 기본)
- 각 컨트롤 플레인 노드에 etcd가 **함께** 올라감
- 구성 간단, 노드 수 절약
- 단점: 노드 하나 죽으면 etcd 멤버 + 컨트롤 플레인 인스턴스가 동시에 죽음

```
[LB] ──> CP1(apiserver+etcd) 
     ──> CP2(apiserver+etcd)
     ──> CP3(apiserver+etcd)
```

### 2-2. External etcd
- etcd 클러스터를 **별도 노드들**에 분리
- 장애 격리 우수, 대신 노드가 2배 필요 (CP 3 + etcd 3 = 6대)

### etcd 정족수(quorum)
- etcd는 Raft 합의 기반: **과반수가 살아 있어야** 쓰기 가능
- 멤버 수는 **홀수**로: 3대(1대 장애 허용), 5대(2대 장애 허용)
- 2대는 1대보다 오히려 나쁨 (1대만 죽어도 과반 상실)

## 3. 로드밸런서

- apiserver(6443) 앞에 TCP 로드밸런서 배치 (HAProxy, keepalived, 클라우드 LB 등)
- 모든 클라이언트(kubectl, kubelet, 컴포넌트)가 LB 주소로 접속

HAProxy 예시 (개념 확인용):
```
frontend kube-apiserver
    bind *:6443
    mode tcp
    default_backend apiservers
backend apiservers
    mode tcp
    balance roundrobin
    option tcp-check
    server cp1 10.0.0.11:6443 check
    server cp2 10.0.0.12:6443 check
    server cp3 10.0.0.13:6443 check
```

## 4. kubeadm으로 HA 클러스터 만들기

### 4-1. 첫 번째 컨트롤 플레인

```bash
sudo kubeadm init \
  --control-plane-endpoint "LB_주소:6443" \
  --upload-certs \
  --pod-network-cidr=10.244.0.0/16
```

- **`--control-plane-endpoint`가 핵심**: 인증서와 kubeconfig가 LB 주소 기준으로 생성됨. 단일 노드로 시작해도 나중에 HA로 확장할 계획이면 처음부터 지정할 것 (나중에 바꾸기 어려움).
- `--upload-certs`: 컨트롤 플레인 인증서를 암호화해 클러스터 Secret(`kubeadm-certs`)에 업로드 → 추가 CP 노드가 자동으로 받아감 (2시간 유효).

### 4-2. 추가 컨트롤 플레인 조인

init 출력에 나오는 컨트롤 플레인용 join 명령 사용:
```bash
sudo kubeadm join LB_주소:6443 \
  --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash> \
  --control-plane \
  --certificate-key <key>
```

- 워커 join과의 차이: **`--control-plane --certificate-key`** 두 옵션.
- certificate-key가 만료(2시간)됐으면 재발급:
  ```bash
  sudo kubeadm init phase upload-certs --upload-certs   # 새 certificate-key 출력
  kubeadm token create --print-join-command             # 토큰 부분 재발급
  ```

### 4-3. 워커 조인
일반 join과 동일 (03단원). 대상 주소만 LB.

## 5. 확인

```bash
kubectl get nodes                                  # control-plane 롤 여러 개
kubectl get pods -n kube-system | grep etcd        # CP 수만큼 etcd
# etcd 멤버 확인
ETCDCTL_API=3 etcdctl member list \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
```

## 6. HA에서 컴포넌트 동작 방식

- **apiserver**: 무상태(stateless) → 여러 인스턴스가 동시에 활성(active-active), LB가 분산
- **controller-manager / scheduler**: **리더 선출(leader election)** — 한 번에 하나만 활성, 나머지는 대기
- **etcd**: Raft 리더 1 + 팔로워, 쓰기는 리더 경유

## 7. 체크리스트

- [ ] stacked vs external etcd 차이와 장단점을 설명할 수 있다
- [ ] etcd 정족수 — 3대는 1대 장애 허용, 홀수 유지 이유를 안다
- [ ] `--control-plane-endpoint`, `--upload-certs`의 역할을 안다
- [ ] CP 조인 = `--control-plane --certificate-key` 를 안다
- [ ] scheduler/controller-manager는 리더 선출로 동작함을 안다
