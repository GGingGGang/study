# 19. 트러블슈팅 II — 워크로드와 네트워크

> 도메인: 트러블슈팅 (30%)
> 시험 포인트: Pod 상태별 원인 매핑과 "서비스가 안 붙는" 문제의 체계적 추적. 속도가 생명 — 상태만 보고 바로 원인 후보를 좁힐 수 있어야 한다.

---

## 1. Pod 상태별 원인 지도 (암기표)

| 상태/이유 | 뜻 | 1순위 확인 | 흔한 원인 |
|---|---|---|---|
| `Pending` | 스케줄 안 됨 | `describe pod` Events | 리소스 부족, taint, affinity, PVC 미바인딩 |
| `ImagePullBackOff` / `ErrImagePull` | 이미지 못 받음 | Events의 정확한 에러 | 이미지명/태그 오타, 프라이빗 레지스트리 인증(imagePullSecrets) |
| `CrashLoopBackOff` | 컨테이너가 반복 사망 | `logs --previous` | 앱 에러, 잘못된 command/args, 설정 누락, liveness 과민 |
| `CreateContainerConfigError` | 설정 참조 실패 | Events | 없는 ConfigMap/Secret/key 참조 |
| `OOMKilled` (Terminated reason) | 메모리 초과 | `describe pod` Last State | memory limit 너무 낮음 |
| `ContainerCreating` 장기화 | 준비 안 됨 | Events | 볼륨 마운트 실패, CNI 문제 |
| `Init:x/y` 멈춤 | init 컨테이너 실패 | `logs <pod> -c <init컨테이너>` | init의 대기 조건 미충족 |
| `Completed` | 정상 종료 | - | Job이면 정상. Deployment면 command가 종료되는 명령 |
| `Evicted` | 노드에서 퇴거 | `describe pod` | 노드 리소스 압박 |
| Running인데 응답 없음 | 앱 수준 문제 | logs, readiness | readiness 실패로 트래픽 제외 |

### 표준 진단 명령 세트
```bash
kubectl get pods -o wide                       # 상태 + 노드 + IP
kubectl describe pod <pod>                     # Events (거의 항상 여기서 해결)
kubectl logs <pod> [-c <컨테이너>]              # 현재 로그
kubectl logs <pod> --previous                  # 죽기 전 로그 (CrashLoop 필수)
kubectl get events --sort-by=.metadata.creationTimestamp -n <ns>
kubectl exec -it <pod> -- sh                   # 내부 확인
kubectl debug -it <pod> --image=busybox       # 쉘 없는 이미지에 임시 컨테이너
```

## 2. CrashLoopBackOff 공략

```bash
kubectl logs <pod> --previous          # ① 죽기 직전 로그가 최우선
kubectl describe pod <pod>             # ② Exit Code 확인
```
| Exit Code | 의미 |
|---|---|
| 0 | 정상 종료 (계속 떠 있어야 할 프로세스가 그냥 끝남 — command 문제) |
| 1 | 앱 에러 |
| 137 | SIGKILL = **OOMKilled** 또는 liveness 실패 강제종료 |
| 139 | segfault |
| 126/127 | 명령 실행 불가/없음 (command 오타) |

- liveness가 너무 빡빡해서 죽이는 경우: `initialDelaySeconds`/`failureThreshold` 완화
- OOM: limits.memory 증가

## 3. Deployment 레벨 문제

```bash
kubectl get deploy,rs,pods -l app=web
kubectl describe deploy web            # Conditions, 이벤트
kubectl rollout status deploy/web      # 롤아웃이 멈춘 이유 표시
```
- **Pod가 아예 안 생김**: replicas=0? ResourceQuota 초과? (deploy/rs describe에 거부 이벤트) controller-manager 죽음?
- **새 버전이 안 퍼짐**: 새 RS의 Pod가 CrashLoop → 롤아웃 정지 상태. `kubectl rollout undo`
- **selector와 template label 불일치**: 생성 자체가 거부됨

## 4. 서비스 연결 문제 — 체계적 추적 (초빈출)

증상: "web에서 api-svc가 안 불린다."

```bash
# ① Service 존재/포트 확인
kubectl get svc api-svc -o wide            # port, targetPort, selector 확인

# ② Endpoints 확인 — 여기서 대부분 판가름
kubectl describe svc api-svc               # Endpoints: <none> ?
kubectl get endpointslices -l kubernetes.io/service-name=api-svc

#   Endpoints 비었으면:
kubectl get pods -l <svc의 selector> --show-labels   # (a) 셀렉터-레이블 불일치?
kubectl get pods -o wide                              # (b) Pod가 Ready인가? (readiness 실패?)

# ③ 포트 매핑 확인
#   svc의 targetPort == 컨테이너가 실제 리슨하는 포트?
kubectl exec <api-pod> -- netstat -tlnp   # 또는 ss -tlnp

# ④ DNS 확인
kubectl run tmp --image=busybox --rm -it --restart=Never -- nslookup api-svc

# ⑤ 직접 연결 격리 테스트
kubectl run tmp --image=busybox --rm -it --restart=Never -- wget -qO- --timeout=2 http://<PodIP>:<포트>   # Pod 직통은 되나?
kubectl run tmp --image=busybox --rm -it --restart=Never -- wget -qO- --timeout=2 http://api-svc:80       # 서비스 경유는?

# ⑥ Pod 직통 OK + 서비스 실패 → kube-proxy 확인
kubectl get pods -n kube-system -l k8s-app=kube-proxy -o wide
kubectl logs -n kube-system <kube-proxy-pod>

# ⑦ NetworkPolicy 확인
kubectl get netpol -A
kubectl describe netpol <이름> -n <ns>     # 대상/방향/포트가 트래픽을 막는지
```

### 원인 정리
| 관찰 | 원인 |
|---|---|
| Endpoints `<none>` | 셀렉터 불일치 / Pod NotReady / Pod 없음 |
| Endpoints 있는데 연결 거부 | targetPort ≠ 실제 리슨 포트 |
| Pod 직통 OK, svc 실패 | kube-proxy, (드물게) 서비스 포트 설정 |
| 특정 ns에서만 실패 | NetworkPolicy |
| 이름 해석 실패 | CoreDNS (15단원 루틴) |
| NodePort 외부 접근 실패 | 노드 방화벽, nodePort 범위, externalTrafficPolicy |

## 5. Ingress 연결 문제

```bash
kubectl describe ing web-ing        # backends 에 IP가 잡히나
kubectl get pods -n ingress-nginx   # 컨트롤러 살아있나
kubectl logs -n ingress-nginx <controller-pod>   # 요청이 도달하나, 404/503 사유
```
- 404: host/path 규칙 불일치 (curl에 `-H "Host: ..."` 붙였는지)
- 503: 백엔드 서비스 Endpoints 비어 있음 → 4절 루틴으로
- 아예 무반응: ingressClassName 오타

## 6. CNI / Pod 네트워크 문제

- 새 Pod가 전부 `ContainerCreating`에서 멈춤 + describe에 `failed to setup network` → CNI 문제
```bash
kubectl get pods -n kube-system    # CNI DaemonSet (calico-node 등) 상태
ssh <node>
ls /etc/cni/net.d/                 # 설정 존재?
ls /opt/cni/bin/                   # 바이너리 존재?
```

## 7. "컨테이너 출력 스트림 관리" (커리큘럼 항목)

- 컨테이너 로그 = **stdout/stderr** → kubelet이 노드의 `/var/log/pods/`에 저장
- `kubectl logs`의 소스가 이 파일들. 파일로 쓰는 앱 로그는 kubectl logs로 안 보임 → 사이드카로 tail 하거나 stdout으로 내보내도록
```bash
kubectl logs deploy/web --all-containers --prefix
kubectl logs <pod> -c <c> --tail=100 --since=5m -f
kubectl logs -l app=web --max-log-requests=10      # 레이블로 여러 Pod
```

## 8. 체크리스트

- [ ] Pod 상태 → 원인 매핑표를 안 보고 말할 수 있다
- [ ] CrashLoop이면 반사적으로 `logs --previous`와 Exit Code를 본다
- [ ] 서비스 문제 추적 7단계(svc→endpoints→포트→DNS→직통→kube-proxy→netpol)가 몸에 배었다
- [ ] Endpoints가 비는 3대 원인을 즉답한다
- [ ] Exit Code 137 = OOM/강제종료를 안다
- [ ] 컨테이너 로그는 stdout/stderr 기반임을 안다
