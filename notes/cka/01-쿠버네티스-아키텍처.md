# 01. 쿠버네티스 아키텍처

> 도메인: 클러스터 아키텍처, 설치 및 구성 (25%)
> 시험 포인트: 컴포넌트의 역할과 **파일 위치**를 아는 것이 트러블슈팅(30%)의 기반이 된다.

---

## 1. 전체 구조

쿠버네티스 클러스터 = **컨트롤 플레인(control plane)** + **워커 노드(worker node)**

```
┌─────────────── Control Plane ───────────────┐
│  kube-apiserver ── etcd                      │
│  kube-scheduler                              │
│  kube-controller-manager                     │
│  (cloud-controller-manager)                  │
└──────────────────────────────────────────────┘
        ▲ (모든 통신은 apiserver를 경유)
┌─────────────── Worker Node ─────────────────┐
│  kubelet ── 컨테이너 런타임(containerd)       │
│  kube-proxy                                  │
└──────────────────────────────────────────────┘
```

## 2. 컨트롤 플레인 컴포넌트

### kube-apiserver
- 클러스터의 **유일한 진입점**. 모든 컴포넌트와 kubectl이 여기에 REST로 통신.
- 인증(Authentication) → 인가(Authorization, RBAC) → 어드미션(Admission Control) 순서로 요청을 처리.
- **etcd에 직접 접근하는 유일한 컴포넌트.**
- 기본 포트: **6443**

### etcd
- 클러스터의 **모든 상태를 저장하는 key-value 저장소** (분산 합의: Raft).
- 데이터 디렉터리: `/var/lib/etcd`
- 클라이언트 포트 **2379**, 피어 포트 **2380**
- 백업/복원은 04단원 참고 — **시험 단골 주제**.

### kube-scheduler
- 새로 생성된 Pod 중 `nodeName`이 비어 있는 것을 감시하고, 필터링(predicates) → 점수화(scoring)를 거쳐 노드를 결정.
- 스케줄러는 **결정만** 하고, 실제 실행은 해당 노드의 kubelet이 담당.

### kube-controller-manager
- 여러 컨트롤러의 집합체: Deployment, ReplicaSet, Node, Job, EndpointSlice, ServiceAccount 컨트롤러 등.
- 각 컨트롤러는 "현재 상태를 원하는 상태(desired state)로 수렴"시키는 조정 루프(reconciliation loop)를 돈다.

### cloud-controller-manager
- 클라우드 제공자 연동(LoadBalancer 프로비저닝, 노드 라이프사이클 등). 온프레미스/kubeadm 클러스터엔 보통 없음.

## 3. 노드 컴포넌트

### kubelet
- 각 노드의 에이전트. **시스템 서비스(systemd)로 실행됨** — Pod가 아님!
- apiserver에서 PodSpec을 받아 컨테이너 런타임(CRI)에 실행을 지시하고, 상태를 보고.
- **static pod**: `/etc/kubernetes/manifests/` 디렉터리의 YAML을 apiserver 없이도 직접 실행 (컨트롤 플레인 부트스트랩의 핵심 원리).
- 주요 파일:
  - 서비스 설정: `systemctl status kubelet`, `journalctl -u kubelet`
  - kubelet 설정 파일: `/var/lib/kubelet/config.yaml`
  - apiserver 접속 정보: `/etc/kubernetes/kubelet.conf`

### kube-proxy
- Service의 가상 IP(ClusterIP)를 실제 Pod IP로 연결하는 규칙을 노드마다 유지.
- 모드: **iptables**(기본), ipvs, nftables. DaemonSet으로 배포됨.

### 컨테이너 런타임
- CRI(Container Runtime Interface) 구현체. 사실상 표준은 **containerd**.
- 노드에서 직접 컨테이너를 조회할 땐 `crictl` 사용 (docker 명령 아님):
  ```bash
  crictl ps          # 실행 중 컨테이너
  crictl logs <id>   # 컨테이너 로그
  ```

## 4. 애드온
- **CoreDNS**: 클러스터 내부 DNS (Deployment로 kube-system에 배포)
- **CNI 플러그인**: Pod 네트워크 (Calico, Flannel, Cilium 등)
- **metrics-server**: `kubectl top`에 필요한 리소스 메트릭 수집

## 5. kubeadm 클러스터의 컨트롤 플레인 = Static Pod

kubeadm으로 만든 클러스터에서 apiserver, etcd, scheduler, controller-manager는 전부 **static pod**다.

```bash
ls /etc/kubernetes/manifests/
# etcd.yaml  kube-apiserver.yaml  kube-controller-manager.yaml  kube-scheduler.yaml
```

- 이 파일을 수정하면 kubelet이 감지해서 해당 Pod를 **자동 재생성**한다.
- 파일을 디렉터리 밖으로 옮기면 Pod가 **중지**된다 (트러블슈팅/etcd 복원 때 활용).
- static pod 이름에는 노드명이 접미사로 붙음: `kube-apiserver-controlplane01`

## 6. 꼭 외워야 할 디렉터리/파일

| 경로 | 내용 |
|---|---|
| `/etc/kubernetes/manifests/` | 컨트롤 플레인 static pod 매니페스트 |
| `/etc/kubernetes/pki/` | 클러스터 인증서 (ca.crt, apiserver.crt 등) |
| `/etc/kubernetes/pki/etcd/` | etcd 인증서 |
| `/etc/kubernetes/admin.conf` | 관리자 kubeconfig |
| `/etc/kubernetes/kubelet.conf` | kubelet의 apiserver 접속용 kubeconfig |
| `/var/lib/kubelet/config.yaml` | kubelet 설정 |
| `/var/lib/etcd/` | etcd 데이터 |
| `/etc/cni/net.d/` | CNI 설정 |
| `/opt/cni/bin/` | CNI 플러그인 바이너리 |
| `/var/log/pods/`, `/var/log/containers/` | 노드 레벨 컨테이너 로그 |

## 7. 요청 처리 흐름 (Deployment 생성 예)

1. `kubectl apply` → apiserver (인증/인가/어드미션 통과)
2. apiserver가 etcd에 Deployment 객체 저장
3. Deployment 컨트롤러가 감지 → ReplicaSet 생성
4. ReplicaSet 컨트롤러가 감지 → Pod 객체 생성 (nodeName 비어 있음)
5. scheduler가 감지 → 노드 결정, Pod에 nodeName 기록
6. 해당 노드 kubelet이 감지 → CRI로 컨테이너 실행
7. kubelet이 Pod 상태를 apiserver에 보고 → etcd에 저장

> 이 흐름을 알면 "Pod가 Pending인데 왜?"(→ scheduler 문제 또는 스케줄 불가), "Pod가 생성 자체가 안 되는데?"(→ controller-manager 문제) 같은 트러블슈팅 방향을 바로 잡을 수 있다.
